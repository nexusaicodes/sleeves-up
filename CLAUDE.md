# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A native Android check-in/check-out tracker built around **showing up**, not hours cleared. It records presence-gated check-in/out intervals, shows what each day held, and counts the days shown up for.

**Branding.** The product is **Sleeves Up** — a string only: `app_name` plus the copy that spells it out (`licenses_intro`, `Feedback.draft`). Package, `applicationId`, Gradle build, types and file names all still say CheckIn (see Build Commands). The name describes a state, not a measurement or an exhortation. Its metaphor is glossed **once**, in the Play listing's opening line, and never in in-app copy — "roll your sleeves up!" in a notification or empty state makes the name a mascot, the gamification register the app refuses. `play-store-assets/LISTING.md`'s vocabulary table holds the rule.

**Rules:**
- Net time = sum of completed intervals per day (open intervals excluded). Nothing is ever subtracted from an interval.
- Every day counts — 7 days a week, no weekend or holiday exemption.
- **A day counts because it has a session.** No target, no half-day tier, no deficit: 45 minutes counts exactly as much as nine hours.
- Hours are shown everywhere (totals, charts, the calendar's screen-reader text, CSV) as a **plain quantity with no direction** — never a ring fill, colour ramp, superlative or comparison with the user's own best.
- **Sessions are immutable** — no edit, delete or manual entry.
- Every check-in **and** check-out is gated by a presence check: camera-HAL face detection (offline, no image captured), with **device unlock** as the fallback.
- **Habits are separate records, viewed one at a time** — each with its own sessions, calendar, Reports, CSV, reminder time and notification channel; a top-bar switcher picks which one every tab shows. **Nothing compares, ranks or totals two habits.** **One open session across all habits**; the switcher locks to it while it runs.
- Self-contained: Room only, no backend, no `INTERNET` permission; CSV export via the share sheet. The one outside question is Play's in-app update check, asked of the Play Store app over IPC. The record rides Android's own backup (`data_extraction_rules.xml`), which the app sends nothing to.

## Build Commands

Gradle wrapper pinned to **8.13** (Kotlin 1.9.20 + AGP 8.13.2 break on Gradle 9, which removed `HasConvention`). `gradle/gradle-daemon-jvm.properties` requires a **JetBrains JDK 21** daemon — Android Studio's bundled one, found automatically there. For CLI builds:

```bash
export JBR="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
./gradlew :app:testDebugUnitTest -Dorg.gradle.java.installations.paths="$JBR"  # JVM unit tests
./gradlew :app:assembleDebug     -Dorg.gradle.java.installations.paths="$JBR"  # Build debug APK
./gradlew :app:installDebug      -Dorg.gradle.java.installations.paths="$JBR"  # Install on a device
./gradlew staticAnalysis         -Dorg.gradle.java.installations.paths="$JBR"  # ktlint + detekt
./gradlew :app:verifyLicenseCoverage -Dorg.gradle.java.installations.paths="$JBR"  # licence list vs classpath
./gradlew :app:verifyDocMap          -Dorg.gradle.java.installations.paths="$JBR"  # this file vs the tree
./gradlew :app:lintDebug             -Dorg.gradle.java.installations.paths="$JBR"  # Android lint
./gradlew ktlintFormat           -Dorg.gradle.java.installations.paths="$JBR"  # Auto-fix formatting
```

Single test class: `./gradlew :app:testDebugUnitTest --tests "com.checkin.app.ConsistencyStatsTest"`.

**Three identities, deliberately different.** `rootProject.name` is `CheckInApp` (the Gradle build only). `namespace` is `com.checkin.app` (Kotlin package, `R`, `BuildConfig`). `applicationId` is `com.nexusai.checkin.app` (Play identity, data directory, FileProvider authority `${applicationId}.fileprovider`). The launcher component is therefore **`com.nexusai.checkin.app/com.checkin.app.MainActivity`** — `am start -n com.checkin.app/.MainActivity` fails with `does not exist`. The `applicationId` has shipped to Play and is permanent; leave the split alone.

**Toolchain.** JDK 17 source/target; `compileSdk`/`targetSdk` **36**; **`minSdk` 31** (Android 12). Two platform features arrived in 33, and each has exactly one API-level branch: `POST_NOTIFICATIONS` (`notificationsNeedRuntimeGrant`/`holdsNotificationPermission` in `notify/Notifier.kt`, over the pure `NotificationDelivery.needsRuntimeGrant`) and the per-app locale (`AppContainer.languageSettings`, null below 33). **Never read `POST_NOTIFICATIONS` with a bare `checkSelfPermission`**: below 33 it reports DENIED for a permission that does not exist, `canDeliver` refuses every post, and every notification goes silently dead — lint reports only an `InlinedApi` warning. The blockers below 31 are `Window.isNavigationBarContrastEnforced` (`ui/theme/Theme.kt`), `android:Theme.DeviceDefault.DayNight` (`themes.xml`) and biometric 1.1.0's `BIOMETRIC_STRONG or DEVICE_CREDENTIAL` (API 30).

**Tests** (`app/src/test/java/com/checkin/app/`) are pure JVM: no Robolectric, no mocking library — seams are hand-faked (`Fakes.kt`, `FakeCheckInSessionDao.kt`, `FakeHabitDao.kt`), and JUnit plus `kotlinx-coroutines-test` are the only test dependencies. There is **no `androidTest` source set**.

**Versioning** (`gradle.properties`, overridable with `-P`): `VERSION_CODE` is the release day as `YYYYMMDD`, set by hand and strictly increasing across uploads (same-day rebuild: `YYYYMMDDNN`); `VERSION_NAME` is the user-facing label. Promoting an `.aab` across tracks reuses its code; a rebuild needs a new one. A tag marks the commit a release was **cut** from and can precede the upload by weeks — ask Play what is live. Never move or reuse a pushed tag.

**IMPORTANT — every change ships through a version branch.** `main` holds only released code. The next release collects on a version branch named for it (`v3.2`), cut fresh from `main`; each feature or fix is its own branch off that version branch, and **every PR targets the version branch, never `main`**. When the release is ready, the version branch merges to `main` in one PR, that merge is tagged with the version, and the build from it is what goes to Play. If no version branch is open, propose which version the change belongs to (with the reason) and **confirm before creating it** — never pick a version silently, and never branch a feature off `main` directly.

**Static analysis**: **ktlint** (plugin 12.1.1, engine 1.5.0) and **detekt** 1.23.8 on every project including the root script, both behind `staticAnalysis`. Style comes from `.editorconfig` (`intellij_idea`, 120 columns, `@Composable` exempt from `function-naming`); `config/detekt/detekt.yml` states only overrides of detekt's defaults and never duplicates ktlint (`MaxLineLength` off). **No detekt baseline, deliberately** — `baseline.xml` is wired but absent because the tree is clean. Answer a finding with a fix or a site-level `@Suppress` carrying the reason (e.g. `CheckInService.enterForeground`, `SessionWatchdog.reviveIfNeeded`, `DefaultCsvExporter.export`).

**Pre-commit hook** (`githooks/pre-commit`; enable with `git config core.hooksPath githooks`) runs `staticAnalysis` when a `.kt`/`.kts` file is staged, and always refuses `*.jks`, `*.keystore`, `keystore.properties` and `local.properties` — `git add -f` beats `.gitignore`, and a leaked upload key is unrecoverable. Tests and lint are CI's job.

**`verifyDocMap`** fails when (1) a main-source `.kt` file's name appears nowhere in this file, (2) a backticked `….kt` path here resolves to nothing in main or test sources, or (3) a source comment (or `app/build.gradle.kts`) names `Type.member` on a top-level project type that declares no such member. **No allowlist**: a new file gets a line in Key Source Paths. It cannot see a reference whose owner type is gone, nor a wrong value or count in prose.

**CI** (`.github/workflows/ci.yml`, push/PR to `main` and every version branch, `v[0-9]*`) sets up JetBrains Runtime 21 and passes `-Dorg.gradle.java.installations.paths="$JAVA_HOME"`. Steps, cheapest first: `staticAnalysis :app:verifyDocMap` (no classpath, fails in seconds) → `:app:testDebugUnitTest :app:verifyLicenseCoverage :app:assembleDebug` → `:app:lintDebug`. **Lint is its own gate**: the only one that sees manifest and resources (`UnusedResources` is an **error**; indirect references take a scoped `tools:ignore` with a reason) and the only one enforcing AndroidX's Java-side `@RequiresOptIn` markers, which the Kotlin compiler ignores.

## Architecture

**MVVM: Jetpack Compose + Room + a foreground service + CameraX/Camera2 face detection + BiometricPrompt.** Manual DI: `CheckInApplication` holds an `AppContainer` that builds the repositories, `platform/` seams, notification and nudge machinery, session lifecycle, `TimeSource` and an app-wide `CoroutineScope`. Each `ViewModel` is constructor-injected via a `viewModelFactory`, exposes **one** `UiState` `StateFlow` built over Room `Flow`s, and is JVM-tested with fakes.

```
UI (4 tabs + detail screens) → ViewModel (one UiState) → Repository → Room DAO → SQLite
                                    ↕
                    CheckInService (foreground service: the timer notification only)
                                    ↕
        Presence gate: CameraX preview + Camera2 HAL face metadata → BiometricPrompt fallback
```

- **Pure core** (no Android, unit-tested): `PresenceCheckState`, `ConsistencyStats`, `SessionRhythm`, `TimeSource`/`DayClock`, `HabitRules`, `SessionSchedule`/`SessionClock`, `NudgeEligibility`/`NudgeSchedule`, `TapRouting`, `WidgetFace`, `FirstRun`, `ReportScope`, `ChartGeometry`, `CsvFormat`, `TimeFormat`.
- **Room `_app`, version 2**:
  - `CheckInSession` (`sessions`): `id`, `started_at`, `stopped_at` (null while open), `duration` (null until check-out), `date_key` (`yyyy-MM-dd` of check-in), `closed_by` (`ClosedBy`'s frozen string), `habit_id` (default 1, indexed, **no foreign key** — habits are never deleted).
  - `Habit` (`habits`): `id`, `uuid` (unique, the permanent identity), `name` (null = owed a name), `archived`, `created_at`, `channel_id`.
  - `AppState` (`app_state`, one row): `selected_habit_id`.

  `MIGRATION_1_2` adds `habits`, `app_state` and `sessions.habit_id DEFAULT 1`, so an older record lands in the seed habit (`Habit.SEED_ID`). `AppDatabase.seedIfEmpty` creates that unnamed, selected seed habit on any habit-less database, at the end of the migration **and on every open** (the destructive fallback runs no `onCreate`). `AppDatabase`'s KDoc covers writing the next migration. **No gate catches a broken migration** — install the previous build, seed it, install over it. `fallbackToDestructiveMigration()` is a development backstop only.
- **`nudges.db`** (`NudgeSendDatabase`, version 3) is a separate database holding only the nudge send ledger, so it can never put session records at migration risk.
- **`CheckInService`** — `specialUse` foreground service showing the timer notification and nothing else: no ticker (a platform chronometer), no alarms (`SessionLifecycleRunner` owns them). Its `checkin_timer_prefs` mirror only renders the notification on a `START_STICKY` restart; **the DB row is authoritative** — every command reconciles via `ServiceReconciler`, and a closed or absent row tears the service down.
- **Presence gate** — `PresenceGate` is the single entry point and the only `CAMERA` request: disclosure → `CAMERA` + `POST_NOTIFICATIONS` → `PresenceCheckScreen`, which passes itself on the first frame the HAL reports a face. Device unlock is offered after `DEVICE_UNLOCK_OFFERED_AFTER_MS` (10s) or at once on a non-detecting camera; with no screen lock, a route to security settings instead, so the gate is never a dead end. Two callers: the root gate in `AppRoot` (driven by `PresenceCheckSignal`: a check-out from the timer or reminder notification or the home-screen widget, or a check-in from a nudge or the widget — the widget's through the habit picker when there is a choice) and the in-app gate in `AppNavScaffold`. `MainActivity` is a `FragmentActivity` because `BiometricPrompt` requires one. Gate and nav host render mutually exclusively, with the nav controller hoisted above the switch so the back stack survives.

## Gotchas & Non-Obvious Behaviors

### Product rules, History and Reports

- **There is no daily target, and adding one back would undo the point.** Targets are missed as the normal case, so a system whose output is "did you clear the bar" mostly reports failure, and a 45-minute day on a bad week reads the same as not turning up — exactly the day the app most needs to reward. A day counts if it has a session; hours are shown as a plain quantity (see the no-direction entry). Any threshold — a minimum session length, a "real day" cutoff, a goal ring — brings the failure back under another name.
- **Hours are a quantity with no direction.** The test for any displayed number: is there a direction in which higher reads as better? For hours it must be no — no ring fill, no colour ramp, no size beyond a chart's own axis, no superlative, no comparison against the user's own past figures. For **presence** yes is fine: days shown up is the app's thesis. A personal-best baseline is worse than a target because it **ratchets** — beat it once and every ordinary day renders as a partial version of that one — and it can be set by accident, since a forgotten session is auto-closed at midnight onto a row nothing can edit. Hence: the app draws no arc anywhere; `ConsistencyStats` returns no longest day or run length; the word "streak" is in no user-facing string; Reports' averages (hours per tracked day, sessions per day shown up) are plain `StatsRow`s, never arcs, because the only denominator to fill one against is the user's own best. The start-time and sessions-per-day splits are plain counts in three hues of equal weight (`descriptiveHues`), never one hue at three strengths — a ramp is how a rank gets back in.
- **Nothing compares habits — the no-grading rule one level out.** Every tab shows the selected habit's record alone; no screen, chart, notification or export sets two habits' figures side by side, ranks or totals them. The switcher and Habits screen show **names and reminder times only**: a count or hours figure per row would grade the habit that had a slow week against the one that didn't. "Habit", never "goal" — a goal is a target. A cross-habit figure cannot be drawn without a direction, so don't add one.
- **The calendar is binary: a day has a session or it does not, and nothing renders red.** Every day inside `trackingStart..countedThrough` with a summary gets `dayColor()` at one fixed `RECORDED_DAY_ALPHA`; an empty day is transparent. Never scale the shade by hours or reintroduce any normalizer — a ramp against the longest day re-grades the whole history behind one long (or forgotten) session. **Today takes its colour at check-out** and carries only its marker until then; `today` and `countedThrough` are separate parameters because today is drawn as today either way. The cell's `contentDescription` still states the hours for screen readers. **Only days outside the record are faded** (`OUTSIDE_WINDOW_ALPHA`, on the number): the future, days before the first session, and every day when `trackingStartDate` is null. Fading empty past days instead would be the verdict this calendar never renders.
- **Charts are hand-rolled, and the maths is separate from the drawing.** `ui/components/charts/ChartGeometry` is pure Kotlin, unit-tested (`ChartGeometryTest`) for the degenerate cases: empty, all-zero, single point, above the ceiling, zero ceiling. The `Canvas` composables only translate its output; there is no charting dependency. **An all-zero window must read as a row of zeros, not a failed chart** — it is what a lapsed user sees — so `LineChart` insets its plot by a full stroke (a floor-pinned line otherwise loses half its width to the edge) and `BarChart` always draws its `baselineColor` rule, skipping zero-height bars (a zero-height rounded rect renders as a stray lens). Every chart takes a `contentDescription`, since a `Canvas` is invisible to a screen reader; the daily line chart's names only its span (`cd_daily_hours_chart`) — naming a best day would rank. **`DonutChart` bounds centred `content` to the hole's inscribed square** (`ChartGeometry.INSCRIBED_SQUARE`, 0.707): a caption bounded by the diameter overhangs the arc above and below. No caller passes `content` today; keep the bound for the next one. `DonutChartDefaults.size()` grows with `fontScale` (112→148dp cap) so an `sp` caption fits a `dp` ring; past the cap it ellipsizes.
- **Reports derives over one resolved window.** `ReportScope` is `Month` or `AllTime` — two kinds, so each card has one rule per kind — and `ReportScope.resolve(trackingStart, countedThrough)` gives the `ReportWindow` every figure, chart **and the CSV export** read. The screen and `exportCsv` each call `resolve` on the same `scope`, so the file and the screen describe the same days; there is no second clamp to drift. `resolve` clamps both ends and returns **null** for a scope with no counted day, rendered as an empty scope rather than zeros (zeros would assert absences on days the record doesn't cover) — and it is why `window.days` is never zero, so nothing divides by it unguarded. `ReportsViewModel` combines `dailyAggregatesFlow` and `sessionStartsFlow` over **the identical range**, or the start-time split would describe sessions the rest of the screen excluded; the starts query exists because `DailyAggregate.firstCheckIn` gives one start per day. `countedThrough` comes from a one-day aggregate query. The tab opens on the current month and returns to it on a habit switch. Series are gap-filled with real zeros; missed days are the window minus recorded days; the daily chart's dashed line is the window's own mean, not a target. The daily series is capped to `DAILY_WINDOW_DAYS` (30) under all time only; `monthlySeries` is empty under a month scope, so Hours by Month isn't rendered. **No card title may name a span** — the selector states the scope and nothing else may.
- **History is flat: a calendar and the sessions of whichever day you tap. It derives nothing — Reports does.** History answers "what did I do on the 12th"; two tabs computing the same class of figure at two scopes is how they come to disagree, so no summary, average, ratio or ring goes on this tab. The slot below the grid has three states, and the middle one matters: nothing selected, **a selected day holding nothing** (an `EmptyState` titled with that date, so the tap visibly landed — every cell is tappable, future ones included), and the day's rows via the shared `SessionIntervalRow`. The header (`DayHeader`) counts the rows on screen and sums their `duration`s in the composable — a restatement of what is visible cannot drift from it — so an open session adds to the count, not the total.
- **The History calendar is sized from the real viewport.** `HistoryScreen` derives `cellHeight` inside a `BoxWithConstraints` from `maxHeight` (not the physical screen, which counts the app bar and bottom nav) less padding, the month selector, the weekday header and — single-pane only — the day slot, divided by `weekRowsIn` the month and clamped to 48..80dp. `startOffsetIn`/`weekRowsIn` are `internal` in `CalendarGrid.kt` so the screen and the grid share one row count. The 48dp floor wins over fitting (minimum tap target; a 6-row month scrolls slightly), the 80dp cap stops a ~53dp-wide cell becoming a ribbon. On an expanded width the slot is its own pane and costs the grid nothing. `DETAIL_SLOT_HEIGHT` (180dp) is a constant because the grid is sized before the slot is laid out, so **keep it in step with `daySlotItems`** — it is sized to the tallest state, the `EmptyState` placeholder. Under-stating it clips the slot while over-stating only costs grid height, so it and `TEXT_CONTENT_HEIGHT` (font-scale growth) err high.
- **CSV export: one habit, the screen's window, an append-only format.** `DefaultCsvExporter` writes to `cacheDir/exports/`, shares via `FileProvider`, and gap-fills every day of the window with zeros. **Column order is append-only** — people script against it, so a column is never renamed, retyped or moved; `csvHeader()`/`csvRow()` are pure in `platform/CsvFormat.kt` so `CsvFormatTest` pins the bytes the file gets. The last five columns count the day's sessions by `ClosedBy` (`Day Boundary`, `In App`, `Timer Notification`, `Reminder Notification`, `Widget` Check Outs), summing to `Session Count`; a sixth ending is an eleventh column on the end. They record what ended a session, not how the day went, and nothing user-facing may compare them. There is **no Status column**: zero hours and zero sessions already say a day held nothing. The file is the selected habit's alone, with no habit column; `exportFileName` names it `checkin_<habit>_<start>_<end>.csv`. The range is the active scope's `resolve`d window (see the Reports entry), so any past month is exportable and both ends are clamped — unclamped, gap-fill would write future dates and pre-install days as empty recorded days; the end includes today only once it has been checked out of. **No tracking start, a null window, or a window with no completed day returns `ExportResult.Nothing`** (not a `Failure`) and writes no file — a well-formed range of abandoned check-ins would otherwise be pure gap-fill. `ReportsViewModelTest` pins each case.

### First run, presence gate, navigation and habits

- **First run is one linear path: welcome tour, naming step, then the one launch-time ask.** `AppRoot` ranks six full-screen surfaces — `WelcomeScreen`, `NameHabitScreen`, the habit picker (`HabitPickerScreen`, the widget's first stage), the presence gate, the widget page, the nav host — and `FirstRun.step` (pure, `FirstRunTest`) decides which first-run step is owed. The tour is four `HorizontalPager` pages (the quote, attributed to Durant on Aristotle; the thesis — "glance", never "scan", since this is detection not recognition; the home-screen widget; habits) and **names nothing**; its last page leads into the naming step, which names the seed habit and picks its reminder time, so reminders have just been chosen when `POST_NOTIFICATIONS` is requested.
  - **Ordering is structural**: `NotificationPermissionOnFirstOpen` is composed only when `step == ASK_NOTIFICATIONS`, so no branch reorder can put the dialog before the tour. `AppUpdateOffer` asks Play once per activity start, through an `UpdateCheckTurn` that `AppRoot` raises on each start and whatever surface is on screen settles: the offer claims it; the tour, the naming step, either gate, the notification ask and the check-out celebration forfeit it (`ForfeitUpdateCheck`). So Play's dialog never lands on any of them, nor right after one closes — a start spent on a gate is not replayed when the gate hands back to the nav host. It shows once per available version code (`UpdatePrompt`), recorded only once Play's flow actually opened; its Restart snackbar waits while a session is open and, if let go, returns at the next start.
  - **The widget page is how the widget is introduced, and the only place.** It is the tour's third page, with an **Add widget** button (`HomeWidgets.requestPin`, the launcher's own confirmation) or, where `canRequestPin` is false, how to place one by hand. Ending the tour either way writes `widget_page_seen`, so a fresh install meets it there and nowhere else. An install that finished the tour before the page existed meets it once, alone (`WidgetPageScreen`), when `FirstRun.widgetPageOwed` says so: tour seen, page not seen, no widget placed, and `WIDGET_PAGE_AFTER_DAYS` (2) days holding a session of the selected habit (`CheckInRepository.daysWithSession`, never displayed). It is decided at each activity start, never mid-use, because the check-out that brings the second day would otherwise swap it in over the screen in use. It ranks below the gate and never draws under the celebration; either way out marks it seen, and so does a start that finds a widget placed, which ends the question for good. No Settings row, no notification and no snackbar advertise the widget, and nothing does after this page has been shown.
  - **Tour and naming step outrank the gate.** A fresh install cannot meet the gate early (a never-launched app has no alarms), but an install *updated* onto this build owes both while its nudges are live. Gate-first would introduce the app after a check-in, to a habit with no name; the presence request survives the wait because its 10-minute fuse only expires in `MainActivity.onStart`. Nothing preempts the tour, so its pager state is never disposed mid-read and no celebration draws over it.
  - **`!seenWelcome` is tested first**, so an updated install already holding `notifications_asked` still sees the tour once; reading that flag as "an update, skip it" would let any earlier write of it silently disable the tour.
  - **Skip and finish differ.** Only a finished tour releases the dialog (`FirstRun.asksNotificationsAfter`); a skip writes `notifications_asked` without asking. That costs no notifications — `PresenceGate` still asks at the first check-in.
  - **Neither surface has a root `BackHandler`**: back leaves the app and the step is owed again; only ending it writes the flag (the pager has one for the page index). The button label reads `settledPage`, never `currentPage`, which flips mid-scroll and turns a double-tap on page 2 into "Get started".
  - **The naming step is read from the habits table** (`HabitsUiState.needingName`), not prefs, so it covers every fresh install (the seed habit is unnamed) and installs migrated by `MIGRATION_1_2`; `Step.PENDING` draws nothing until the table answers rather than guessing.
- **`POST_NOTIFICATIONS` is asked twice on purpose (from API 33; below it there is nothing to ask, and both askers skip it); the camera only at a check.** `NotificationPermissionOnFirstOpen` asks once, on the first launch reaching the nav host after a finished tour, because nudges default on and the timer notification is the main surface — waiting for a check-in leaves a new user with every notification silently dead. It is tracked by `notifications_asked` rather than the grant, since a refusal and a never-asked look identical through `PackageManager` and Android drops the dialog after two refusals; and it renders only outside the gate, since two stacked system dialogs cannot be answered. Everything else — disclosure, `CAMERA`, `POST_NOTIFICATIONS` again — lives in `PresenceGate`, raised only when a check needs it, so the app is browsable with nothing granted and a revoked camera surfaces at the next check instead of locking the app. Load-bearing details: the gate asks on *entering* the "disclosed but not granted" state (one request per visit), not on the disclosure's button, or a permission revoked between sessions strands the user on a recovery screen that never prompts; a `LifecycleResumeEffect` re-reads the grant because the recovery route is system settings, which returns no result; every gate stop (`GateMessageScreen`) has a **Not now** exit.
- **No image is captured — the camera HAL detects, and the app sees only a count.** `faceDetectingPreview` (in `PresenceHardware.kt`) requests `CaptureRequest.STATISTICS_FACE_DETECT_MODE` via `Camera2Interop`; `PresenceCheckScreen` reads `CaptureResult.STATISTICS_FACES` off each result. Frames never leave the camera pipeline, so there is nothing to delete or strand. The disclosure says only what happens ("The front camera checks you're here…"); the no-image claim lives on the Privacy screen and listing. **No copy may say photo, capture or selfie.**
- **The camera's answer is optional: read both what it advertises and what it runs.** `FaceDetectSupport` (pure, `FaceDetectSupportTest`): `preferredMode` takes `SIMPLE` over `FULL` from `STATISTICS_INFO_AVAILABLE_FACE_DETECT_MODES` (only a count is read; `FULL` doesn't imply `SIMPLE`), null when only `OFF` is offered. `resultIsDetecting` then checks each result, because a HAL can list `SIMPLE` and run `OFF`, reporting empty frames forever. **A non-detecting camera is offered device unlock immediately** — a countdown that cannot be won is worse than none — after `NON_DETECTING_RESULTS` (10) consecutive non-detecting results, since results around session configuration can carry `OFF` on a working camera. A result carrying face rectangles counts as detecting whatever its mode says, and a later detecting result takes the camera back.
  - **No score floor, ever.** `someonePresent` counts every reported face. `Face.getScore` has `SCORE_MIN = 1` and the `SIMPLE` contract requires nothing of it; a MediaTek front camera scores every genuine face **1**, so any floor (50, 20) rejects them all. The rectangle is the honest signal.
  - **Nothing to press: the first frame reporting a face passes.** `snapshotFlow { facePresent && !usingDeviceUnlock }.first { it }`, then `SUCCESS_CONFIRMATION_MS`, then `onAuthSuccess`, in `LaunchedEffect(Unit)` — **never keyed on `facePresent`**, or lowering the phone cancels a check already passed. A confirm button is wrong because reaching it tilts the face out of frame. `presence_looking` shows from the moment the gate opens; `presence_looking_slow` explains the fallback when it appears.
  - **The fallback timer runs from the gate opening, not the first capture result.** `DEVICE_UNLOCK_OFFERED_AFTER_MS` (10s, `DeviceUnlock.kt`) covers a camera that detects but never finds this user. Timing from the first result would start no clock on a camera that binds and then delivers nothing (stalled HAL, camera held elsewhere), leaving only Dismiss. The wait runs off a saved `searchStartedAt` (`elapsedRealtime`) so rotation resumes it, and `cameraUsable == false` also latches `searchTimedOut` so a recovering camera cannot pull the button away. The button is hidden while `usingDeviceUnlock` is set, so no second prompt.
  - **`usingDeviceUnlock` closes the race auto-success opens: the camera streams behind the `BiometricPrompt`**, and a face found mid-prompt would pass under the dialog. It is `rememberSaveable` because the prompt outlives an activity recreation (`MainActivity` declares no `configChanges`) — safe only because `rememberDeviceUnlock` builds the prompt in `remember(activity)`, re-registering a live callback; a tap-time callback would write to a dead composition, leaving the saved `true` uncleared and the camera path shut for good. `authenticate` is in `runCatching` because only an error callback clears the flag. `facePresent` is cleared on `ON_STOP` so a pre-background frame cannot pass later. `cameraUsable`/`facePresent` are `StateFlow`s and the non-detecting run an `AtomicInteger`: capture callbacks are off the main thread.
- **The gate is never a dead end: with no usable device unlock, the fallback is a route to set one up.** Every check-in and check-out runs through it, and a session nobody can check out of runs to the day boundary, writing a full day onto an uneditable row. So when `deviceUnlockStatus` (`canAuthenticate(BIOMETRIC_STRONG or DEVICE_CREDENTIAL)`) is anything short of `BIOMETRIC_SUCCESS`, the fallback button is **Set up screen lock** (`openScreenLockSettings`, `Settings.ACTION_SECURITY_SETTINGS`). Un-gating is not an option. The status is re-read in a `LifecycleResumeEffect` (the settings round trip returns nothing); `ActivityNotFoundException` falls back to the `biometric_unavailable` message. Real state: a real slice of front cameras offer only `OFF`.
- **`androidx.fragment:fragment:1.8.2` is a version floor; deleting it crashes every runtime permission request.** Only `FragmentActivity` is used, re-exported by `biometric`, so it looks like dead weight. But `biometric` 1.1.0 (newest stable) pins fragment 1.2.5, whose `startActivityForResult` rejects request codes above 16 bits while `ActivityResultRegistry` issues them from 65536 up — crashing both the first-open notification ask and the gate's camera request. ML Kit once pulled fragment forward; its removal created the crash. **Deleting a dependency can lower a version another relied on**: diff `./gradlew :app:dependencies --configuration releaseRuntimeClasspath` after any removal and check bytecode (`javap -c`), not version numbers. If tidied, use a `constraints { }` block, which reads as a floor.
- **The nav scaffold owns the title, and `allScreens` is the one registry.** `AppNavScaffold` draws a start-aligned `TopAppBar` (title at the start, switcher at the end) titled from `Screen.titleRes` off the same back-stack subscription as the bottom nav; screens draw no heading and get the inset via `innerPadding`. `Screen` splits into `Tab` and `Detail` (back arrow; `parent` tab stays lit). **Register a destination in `allScreens` (`Screen.kt`), not only in `NavigationGraph.kt`** — the title lookup falls back to `Screen.CheckIn`, so an unregistered route renders as "Check In". `tabs`/`titledScreens` derive from it; `ScreenTest` pins unique routes, titles and `Detail.parent`, but cannot check registration without `kotlin-reflect`.
  - **A route string is frozen once uploaded in a version code.** It is the id a saved back stack restores against (`route.hashCode()`), and `NavController` throws on a restored destination the graph lacks. A rename keeps the old string as a redirect. (`attendance` → `history` shipped in 2.0 as an accepted risk against ~0 installs — not a precedent; whether a Play update preserves saved task state is unverified, so don't settle it from recall.)
  - **A tab tap pops every open `Detail` first**, down to whatever tab is beneath (not always its `parent` — the switcher pushes Habits over Check In); otherwise `saveState`/`restoreState` saves the detail into the tab's stack and the lit tab reopens it.
  - **Settings holds no state**: a Habits link (locked mid-session; `runningHabitName` is passed down for that alone), a Language row (`LanguageRow`: System default, English, العربية, written through `LanguageSettings`), and About.
  - **`HabitSwitcher` sits on every tab and no detail screen.** It is the selected habit's name in `titleLarge` with a swap mark, and **a tap opens the Habits screen, not a menu** — one list for choosing, adding and editing, with Edit and Archive in each row's overflow. Tapping a row selects and pops back *after* the write lands (`HabitsViewModel.select` takes the callback), because the screen-scoped ViewModel dies with the pop.
- **One open session across all habits; switching and managing habits lock to it.** `getActiveSession`/`getActiveSessionFlow` are the only unscoped reads in `CheckInSessionDao`. While a session runs, `HabitRules.effectiveSelection` shows its habit everywhere and `HabitRepository.select` refuses any other — the repository check covers the nudge tap, which selects too. The switcher shows a lock and snackbars `habit_switch_locked`; Settings' Habits row is disabled; a Habits screen open when a session starts (a nudge tap checks in over it) is popped by `NavigationGraph`. `HabitRepository.archive` refuses the running habit (`ArchiveResult.RUNNING`) and the last active one (`LAST_ACTIVE`), and archiving the selected habit moves the selection to the first remaining one. **`selectedHabitFlow` is `distinctUntilChanged` at source and must stay so**: it combines three Room flows that re-emit on every write, and every ViewModel `flatMapLatest`s off it — the dropped-invalidation window `dayTrigger` is deduped for. Queries key on `selectedHabitIdFlow` so a rename rebuilds no query; Reports returns to the current month on a switch.
- **A habit's identity is its uuid; its row id belongs to `_app` alone.** `_app`, `reminder_prefs` and `nudges.db` all travel in a cloud backup and a device transfer, so a restore lands every uuid-keyed setting beside its habit. But `_app` can still be rebuilt alone, with row ids restarting at 1 — the destructive fallback — while the other two survive. So everything outside `_app` keys on `Habit.uuid` — `reminder_minute_<uuid>`, the ledger's `habit_uuid`, the nudge tap's `LaunchExtras.HABIT_UUID`, the stored `channel_id` — and a rebuild can orphan a setting but never hand it to another habit. Notification ids (`NotificationIds.habitNudge`) use the row id, since the tray doesn't survive a restore. **Habits are never deleted, only archived**, which is why `sessions.habit_id` needs no foreign key. The selection lives in `_app`'s `app_state`, reactive and always restored with the record it indexes. A restored install's channels are recreated off the restored habits by `launchHabitSync`'s first emission (their ids are on the rows).

### Sessions, storage and the foreground service

- **Four SharedPreferences namespaces, and none holds a fact about the record.** `session_zone_prefs` (`SessionZones`: one session id and the zone it was checked in under) is **backed up with `_app`**, whose row id it names, and is the one piece of live session state that travels — see the day-boundary entry. `reminder_prefs` (`reminder_minute_<habit uuid>` plus `active_habit_uuids`, behind `notify/nudge/ReminderSettings`) is **backed up with `_app`**, so every restored time lands beside the habit it belongs to; an orphaned one is only counted by `earliestMinute`, the fallback alarm, which reads only the active set the habits collector stores. `prompt_prefs` (`camera_disclosure_seen`, `notifications_asked`, `welcome_seen`, `widget_page_seen`, `update_offered_version_code`; namespace, keys and accessors all in `platform/PromptSettings`) and `checkin_timer_prefs` (the timer's render mirror plus `SessionAlarms`' `remindersSent` and armed instants) are the **only cloud-backup exclusions**: the mirror and instants describe alarms and a service that exist only on the device that set them (a session restored open is repaired by `SessionWatchdog`, see the day-boundary entry), and a cloud restore carries no permission grants, so a restored `notifications_asked` would suppress the launch ask and leave every notification silently dead. A restored install therefore sees the welcome tour again; the naming step reads the habits table and is skipped. Device-to-device transfer keeps everything. `ShippedBackupRulesTest` pins the policy in both rule files. **Everything outside `_app` keys on the habit's uuid**: `_app` can be rebuilt with row ids restarting at 1 (the destructive fallback) while `nudges.db` survives, so a row-id key would credit one habit's send to whichever new habit took its number, while an orphaned uuid key matches nothing. **A new one-time prompt is a new key in `prompt_prefs`, never a new file** — a key inherits the exclusion; a new namespace needs it added to both XML files. **Never reuse `engagement_prefs`, `master_enabled` or `nudge_enabled_<NUDGE_NAME>`**: old installs still hold stale opt-outs under them that nothing reads.
- **Two databases, and the second is scheduler state.** `_app` (v2) holds sessions and habits. `nudges.db` (`NudgeSendDatabase`, v3) holds one thing: which habit's nudge was attempted, when, and whether it reached the tray, read only by `NudgeSendLog.attemptsSince` for the frequency rules. It is a separate database so no change to it can put session records at migration risk, and so `fallbackToDestructiveMigration` is a safe backstop there (a wipe costs at most a duplicate nudge that day), as it never is for `_app`. **A refused post is recorded too** (`posted = false`): it spends the habit's day without moving the gap, and keeps a re-arm from treating a refused band as still open. `MIGRATION_1_3` adds `posted` (default 1), `habit_uuid` (default empty, read as the seed habit's) and an `(habit_uuid, at)` index. The pre-rename file `engagement.db` (`NudgeSendDatabase.RETIRED_DB`) is deleted, not migrated, by `NudgeSendDatabase.deleteRetiredFile`, launched on the application scope from `CheckInApplication.onCreate` (off the main thread). Both are backed up, with `-wal`/`-shm` (Auto Backup shuts the app down first, so the set is consistent); `restoreAnyVersion` stays at its default (false), so a restored `_app` is never newer than the schema the build opens, and an older one runs `MIGRATION_1_2` on first open. A restored ledger can at worst suppress one day's nudge. **Nothing write-only may be added back** — a row with no reader is not a record (see the no-debug-UI entry).
- **The tracking start is derived, not stored.** It is `SELECT MIN(date_key) FROM sessions WHERE habit_id = :habitId` — `CheckInRepository.trackingStartFlow(habitId)`, plus suspend `trackingStart(habitId)` for the CSV: the habit's first session day, null until one exists, reactive. Open sessions count: a first check-in still running is still the day tracking began. A stored copy can disagree with the table — restored without the sessions, it reported **every day since as missed** — and read off the sessions that is unrepresentable. So `HistoryUiState.trackingStartDate` and `ReportsUiState.trackingStartDate` are nullable, and `CalendarGrid` draws null as a month the record does not cover, never as missed days; nothing can be seeded synchronously, so Reports renders nothing while `loading` and `CheckInScreen` holds the gauge's slot empty while `loading` rather than flashing the first-run welcome.
- **Only completed sessions aggregate, and every window ends at `ConsistencyStats.countedThrough`: today once today has been checked out of, otherwise yesterday.** Every aggregate and session-start query filters `stopped_at IS NOT NULL`, so a row for today exists *iff* today holds a completed session, and `summaries.containsKey(todayKey)` **is** the predicate — no extra query, and an open session correctly counts for nothing. History, Reports and the CSV all end there (each asking via a one-day query for today, never reading the whole record), so a check-out lands in counts, totals, splits and calendar immediately. **The conditional is load-bearing**: a window always ending at today would open every morning with a missed day and a dipped count, then take both back at the first check-out — the failure-first reading the daily target was deleted for. It follows that the map holds no key past `countedThrough`, which is why `totalWorkedMs`/`showedUpDays` take no range. `ReportScope.resolve` returns null rather than an empty window, since the record's first day can be uncounted and `window.days` would be 0. At midnight (`TimeSource.currentDay()`) screens roll over live, and a day counted at check-out must read identically after; only History's displayed month stays put.
- **Check-out is one write, and every caller must say what ended it.** `checkOut` delegates to `checkOutAt` with now; `checkOutAt` (the day boundary's entry) stamps a caller-computed instant; `checkOutActiveSession` closes whatever is open. Duration is floored at zero, since a negative (changed clock, corrupt row) would poison every sum. All three **return the closed row**, so callers report the stored figure instead of re-subtracting. **A row is closed once**: `CheckInSessionDao.closeIfOpen` carries `stopped_at IS NULL` in the `UPDATE` itself and `checkOutAt` returns null when it changed nothing, so the late day-boundary alarm and a tap on Check Out landing together cannot restamp each other's close (`CheckInRepositoryTest`). The row keeps its check-in `date_key` even when it ends the next day (asserted in `CheckInRepositoryTest`). **`closedBy` is deliberately un-defaulted**: `ClosedBy` has five values, each with one writer — `IN_APP` (`CheckInViewModel.executeCheckOut`), `TIMER_NOTIFICATION`/`REMINDER_NOTIFICATION`/`WIDGET` (`MainActivity.onRootGatePassed`, read off the `Reason`), each through `SessionActions.checkOut`, `DAY_BOUNDARY` (`SessionLifecycleRunner.onDayBoundaryFired`); a default would let a new path silently claim one. The `storedValue` strings are **frozen**: they are CSV cells and the DAO's `CASE WHEN` sums spell them out literally. It exists chiefly to flag `DAY_BOUNDARY` rows, whose stop instant is a plausible time **nobody chose**. It is **displayed nowhere and never compared in front of the user** (that would grade how someone uses the app) and it records what ended a session, never how the day went.
- **There is no mid-session presence check and no pause.** A check that stopped the clock when unanswered silently deleted worked hours from an uneditable row. Nothing subtracts from a session: `duration` is exactly `stopped_at - started_at`. Only check-in and check-out are gated.
- **An open session keeps two inexact alarms with different jobs.** `SessionLifecycleRunner.arm` schedules both through `SessionAlarms`, and `SessionAlarmReceiver` handles each itself (`goAsync`) rather than waking the service: they exist for when the service is gone, and a background foreground-start would be refused then. Both use `setAndAllowWhileIdle`, which fires through Doze: neither instant needs precision, `SCHEDULE_EXACT_ALARM` is denied by default from Android 14, and Play restricts `USE_EXACT_ALARM` to alarm-clock apps. **Never `setAlarmClock`** — it puts an alarm icon in the status bar and an entry on the lock screen.
  - The **reminder** fires every `SessionSchedule.REMINDER_INTERVAL_MS` (2h), posting "Still checked in?" with a gated Check Out action; ignoring it costs nothing. Only the first of a session alerts (`SessionAlarms.remindersSent`), so an overnight session accumulates silently on the shade. A refused post returns `Outcome.Refused` and re-arms **without advancing the count**, so the first reminder the user can actually see still alerts.
  - The **day boundary** closes the session and is the only thing that ends a forgotten one. **It stamps the session's own midnight, never the fire time** — an inexact alarm can land hours late. It uses the instant that was armed (`SessionAlarms.dayBoundaryAt`), falling back to `SessionSchedule.dayBoundaryOf(date_key)`, clamped between the check-in and now. The fallback is the normal path for a session restored open from a cloud backup (no `checkin_timer_prefs` comes with it): the first app open's `ensureArmed` arms that already-past midnight and the platform delivers it at once, closing the session as `DAY_BOUNDARY`. **The fallback reads the zone the session was checked in under** (`SessionZones`, `session_zone_prefs`, written by `arm` and cleared by every close), because the restoring device's zone is wrong in a way the row cannot reveal: a 23:00 check-in in Tokyo is 07:00 the same date in Los Angeles, and LA's midnight would stamp 17 hours instead of one. Only a session with no recorded zone (opened by a build that kept none) still reads the current zone; restored east, that lands before a late check-in and the lower clamp holds it at the start, while restored west it lands hours late and nothing can tell. **The stored instant comes first on purpose**: recomputing reads the *current* zone, while the armed instant came from the zone the `date_key` names, so a session that crossed a zone change would be stamped hours into the future or hours short — and short silently deletes worked hours. `dayBoundaryOf` goes through the calendar, so a DST day still ends at midnight.
  - **It is the one un-gated check-out**, because a forgotten session is exactly the one nobody is present to authenticate. It can only end a gated session, at an instant the calendar fixes. The cost: a session started at 23:50 closes ten minutes later.
- **An open session can lose its service and its alarms separately, and `SessionWatchdog.reviveIfNeeded` repairs both.** `START_STICKY` is best effort (force stop, OEM kill, crash), leaving the Check-In screen's timer with nothing behind it, and **a force stop or package replace also cancels alarms** (a plain kill does not). So `reviveIfNeeded` first calls `SessionLifecycleRunner.ensureArmed` unconditionally, then revives the service only if `CheckInService.isRunning` is false. `ensureArmed` is safe on every app open: it re-arms the instants stored in `checkin_timer_prefs` (`AlarmManager` cannot be asked what is set), never touches `remindersSent`, re-derives the reminder only if its instant has passed, re-arms the boundary even when past, and drops the alarms when no session is open. It runs from three callers, in order of reliability: `MainActivity.onStart` (a visible Activity may always start a foreground service), `SessionRestoreReceiver` on `BOOT_COMPLETED` and `MY_PACKAGE_REPLACED` (both exempt; it never calls `arm`, whose `cancelAll()` resets `remindersSent`), and the hourly `NudgeWorker` (may be refused). A refusal is absorbed (the next caller is the retry), and `reviveIfNeeded` catches everything, since its callers launch on `applicationScope`, which has no exception handler. **The revive is `ACTION_REVIVE`, never `ACTION_START`**, which takes its timing from the intent and is for a fresh check-in.
- **Whoever writes the row arms it, and whoever closes it cancels.** Both gated writers — `CheckInViewModel` and `MainActivity.onRootGatePassed` — go through `SessionActions`, so the order lives once: `open` writes the row, starts the timer, then `arm`s and retires the nudge; `close` writes and cancels the alarms as one locked step (`SessionLifecycleRunner.close`, so a check-in landing in between cannot lose its fresh alarms), then `stop()`s and celebrates, and does none of that when its write closed nothing (another closer did it). Both run on `applicationScope` with every failure caught — `checkIn` also takes a habit to resolve there, for a screen that has not rendered one yet — so leaving the screen as the gate passes cannot cancel the work between the write and its alarms, and a throw cannot end the process; what a failure leaves half-done, `SessionWatchdog` repairs at the next start. `arm` is never called from the service: `ServiceController.startTimer` can be refused (standby bucket, an OEM declining a `specialUse` start) and neither writer inspects its `Boolean`, so arming in the service would leave a refused start with no day-boundary close. The cancel is the closer's, never left to `ServiceController.stop()`, which is a no-op on a dead service and would strand both alarms over a closed session. **The service's teardown cancels nothing, and `ACTION_STOP` decides nothing**: a stop reconciles against the row like every other command, tearing down only when no session is open, because a late stop (a close racing the next check-in, or the day boundary racing a check-out) would otherwise drop a live session's notification and alarms; an alarm outliving its session drops itself on firing. The day boundary's write can find the row already closed, and then returns `Outcome.AlreadyClosed`, cancelling and stopping nothing. **Every `SessionLifecycleRunner` entry point holds one `Mutex`** across its read of the open session and its alarm writes, because `MainActivity.onStart`'s `ensureArmed` really does run beside a check-in's `arm`; unlocked, a repair that read "nothing open" just before the insert could cancel just after the arm.
- **`CheckInService.isRunning` tracks the notification, not the object.** It is set only after a successful `startForeground` in `enterForeground`, cleared when that guarded call throws, on teardown and in `onDestroy`. Set any earlier, a caught failure leaves an instance with no notification reporting itself healthy, and the watchdog skips it.
- **`serviceScope` needs both its `SupervisorJob` and its empty `CoroutineExceptionHandler`.** The handler absorbs a throw but does not contain it: under a plain `Job()` the first throw cancels the scope for good, and every later reconcile or refresh — including the one that would tear down an orphaned notification — becomes a silent no-op. Without the handler, the throw reaches the thread's default handler and kills the process the service exists to keep alive. **The empty handler is not dead code.**
- **There is no debug UI and no `BuildConfig.DEBUG` branch anywhere in the app.** A diagnostics screen that must be opened on a debug build while a silent failure happens to be live catches nothing, and a row nothing reads is not a record. If a state needs reporting, wire it to something that runs (e.g. a trace attached to `Feedback.draft`). `NudgeDispatcher.runOnce` is the only path that posts a nudge, so what a device shows is whatever eligibility produces — `NudgeDispatcherTest` pins the posted spec's id, channel and registered copy.

### Notifications and nudges

- **The nudge layer is structurally isolated: one pure object decides everything.** `notify/` reads tracking state to build a `NudgeSnapshot` per **active** habit (archived habits are never read, which is the whole of "an archived habit sends no nudges") and never writes to `sessions`. `NudgeEligibility` is the decision surface — `select` (what to send now), `nextEligibleAt` (when it next would), `nextAlarmAt` (what the alarm is armed for) and `nextAlarmAcross` (the minimum over every habit, since they share one alarm) — pure, all reading one `stillSendable` gate; `NudgeEligibilityTest` sweeps a day to pin that `nextEligibleAt` returns now exactly when `select` returns a nudge. Things it deliberately does **not** hold: an enabled/disabled test (consent is the channel's — see the opt-out entry), a tracking-started gate (a "you haven't checked in" nudge exists for the user who has not started), and an app-level quiet-hours window (the channel already gives one). **Nudges default on**: the user who has not formed the habit is the one who never goes looking for a switch. There is no conversion attribution; if effectiveness ever needs measuring, build the reader first.
- **Frequency is bounded two ways, and the band is not one of them.** `spentToday` allows **one nudge per habit per day**, a refused attempt included — the worker re-asks inside the hours-wide band. `NudgeConfig.minGapMs` (**90 minutes**) is **global across habits**, so two habits' reminders cannot arrive back to back; it defers rather than cancels, and the alarm is armed for the instant it clears. **No daily cap across habits**: four habits asked for four reminders. Both rules read one query, `NudgeSendLog.attemptsSince(startOfDay)`, split by habit in Kotlin, so they cannot disagree about where the day began; a refused post is recorded `posted = false`, which spends the habit's day without moving the gap (`lastShownAtMs` counts posted rows only). **`NudgeDispatcher` serialises passes with a `Mutex`**: the checkpoint alarm and the hourly worker both reach `runOnce`, and unserialised both read an empty ledger and both post. Under that lock it calls `HabitChannels.ensure` before posting, because a post to a missing channel is discarded and recorded as a refusal.
- **A check-in retires that habit's nudge, whichever way it was made.** Nothing the app posts is `autoCancel`, so `PostedNudges.retire(habitId)` is called from `SessionActions.open`, which both check-in writers use, and from the nudge tap — for that habit only, since another habit's reminder is still true. `NudgeDispatcher` implements it, since it owns the ids `runOnce` posts under, and it also cancels `NotificationIds.RETIRED_NUDGES`.
- **A nudge tap is still gated, and it is for one habit.** The tap carries `LaunchExtras.HABIT_UUID` plus a `checkin://nudge/<uuid>` data URI — what keeps each habit's `PendingIntent` distinct under the one `NUDGE_TAP_REQUEST_CODE` (30_000); a tap with no uuid (a pre-habits nudge in an updated tray) means the seed habit, and one whose uuid no habit carries does nothing. While the tap is resolved off the database, `PresenceCheckSignal.resolvingTaps` holds the splash screen (cold start) and has `AppRoot` draw nothing, so the nav host never shows the wrong habit before the gate. `MainActivity.onNudgeTapped` reads, retires the nudge, then `TapRouting.forHabit` decides: an archived habit does nothing; this habit's session already open does nothing; **another habit's** session open shows `habit_running_check_out_first` as a **toast** (the tap can land on the tour or naming step, which have no snackbar host) and opens no gate; otherwise it selects the habit and raises `CHECK_IN` with its id. `repository.checkIn(habitId)` backstops both re-checks, returning `AlreadyOpen`/`OtherHabitOpen` rather than inserting a second open row; its read and insert run under one `Mutex`, so two writers resolving together cannot both find nothing open. An unanswered request (Home on any gate screen) would leave a process-global reason set, so `PresenceCheckSignal.raise` stamps it and `MainActivity.onStart` calls `expireIfStale` (`EXPIRY_MS`, 10 minutes). **Expiry is on start, not stop**, because leaving for system settings and back is the gate's legitimate path; without it a nudge abandoned at 09:00 reopens that evening and writes a check-in on the wrong day onto an uneditable row. `PresenceCheckSignalTest` pins it. **A tap is acted on once**: `handlePresenceIntent` consumes its extra, and `onCreate` skips an intent restored with saved state or launched from Recents (`FLAG_ACTIVITY_LAUNCHED_FROM_HISTORY`), since either carries the tap that first launched the task.
- **The home-screen widget is a door to the gate, never a display of the record.** One widget covers every habit: "Check in to …" cycles through the active habits' names (creation order, `flipInterval` the same for each, a fade), a single habit is named outright, an open session reads "Check out of …" with the mark at full colour, and with animations off several habits read a still "Check In". **It shows no figure** — no today state, count, hours or timer — because a per-habit mark side by side ranks habits, and a number on the home screen all day reads as a score; `WidgetFace` (pure, `WidgetFaceTest`) is the whole of what it can show.
  - **It decides nothing.** Its tap is one constant, explicit intent (`LaunchExtras.WIDGET_TAP`, request code `WidgetViews.TAP_REQUEST_CODE` 40_000, never a deep link, which anything on the device could fire), and `MainActivity.onWidgetTapped` routes it with `TapRouting.forWidget` against the rows at the tap: an open session → `CHECK_OUT_FROM_WIDGET` (recorded `ClosedBy.WIDGET`); one active habit → the gate; more → `PresenceCheckSignal.choose`, the picker. A stale face therefore cannot cause a wrong write, which is why nothing has to keep it perfectly current.
  - **The picker is the first stage of the same request**: `Request(CHECK_IN, habitId = null)`, `choosingHabit`. An abandoned picker expires as a gate does, `EXPIRY_MS` from the tap; a pick is a fresh answer from someone present, so it re-raises with the habit and restamps, and the gate gets its own `EXPIRY_MS` (so picker plus gate can stay live up to twice that); a passed gate with no habit writes nothing; a pick goes through `TapRouting.forHabit` — the nudge rule — so picking a habit and tapping its nudge cannot diverge. `HabitPickerScreen` is the Habits list with everything but choosing removed (no times, add, edit or archive); both draw rows through `HabitNameRow`, and back or **Not now** lands in the app with nothing written.
  - **Drawn off the tables, never by a writer.** `WidgetSync` maps the active habits, the open session and the animation setting (observed through `HomeWidgets.animationsOn`) through `WidgetFace.faces` — the one description of the face — for both of its paths: `start` (from `CheckInApplication.onCreate`, so a broadcast-born process — the day boundary, a boot — reconciles it, and from the provider's `onUpdate`) collects it while a widget is placed, and `redraw` draws once from a fresh read for `onUpdate` and a language change. **Every draw runs under one lock and skips a face identical to the last drawn**: Room re-emits on every write and each `updateAppWidget` restarts the flipper, and a redraw's read sits inside the lock so a face read before a check-out cannot land after the collector drew it. `onUpdate` and the language change go through `redraw`, which skips no face, since the system may hold no views yet and new words keep the same face. With no widget placed the collector ends at once (most installs never place one), `redraw` does nothing, and nothing is recorded as drawn; `onDisabled` stops it. A failed read re-subscribes after `RETRY_DELAY_MS` rather than ending the sync, and nothing in it throws, since the application scope has no handler. `WidgetSyncTest` pins the dedupe, the redraw, the retry and the not-placed case. **The animation setting is followed only while the process lives**: Android broadcasts no change to it, so one made while the process is dead shows at the next process start — opening the app, any alarm, a boot, at worst the hourly `NudgeWorker` — and a stale face costs nothing, since the tap is routed from the rows. A periodic `updatePeriodMillis` would close the gap by waking the device every 30 minutes for a cosmetic state; don't add one.
  - **No Glance, and no dependency at all**: a `ViewFlipper` is a supported `RemoteViews` class and Glance has none, so the widget is plain `RemoteViews`, keeping the licence list and the merged manifest untouched. Its colours are XML the launcher resolves in its own theme (`widget_*` in `values`/`values-night`, two mark `ImageView`s rather than one re-tinted from code), and its text is the system sans-serif, on up to two lines so a long verb (Arabic's) wraps the habit's name rather than ellipsizing it; it resizes upwards as well as sideways, so the second line has room at a large font scale. Its layout direction is the app's, set in `WidgetViews.build`: the launcher lays the views out in its own configuration, which a per-app language is not part of.
- **A nudge is delivered by an alarm; the hourly worker is only the backstop. Never put the trigger back on the worker.** A periodic job's interval is a request: an app the user is not opening falls through the standby buckets and its job settles at a consistent hour, often overnight, so a time-of-day rule asked from the worker can be false every day — hardest for the user the nudge exists for. `NudgeAlarms` keeps **one** inexact `setAndAllowWhileIdle` alarm for all habits; `NudgeDispatcher.runOnce` re-arms it from a fresh ledger read in a `finally`, so a throwing pass still schedules the next one and `NudgeAlarmReceiver` needs no arm of its own. The receiver and `NudgeWorker` both call `NudgeCoordinator.runPass` (built in `AppContainer` as `nudges`, unit-tested in `NudgeCoordinatorTest`), which never throws and arms `armFallback` (the next band of `ReminderSettings.earliestMinute`, readable without a database) when the dispatcher cannot be built or read. **Nothing runs and nothing is armed while a post would be refused for a permission never asked** (the coordinator's `firstRunPending`: `notifications_asked` unwritten and `POST_NOTIFICATIONS` not held), since the recorded refusal spends the habit's day under the tour. Below API 33 it never holds, so an Android 12 first run left unfinished still gets its nudges. Both ends of first run (the ask, and a skipped tour) call `launchRearm`, which starts the chain. The worker also waits one interval before its first pass (`setInitialDelay`); `KEEP` leaves an existing schedule alone; and it returns `Result.success()` on failure, since `failure()` is terminal for periodic work.
- **`NudgeAlarms` is stateless; `SessionAlarms` is not.** Session instants derive from a session and are persisted; the next nudge instant is derivable from now, the habits, their times and the day's sends, so nothing is stored. **`NudgeAlarms.arm` only sets an instant; the dispatcher decides it**, and every arming site goes through it via `NudgeCoordinator`: `runPass` (receiver, worker) and `rearmNow` — from `launchHabitSync`, the habits-table collector, whose **first emission is process start** (re-arming after boot, package replace or force stop, which cancel alarms) and later ones each habit change; and from every time chooser through `chooseReminderTime`, which takes `launchRearm` so none launches it differently. A new habit is re-armed explicitly after its time is stored, since the insert's own emission may have read the prefs first. **Never arm a plain "next band" while the ledger can be read**: an open-but-unsent band (after an update, reboot or new time) belongs inside today's band, and a gap-held habit belongs at the instant the gap clears. **A nudge already due is never armed for now**: `nextAlarmAt` puts it off by `NudgeConfig.dueNowDelayMs` (30 minutes), because these arms usually follow the user opening the app to check in, and a pass that always throws would otherwise re-arm itself every few seconds. `rearm` and `runOnce` share the `Mutex` across the time read, the decision and the arm, so a newly stored time cannot be overtaken by a pass that read the old one.
- **One band per habit, from its chosen minute to midnight.** Each habit's reminder is a minute of the day picked on a clock (`ReminderTimePicker`) in the naming step or the Habits screen's editor, stored as `reminder_minute_<uuid>` in `reminder_prefs`, default `NudgeSchedule.DEFAULT_MINUTE` (10:00); no app-wide time, no follow-up. It is limited to `NudgeSchedule.minuteRange` (05:00–21:00; the picker disables Set outside it rather than clamping a visible choice), which keeps every band at least three hours before midnight — room for an alarm slipping an hour plus a 90-minute gap deferral — and `NudgeConfigTest` pins it against `NudgeConfig.DEFAULT_MIN_GAP_MS`. Clamping (`NudgeSchedule.clampMinute`) happens only in `ReminderSettings.kt`, on read and write; the schedule maths take the minute as valid. **The minute is kept, not rounded**: per AOSP's `AlarmManagerService.maxTriggerTime` a one-off inexact alarm lands within an hour after its trigger, never early, and standby quotas do not bind one alarm a day. Copy says "around" the time; no notification names it. `reminder_hour_<uuid>` (whole hours, never released) must not be reused. `NudgeSchedule` is the one source of these hours for alarm and rule alike, or the alarm fires when the rule declines. **Do not unify it with `SessionRhythm`'s `StartBucket`**: one describes when a session began, the other decides when to send. The one nudge, `Nudge.NOT_CHECKED_IN`, posts under `Nudge.notificationIdFor(habitId)` → `NotificationIds.habitNudge`, a block of four ids per habit from 100_000; v3.0's ids 10/11/12 are `RETIRED_NUDGES` (never reused, still cancelled), and v3.0's ledger keys `NOT_CHECKED_IN_MORNING`/`_AFTERNOON`/`_EVENING` map to it through `Nudge.fromStoredKey`, an empty `habit_uuid` to the seed habit.
- **Presence is "today has a row", never "a session is open".** `NudgeSnapshot.hasCheckedInToday` is the only presence question, built per habit from `getSessionsByDate(habitId, today)`, not `getActiveSession()` — so checking in to one habit does not quieten another's reminder. A session open past its own day's midnight is one whose day-boundary alarm was lost; suppressing on "a row is open" would silence every nudge for as long as it stayed open, including the one that would bring the user back. `getSessionsByDate` does not filter `stopped_at`, so a session open today already counts — no second presence concept is needed.
- **Persisted names outlive the code that wrote them, so a rename is a retirement, and these are frozen.** An armed alarm's `PendingIntent` names the receiver's fully qualified class, so moving `NudgeAlarmReceiver` or `SessionAlarmReceiver` drops alarms armed by the previous install; that is survivable only because every arming site is idempotent and runs unprompted (process start, `SessionRestoreReceiver` on `MY_PACKAGE_REPLACED`), costing at most one checkpoint. A WorkManager unique name is its key, so `NudgeWorker.WORK_NAME` is `nudge_pass`, and the old `engagement_nudge_pass` (`RETIRED_WORK_NAME`) is cancelled in `schedule()` **before** the enqueue, or `KEEP` leaves the orphan running beside it. `NotificationChannels.NUDGE` is `nudge_channel` (the seed habit's channel), with `engagement_channel` and `engagement_channel_v2` in `RETIRED_NUDGE_CHANNELS`, deleted in `ensureAll`. Deletion **tombstones** a channel, so a reused id inherits old settings. Those renames were free only at ~0 installs; that exemption is spent. Treat every id, work name and receiver path as frozen, and append to the retired lists rather than replacing them. A placed home-screen widget names `CheckInWidgetProvider`'s path the same way, with no re-arm to recover it: moving the class takes the widget off every home screen it is on.
- **A refused post is a real, silent outcome, and every caller handles it.** `NotificationManager.notify` drops a post and returns normally in four cases beyond a missing channel: `POST_NOTIFICATIONS` revoked, notifications off app-wide, the channel set to none, or its group blocked (which leaves each channel reporting its own importance unchanged). `NotificationDelivery.canDeliver` decides it, pure so `NotificationDeliveryTest` can pin it; a missing channel also counts as undeliverable. `Notifier.show` returns false, and then `SessionLifecycleRunner` re-arms the reminder **without advancing `remindersSent`**, so the first reminder the user can actually see still alerts, and `NudgeDispatcher` records the attempt `posted = false`. Nothing surfaces the blocked state; if it ever must, do it where the user is (the Check-In screen knows a session is running), not as a Settings card.
- **A notification's opt-out is its channel and nowhere else — the rule for every notification the app adds.** No screen holds a notification switch; the Habits screen's per-habit time is timing, never consent, and a long-press on any notification opens its channel. **Each habit has its own channel** (`HabitChannels`): in the `NotificationChannels.HABIT_GROUP` group, named from `habit_channel_name` ("<habit> Reminders", or `nudge_channel_name` "Check-In Reminders" while unnamed) and renamed with the habit, its id stored on the habit row (`nudge_channel` for the seed, `Habit.CHANNEL_PREFIX` + uuid otherwise) and frozen. `AppContainer.launchHabitSync` reconciles channels off the habits table — create or rename an active one, delete an archived one — so no write path can forget. Per AOSP's `PreferencesHelper`, re-creating a channel keeps its user settings, and re-creating a deleted one undeletes it, settings included, for 30 days. An app pref is subordinate to the channel (`canDeliver` already refuses a blocked one), so it can only agree or lie; and an in-app opt-out is a one-way door — Android has no API to block or lower a channel, so a stored opt-out can never be migrated into the system, and deleting the toggle later re-enables the notification for everyone who used it. So a new notification, or a nudge wanting independent control, gets a **new channel**, never a pref; `NudgeEligibility` decides timing, never consent. Names and descriptions are updatable; ids and importance are frozen. "Check-In Reminders" sits beside "Session Reminders", so the descriptions carry the difference — muting the wrong one costs the prompt that catches a forgotten open session.
- **Check-out from a notification is gated.** The timer's and the session reminder's Check Out actions open `MainActivity` with `LaunchExtras.CHECK_OUT_FROM_TIMER` / `CHECK_OUT_FROM_REMINDER`, run the root presence gate and check out on success. `ServiceController.stop()` (`ACTION_STOP`) only ends the service after a check-out has been written, and only if the row says nothing is open; it is never the action itself.
- **One description of a notification, one place that builds it, one place that posts it.** The timer, the session reminder and every nudge are a `NotificationSpec`, built by `NotificationFactory`; `Notifier.show` adds the delivery guard and posts. Building and posting are separate because `startForeground` needs the `Notification` in hand and must succeed without the permission — so **every** timer post, refreshes included, goes `factory.build` → `startForeground` (which updates in place and is exempt), never `notifier.show`, which would drop the refresh once the permission is revoked. Ids live in `NotificationIds`, including nudges' per-habit blocks — never ordinal-derived, never reused, since a shared id replaces rather than adds. **`PendingIntent` request codes are a namespace shared with previously installed versions**, and equality ignores extras, so a collision under `FLAG_UPDATE_CURRENT` rewrites a still-posted notification's target. The bands (1_000+ content, 10_000+ actions, 20_000/20_001 session alarms, 20_010 nudge checkpoint, 30_000 nudge tap, 40_000 widget tap) are frozen and tabled in `NotificationIds`' KDoc. A new sender claims a fresh band and adds a row there.
- **Nothing is `autoCancel`; whoever handles a tap cancels.** `NotificationFactory` always sets `setAutoCancel(false)`, so each notification's removal lives in one place: `PostedNudges.retire` for a nudge; for the session reminder, the service's teardown at check-out and `SessionLifecycleRunner` at the day boundary, and otherwise it is replaced in place under the same id. No delete intent is set, so a swipe is simply unrecorded.
- **The timer channel is `IMPORTANCE_DEFAULT`, which buys placement rather than noise.** Below `DEFAULT` the shade files it under the collapsed *Silent notifications*, and its deliberately stale `when` (pinned to `started_at` for the chronometer) sinks it further as the session runs, so a user misses that a session is open and the day boundary records hours nobody worked. It stays silent: `setSound(null, null)` on the channel, `setSilent(true)` on the spec, and heads-up needs `IMPORTANCE_HIGH`. **Importance is frozen at creation, quietly**: a changed value is ignored on any install that already has the channel, so a device that ran an earlier build keeps the old importance until uninstall — check that first when a change looks inert. Revising it means a new id, resetting every per-channel choice — which now costs real users; a new id for a *new* channel (every habit after the seed) costs nothing.
- **The timer notification survives Clear all but not a deliberate swipe, and nothing re-posts it.** From Android 14 a foreground-service notification is swipeable even with `setOngoing(true)`, though Clear all leaves it alone; on Android 13 `ongoing` still makes it undismissible, so that install only has more coverage. A dismissal is a deliberate swipe beside a Check Out action, and re-posting would override it. Coverage without it: the session reminder's first fire (audible, `silent = count > 1`, and still audible after a refusal since refusals do not advance the count), then silent reminders, then the day boundary. If this proves too quiet, the lever is that predicate in `SessionLifecycleRunner.onReminderFired`, **not** a shorter interval.
- **Notification icons are the brand mark, not platform stock.** `ic_stat_checkin` (a 24dp silhouette from the brand geometry) is the small icon for the timer, the reminder and every nudge; `ic_stat_check_out` matches `Icons.AutoMirrored.Filled.Logout`, which the Check-In button uses for the same action. Status-bar icons keep only their alpha channel, so they stay white-on-transparent.

### Check-In screen, brand, languages and distribution

- **The Check-In gauge is the current session, never the day's total, which is why it needs no label.** It reads zero between sessions and counts up from check-in; one resuming from the day's total reads as a *paused* stopwatch, implying a pause mechanic the app does not have. The day is stated once, by `TodaySessions`' pill (`n sessions · Xh Ym today`, open interval included live), which sits **outside** the `AnimatedVisibility` so it always shows. The pill's **touch height is floored at 48.dp on the `Surface` while its padding is tighter** — a smaller look must never mean a smaller target.
- **One 1-second ticker, on screen only; the service has none.** A composition-scoped `LaunchedEffect` in `CheckInScreen` ticks the readout. The timer notification uses `setUsesChronometer(true)` + `setWhen(started_at)` (`NotificationFactory`), so the platform draws the clock from one post and keeps counting through deep sleep. Both count the open session from the row's `started_at` (passed as `CheckInService.EXTRA_START_TIME`), so they agree. **Do not reintroduce a service-side ticker**: per-second `startForeground` calls are what OEM background management kills apps for, and a coroutine `delay` freezes in deep sleep anyway. The body copy is `notification_running`, never a formatted duration — a printed one would duplicate the chronometer, frozen.
- **The gauge is the brand lattice breathing, and it says one thing: whether a session is open.** `BrandGridGauge` runs a wave of brightness over the seven cells (`WAVE_MS` 3s a pass, `waveLevel`, pure); with no session the grid sits still at track alpha. **No cell's place in the pass may mean anything**: a single cell advanced on a schedule encodes progress through it, and a lattice filling cell by cell is a completion bar — the deleted daily target as geometry. Every cell traces the identical curve a beat apart, since cells differing in height or dwell would rank them; `BrandGridTest` pins that, the wrap, and that no two peak together. `CREST_POWER` (2.0) narrows the crest to about two cells so the pass has a front and a tail; don't speed the pass and narrow the crest together (too insistent), and past ~5s a pass stops reading as one wave. With animations off, running is every cell at full colour — still distinct from rest.
- **The Check-In screen is a fixed, non-scrolling layout with a hand-kept fit budget — keep it that way.** Gauge and button must share one viewport and one thumb reach, so it is a weighted `Column` with the sessions collapsed behind the pill. It *clips* rather than scrolls, so `BoxWithConstraints` falls back to a scrolling branch below `COMPACT_HEIGHT_THRESHOLD` (560.dp) or when an expanded list would get less than `SESSION_LIST_MIN`. **A `Column` measures non-weighted children in declaration order**, so an unbounded list above the button would take its space and coerce it to zero height; the list is capped at what is left after the chrome, the mark, `FIXED_CONTENT_HEIGHT` (date row, pill, the 64.dp `ACTION_HEIGHT`, readout and gap) and `TEXT_CONTENT_HEIGHT` scaled by font scale. **The readout sits below the mark rather than in it**, which is why the gauge is two budget terms: the mark's side (`COMPACT_MARK`/`MARK_MIN`/`MARK_MAX` in `TimerGauge.kt`) is fixed while the readout grows with font scale. The readout is `maxLines = 1` and steps down from `displayMedium` to `headlineMedium` on a short viewport or past `READOUT_SHRINK_SCALE`, because a wrapped clock is a wrong number. Anything added, or a change to the pill's height, must move these figures. The expanded list has two renderings because the scrolling branch cannot host a `LazyColumn` (unbounded height crashes it).
- **The expanded session list is a two-column ledger, and nothing in it ticks.** `SessionIntervalRow` (`ui/components/SessionIntervalRow.kt`, shared with History's selected day so a session renders identically on both tabs) is the clock range, weighted, beside the duration in a fixed column so amounts stack. That column **scales with `fontScale` and caps** (`DURATION_COLUMN` 56.dp to `DURATION_COLUMN_MAX` 88.dp): it is `dp` holding `maxLines = 1` `sp` text, so a fixed width renders "2h 15m" as "2h" — a wrong number; past the cap the range ellipsizes instead. **No third column**: a time-of-day word restates the start time, an ordinal restates the row order and count, and a length label grades the session. The open row shows `ongoing` and the drawn `OngoingPulse` (still when animations are off) instead of a duration — a second live number would compete with the gauge. History's header sums only printed durations, so **on today it differs from the Check-In pill by the open interval's elapsed time**.
- **The check-out celebration is raised by both writers, never by the day boundary, and it never grades.** `CheckInViewModel.executeCheckOut` and `MainActivity.onRootGatePassed` both reach `raiseCheckOutCelebration` through `SessionActions.close` (wired in `AppContainer`, so `service/` imports nothing from `ui/`), so `CheckOutSignal` is process-global — ViewModel state would miss the notification path. The figures are read for the **closed session's own `date_key` and habit**, so one closed after midnight reports the day it belongs to. The day-boundary close reaches neither, correctly: praising the check-out the user forgot is the wrong message. `CheckOutCelebration` draws **over** the nav host, so the tab survives, and **nothing retires it on a timer** — only a tap or back. So one left behind by Home cannot greet a later launch, `raise` stamps and `MainActivity.onStart` calls `expireIfStale` — `CheckOutSignal.EXPIRY_MS` is **2 minutes against the gate's 10**, since this reacts to a moment while the gate waits on a legitimate trip through system settings. Its one motion is `BrandGrid(settle = true)`: the seven cells land in reading order over ~680ms, the last (the record's newest entry) with an `EaseOutBack` overshoot, driven by one `Animatable` cursor over the pure `cellProgress` (`BrandGridTest`); it plays once and honours `animationsEnabled`. **Copy, icon and motion are identical at twenty minutes and at nine hours** — anything that warms with the duration is the daily target returning as a congratulation threshold.
- **The Check-In screen colours the action, never the outcome.** The button is a start/stop control: `startActionColors()` (green, the same hue as a recorded calendar day) to check in, `stopActionColors()` (red) to check out, animated across the switch so it reads as one control changing state. Both live in `ui/theme/Color.kt`; every pair clears WCAG AA. The red is the stop half of start/stop, **not** `colorScheme.error` and not a verdict — no day is ever drawn in it.
- **The mark has one geometry, drawn by two sources that must change together.** `play-store-assets/generate_icons.py` owns it — emitting the `pathData` for `ic_launcher_foreground.xml` and `ic_stat_checkin.xml` plus the 512px Play icon, and asserting the 66dp safe circle in `verify()` — while `ui/components/BrandGrid` restates its constants (3 cells a side, `FILL_FRAC` 0.88, `CORNER_FRAC` 0.22, `EMPTY_CELLS`) because a flattened `pathData` cannot be addressed cell by cell. Nothing gates the two agreeing; `verifyDocMap` checks names, not values. Within the drawables there is **one** mark: the adaptive icon's foreground and `<monochrome>` layers and, via `drawable/ic_splash_icon.xml`, `windowSplashScreenAnimatedIcon` all point at `drawable/ic_launcher_foreground.xml`. `ic_splash_icon` is an `<inset>` at **-8%** (expanding ×1.16, as a fraction of whatever bounds the platform gives), because the foreground is sized for a 72dp launcher window and the splash has a 192dp circle to fill — fix splash size there, never by scaling the mark, which moves the launcher and notification icons too. No density `mipmap-*` rasters and no `-v26` qualifier: at minSdk 31 `mipmap-anydpi` always wins (themed icons render from 33 only).
- **Two languages, English (UK) and Modern Standard Arabic, and every number is Latin.** `values/` is en-GB (`res/resources.properties`, read by `generateLocaleConfig`) and `values-ar/` is Arabic, so Android's per-app language screen offers both. Settings' *App language* row (`ui/settings/LanguagePicker.kt`; **absent below API 33**, which has no per-app locale, so Android 12 follows the system language and nothing is stored) offers the same choice as three entries — System default, English, العربية, each language named in itself — instead of the system screen's list of every suggested region; it writes the platform's per-app locale through `platform/LanguageSettings`, so the two screens always agree and the app stores no choice of its own. **`AppLanguage` stores the bare language** (`en`, `ar`), and every tap writes, the shown choice included, so re-choosing replaces a regioned or unshipped locale stored some other way (shown by its own name, no option selected). The region and week start still come from the system: Android lists the system locales after the stored one (AOSP `PackageConfigPersister.updateConfigIfNeeded`, from API 33), and `displayLocale` passes over a region-less preference, taking the region and Unicode extensions (`-u-fw-`) from the first that has one — a stored copy of either would freeze them. `AppLanguageTest`/`DisplayLocaleTest` pin both halves. **A new string needs its `values-ar` twin in the same commit**: lint's `MissingTranslation`/`MissingQuantity` are errors and `lintDebug` runs in CI. Arabic plurals carry all six quantities. Arabic copy follows the English rules (no grading, no target, no streak; عادة never هدف). `app_name` is `translatable="false"`.
  - **Digits are Latin everywhere** (`util/LatinDigits`, the `nu-latn` extension): `java.time` and templates print ASCII while `String.format` and resource `%d` follow the locale, so Arabic screens would mix scripts. `MainActivity.attachBaseContext` applies `latinDigitsOverride` as an override configuration for every resource the activity formats, and `StringResolver.format` covers notifications. Any `String.format` on a user-facing figure must take `Locale.getDefault().withLatinDigits()` — bare `Locale.getDefault()` is the bug.
  - **Unit letters and date field order are resources** (`time_*`, `date_*_pattern`), built into `TimePatterns` at the theme root and read through `LocalTimePatterns`. US-region devices therefore read "25 Jul 2026"; a `values-en-rUS` overriding only the patterns is the fix if unwanted, at the cost of a third language entry. Punctuation assembled in code (`session_range`, `list_separator`) is a resource too.
  - **The display language is the one Android resolved, never `locales[0]`.** A device preferring `[de, ar]` gets `values-ar`; each `strings.xml` carries `language_code`, and `displayLocale` picks the first preference in that language that names a region (keeping it, which sets the week start), or with none, that language in the first regioned preference's region and extensions — a `[de-DE]` device reads English with a Monday week. The patterns, `typographyFor` (Plex Arabic under `ar`) and `CalendarGrid` all read that one locale. `TimeFormatTest` reads the shipped patterns (`ShippedPatterns`), so a broken one fails a test.
  - **Notification text is rewritten on a language change**: it recreates the activity, not the process, and channel names are stored by the system, so `CheckInApplication.onConfigurationChanged` re-runs `NotificationChannels.ensureAll` and `AppContainer.launchLanguageRefresh` (every habit's channel, and a re-post of a running timer).
  - **The CSV ignores all of it**: machine-read, so its clocks use `CsvFormat`'s own `Locale.US` formatter, its header is English and `date_key` ISO; `CsvFormatTest` pins the bytes under an Arabic default. Only the file *name* follows the habit's name, and `exportFileName` keeps `\p{M}` so Arabic harakat do not split it.
  - **Charts mirror under RTL** via `graphicsLayer { scaleX = mirror }` in `LineChart`/`BarChart`, since a `Canvas` does not mirror but the axis-label `Row`s do; `ChartGeometry` is untouched. `BrandGrid` does not mirror — it is the logo.
  - **Stays English on purpose**: library names, copyrights and licence names on the Licenses screen (only each entry's `note` is a resource), `Feedback.draft`'s subject and body, and the Play listing (an Arabic listing is separate work in `play-store-assets/LISTING.md`).
- **The app makes no network calls and the merged manifest holds no `INTERNET` permission — protect that claim.** The manifest declares six permissions, none for networking or exact alarms. The merged release manifest adds four: `ACCESS_NETWORK_STATE` and `WAKE_LOCK` (`androidx.work`), `USE_FINGERPRINT` (`androidx.biometric`, dead at minSdk 31 but declared unconditionally) and the app-scoped `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` from `androidx.core`. Verify by grepping `app/build/outputs/logs/manifest-merger-release-report.txt` for `uses-permission` (not `strings` on the merged manifest, which also matches components' `android:permission`). A dependency bringing `INTERNET` back (as ML Kit's `transport-backend-cct` did) falsifies the listing and privacy policy. **Play In-App Updates is the one proprietary dependency, admitted only because it adds none**: `app-update` 2.1.0, `core-common`, and gms `play-services-basement`/`-tasks` declare no permission, bind to the Play Store app over IPC (`BIND_UPDATE_SERVICE`), and merge in only the non-exported `PlayCoreDialogWrapperActivity` and the `com.google.android.gms.version` meta-data; the minified dex references no `java.net`/`javax.net`/OkHttp/Cronet/datatransport class. Re-verify all three (merger report, `aapt2 dump xmltree`, a dex grep) on any bump of it, and never take its `-ktx` artifact, which drags in old fragment and coroutines floors. Play's docs say the check sends Google device metadata, app version and installed modules, so the Privacy screen and listing say the app's only outside question is whether Play has a newer version, never that no third-party code collects anything. **That claim also needs emoji2's startup initializer removed** (`tools:node="remove"` in the manifest): Compose depends on `androidx.emoji2`, and its `EmojiCompatInitializer` otherwise asks Play services' font provider (`androidx.content.action.LOAD_EMOJI_FONT`) for an emoji font 500ms after every launch. Without it Compose sees `EmojiCompat.isConfigured()` false and draws emoji with the system font, so an emoji newer than the device's font is a blank box in a habit name. Don't swap in `emoji2-bundled` instead (9.7 MB). Any new library's startup initializer, provider or service is the same kind of risk: read the merged manifest's `InitializationProvider` and components after every dependency change. Outbound links all go through `ui/about/ExternalLinks` as implicit intents: browser for the privacy policy, `ACTION_SENDTO` + `mailto:` for feedback (mail apps only, unlike `ACTION_SEND`), Play for rating. Each returns `false` rather than throwing (catching `ActivityNotFoundException` and `SecurityException`) so callers fall back to the clipboard. Feedback is an email the user reads before sending, not a POST, because any network call means a new Data Safety declaration.
- **The open-source licence list is hand-maintained, grouped, and checked against the classpath in both directions.** `ui/about/OpenSourceLibraries` lists the upstream projects behind the release runtime classpath (`:app:dependencies --configuration releaseRuntimeClasspath`, grouped by group id) — not the dependency block, since `org.jetbrains:annotations`, `org.jspecify`, Guava's `listenablefuture` and AutoValue's annotations ship without being declared. Grouping is sound only where the licence is uniform within a group — hence CameraX's separate BSD (embedded libyuv) beside Apache-2.0. Every entry is Apache-2.0, OFL or that BSD, except the in-app update stack (Play Core terms and the Android SDK License, both linked rather than bundled); the screen is titled **Licences** for that reason. `OpenSourceLibrariesTest` pins the list's shape, fails if ML Kit / odml / datatransport / Firebase reappear, and pins the proprietary entries to exactly `com.google.android.play:*` and gms basement plus tasks — `verifyLicenseCoverage` matches by group, so a third gms artifact would pass it under that entry. `:app:verifyLicenseCoverage` (CI, and a dependency of `check`) resolves the classpath and fails on a group id no `coordinates` covers **and** on an entry covering nothing shipped. It also matches `res/font/` (font extensions only, so a stray `.DS_Store` cannot fail it) against `font:` coordinates such as `font:outfit_*`, since a typeface is redistributed with no Maven coordinate. It fails on an empty parse rather than passing, declares an output stamp so it can be UP-TO-DATE, and detects drift rather than generating the list, which would lose the grouping and notes. Licences that oblige a shipped copy are flagged `LibraryLicense.bundled` and their text ships in `res/raw` (`apache_2_0.txt`, `ofl_1_1.txt`) for offline reading; `LicensesScreen` loops over that flag (the raw-resource mapping stays in the screen, keeping the enum plain Kotlin) and renders each paragraph as its own `LazyColumn` item, since one 11 KB `Text` measures in a single frame.

## Conventions

- Kotlin official style; Composables PascalCase. `./gradlew ktlintFormat` is the arbiter — don't hand-format against it.
- **Time arithmetic uses named unit constants, never inline `60 * 60 * 1000`.** `util/TimeUnits` holds the millisecond ladder every duration constant is built from, and `util/TimeFormat` adds the second-to-hour steps it formats with; files that convert a duration to a fractional number (`platform/CsvFormat`, `ReportsScreen`) carry their own `MILLIS_PER_HOUR`, since they divide by it. Detekt's `MagicNumber` enforces it outside Composables, where dp/sp/alpha literals are exempt.
- **`ui/components/` holds what a second screen would otherwise copy wrongly** (`ActionRow`'s 48dp target, `SessionIntervalRow`'s column order, `FullScreenMessage`'s spacing) or a rule that must live in one place to hold (`AnimationsEnabled`). A single calling screen is normal there (`ChartCard` is Reports-only). Layout private to one screen stays in that screen. `SessionIntervalRow` is `internal` because it takes a Room entity.
- **One `uiState: StateFlow<XUiState>` per screen**, collected with `collectAsStateWithLifecycle`; VMs come from `AppContainer` via a `viewModelFactory`. Each screen adds `LifecycleResumeEffect { onResumed() }`, which feeds `TimeSource.dayTrigger`. **`dayTrigger` must stay deduped**: every VM `flatMapLatest`s its whole Room graph off it, so an emission per resume reopens every subscription — and on return from the device-credential prompt that lands mid-check-in, Room's invalidation reaches the detached observers, and the Check-In screen shows a green Check In button and `0m 0s` over an open session. `maxOf(day, today())` is the other half: `currentDay()` sleeps on a `delay` that stalls in deep sleep, so the tick must read `today()` rather than re-emit a stale value. `DayTriggerTest` pins both. Nothing inside those graphs is read non-reactively, so deduping costs nothing.
- All DAO/repository DB operations are `suspend` or return `Flow`; Room via **KSP**.
- **The day hue is `ui/theme/dayColor()`** (light/dark tuned) — never hardcoded, never a second colour for a worse day, and no fraction overload: an alpha derived from a duration is a ramp, and a ramp ranks days. Callers drawing it behind text apply a fixed alpha.
- **User-facing dates, clocks and durations are formatted in `util/TimeFormat` only.** `dateWithYear` for a date read alone, `dateKeyWithWeekday` for a screen's nullable `date_key` (null on a malformed key; the `LocalDate` overload is private so parsing stays out of composables), `monthYear` for a month heading, `axisDay`/`axisMonth` for chart axes (`multiYear` decided once per series — bare "MMM" lies once the record holds two Augusts). `durationLive` is for the ticking gauge only; everything settled uses `durationShort`. Every function takes a `TimePatterns` built from string resources, **with no default**, so a call site cannot compile in English and render under Arabic. **`date_key` stays ISO** — DAO range queries rely on its lexicographic order, and the CSV is machine-read with its own frozen formatter.
- **Two bundled typefaces split by reading size** (`ui/theme/Type.kt`): **Outfit** for display/headline/title, **Manrope** for body/label — their x-heights (0.460 vs 0.540 em) make each wrong at the other's size. Each is four **static** weight cuts: a variable font needs `@ExperimentalTextApi` `FontVariation.Settings`, and without it the platform fakes bold weights. Only `fontFamily` is overridden; all M3 metrics stay. **`TextStyle.tabularFigures()` on ticking figures is load-bearing**: Outfit's `1` is half the width of its `0`, so the gauge lurches every second without `tnum`. Under Arabic, **IBM Plex Sans Arabic** (four cuts, OFL, attributed as `font:plex_arabic_*`) **replaces both** families — Compose does no per-glyph fallback — and its own Latin and tabular digits cover English habit names. `typographyFor(locale)` picks once at the theme root. The cuts are unmodified upstream files: the OFL reserves "Plex", so a subset would need renaming. The app honours font scale (everything is `sp`) but not a device font choice.
- **String casing** follows the header comment in `strings.xml`: section/card titles and notification channel names are Title Case; everything read as a line (rows, buttons, help, empty states) is sentence case. Exceptions: the product name Sleeves Up and the "Check In"/"Check Out" actions.
- **A count the user reads (or hears, in a `contentDescription`) goes through `<plurals>`.** A string with several counts (`cd_days_split`, `cd_start_time_split`, `cd_sessions_per_day_split`) words each through its own plural first (`days_count`, `sessions_count`) and takes them as `%s`.
- Material 3 with a **fixed indigo brand scheme** (`ui/theme/Theme.kt`) — no dynamic colour — plus system dark mode and a branded splash. Large screens are width-capped (`ConstrainedContent`); History goes two-pane on expanded widths (`WindowSizeClass`).
- **The brand mark is generated, not drawn.** `play-store-assets/generate_icons.py` owns the geometry — a 3×3 grid of rounded cells, seven filled — and prints the `pathData` for `drawable/ic_launcher_foreground.xml` and `ic_stat_checkin.xml` plus the 512px Play icon; paste the printed paths back, never hand-edit one. Its `verify()` asserts the adaptive-icon safe circle on every run. `BrandGrid` restates the same values (cells a side, `FILL_FRAC`, `CORNER_FRAC`, `EMPTY_CELLS`) in Compose because it must address cells individually — **change them in both**; nothing gates the copy.
