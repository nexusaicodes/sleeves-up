# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A native Android check-in/check-out tracker built around **showing up**, not around hours cleared. It records auth-gated check-in/out intervals, shows what each day held, and counts consecutive days shown up for. The app is branded **Sleeves Up** — that is the launcher label, the Play listing name and every place the product names itself in copy. It is *only* the user-facing name: the package is still `com.checkin.app`, the `applicationId` still `com.nexusai.checkin.app`, the Gradle build still `CheckInApp`, and the types, themes and file names all still say CheckIn. Renaming any of those is a separate decision with real cost (see the identity paragraph below); the brand is a string, and `app_name` plus the three copy strings that spell the product out (`welcome_reminders_body`, `licenses_intro`, and `Feedback.draft`'s subject and body line) are the whole of it. **The name is a description of a state, not an exhortation, and that is a copy rule rather than a preference.** Sleeves are up or they are down — which is the binary calendar in four words — and nobody has ever rolled their sleeves up for nine hours, so the name carries no measurement at all. That is what lets it sit on top of an app where hours grade nothing, and it puts the product in the honest-labour register rather than the productivity one: no flames, no confetti, no optimisation. The metaphor is therefore **glossed exactly once, in the Play listing's opening line**, and is banned from recurring in-app copy — a notification, a celebration or an empty state saying "roll your sleeves up!" turns a name into a mascot, and a mascot is the gamification register this app deliberately has none of. The vocabulary table in `play-store-assets/LISTING.md` carries the rule; every in-app string was reviewed against it at the rename and none needed changing, which is the outcome to preserve.

**Rules:**
- Net time = sum of all completed check-in/out intervals per day (open intervals between check-ins are excluded). Nothing is ever subtracted from an interval
- Every day counts (7 days/week — no weekends/holidays exemption)
- **A day counts because it has a session, not because its hours cleared a bar.** There is no target, no half-day tier, and no leave deficit. A 45-minute day counts as a day shown up for exactly as much as a nine-hour one — see the gotcha below before adding any threshold back
- Hours stay fully visible everywhere (totals, charts, the calendar's screen-reader text, CSV) as a **plain quantity with no direction** — never a ring fill, a colour ramp, a superlative or a comparison against the user's own best. See the no-grading gotcha below
- **Sessions are immutable** — no edit/delete/manual entry by design
- Every check-in AND check-out is gated by a presence check: the camera hardware's own face detection (offline, no image captured), with **device unlock** as a fallback — offered after `DEVICE_UNLOCK_OFFERED_AFTER_MS` of looking, or immediately on a camera that cannot detect faces
- Self-contained: Room-only persistence, no backend; CSV export via share sheet

## Build Commands

The Gradle wrapper is checked in and pinned to **Gradle 8.13** (the project's Kotlin 1.9.20 + AGP 8.13.2 are incompatible with Gradle 9.x, which removed `HasConvention`).

`gradle/gradle-daemon-jvm.properties` requires a **JetBrains vendor JDK 21** for the daemon — the one bundled with Android Studio (`/Applications/Android Studio.app/Contents/jbr/Contents/Home`). Android Studio finds it automatically. For **CLI builds**, point Gradle's toolchain detection at it:

```bash
export JBR="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
./gradlew :app:testDebugUnitTest -Dorg.gradle.java.installations.paths="$JBR"  # JVM unit tests
./gradlew :app:assembleDebug     -Dorg.gradle.java.installations.paths="$JBR"  # Build debug APK
./gradlew :app:installDebug      -Dorg.gradle.java.installations.paths="$JBR"  # Install on a device
./gradlew staticAnalysis         -Dorg.gradle.java.installations.paths="$JBR"  # ktlint + detekt
./gradlew :app:verifyLicenseCoverage -Dorg.gradle.java.installations.paths="$JBR"  # licence list vs classpath
./gradlew :app:verifyDocMap          -Dorg.gradle.java.installations.paths="$JBR"  # this file vs the tree
./gradlew ktlintFormat           -Dorg.gradle.java.installations.paths="$JBR"  # Auto-fix formatting
```

Run a single test class: `./gradlew :app:testDebugUnitTest --tests "com.checkin.app.ConsistencyStatsTest"`.

There is also a third identity string, `rootProject.name = "CheckInApp"` in `settings.gradle.kts`. It names the Gradle build and nothing else — not the package, not the Play listing, not a directory the app writes to — and is the one a newcomer meets first, so it is worth knowing it matches neither of the two below.

**The `applicationId` is not the `namespace`, and the split is deliberate.** `namespace` is
`com.checkin.app` — the Kotlin package, where `R` and `BuildConfig` are generated, and what a
relative manifest name resolves against. `applicationId` is `com.nexusai.checkin.app` — the Play
identity, the data directory, and the FileProvider authority (written `${applicationId}.fileprovider`,
so it cannot drift). The launcher component is therefore **`com.nexusai.checkin.app/com.checkin.app.MainActivity`**,
and `adb shell am start -n com.checkin.app/.MainActivity` fails with `does not exist` — the first
thing to get wrong in any adb session, because every source file in sight declares the other one.
Nothing depends on the two matching. Note only that `applicationId` is frozen at the first Play
upload, **and that upload has happened — v1.1 (code 20260725) was the first and v2.0 (code
20260820) is the current release**, so `com.nexusai.checkin.app`
is now permanent and aligning the two would cost a new listing with no install base carried over.
Treat the split as settled rather than as a thing to tidy.

**Static analysis** is **ktlint** (via `org.jlleitschuh.gradle.ktlint`, engine pinned to 1.5.0) and
**detekt** 1.23.8, applied to every project including the root build script. `staticAnalysis` is the
one task CI and the pre-commit hook both call. Formatting rules come from `.editorconfig`
(`intellij_idea` style, matching `kotlin.code.style=official`; 120 columns; `@Composable` exempted
from ktlint's camelCase `function-naming` rule). Detekt's overrides are `config/detekt/detekt.yml`
with `buildUponDefaultConfig = true`, so the file only states what differs, and nothing there
duplicates a ktlint check (`MaxLineLength` is off for exactly that reason). **There is deliberately
no detekt baseline file** — `baseline.xml` is wired up in the root build script but does not exist,
because the tree is clean. Adding one would convert a finding into permanent, invisible debt; the
intended responses to a new finding are a real fix or a site-level `@Suppress` carrying the reason
(see `CheckInService.enterForeground`, `SessionWatchdog.reviveIfNeeded`, `DefaultCsvExporter.export`, `PresenceCheckScreen`).

A **pre-commit hook** (`githooks/pre-commit`, enabled per clone with `git config core.hooksPath
githooks`) runs the same `staticAnalysis` task. It exits early when no `.kt`/`.kts` file is staged,
and refuses outright to commit a `*.jks` / `keystore.properties` / `local.properties` — `git add -f`
can otherwise defeat `.gitignore`, and a leaked upload key is unrecoverable. Tests are deliberately
not in the hook; they are CI's job.

Toolchain: **JDK 17** source/target compatibility. Android **SDK 36** (`compile`/`target`, Android 16 — Play's target-API floor from 2026-08-31), **min SDK 33** (Android 13). **33 is a floor with a reason, not a default to lower further**: `POST_NOTIFICATIONS` is defined from API 33, so below it `ContextCompat.checkSelfPermission` returns DENIED for a permission the platform does not have, `NotificationDelivery.canDeliver` then refuses every post, and the timer notification, the session reminder and every nudge go silently dead while every screen looks normal. Nothing fails and no test catches it — the app carries no `Build.VERSION.SDK_INT` *branch* anywhere (the one reference, in `AboutCard`, reports the level in the feedback draft rather than switching on it), so a lower floor means introducing the first one. Android lint reports this as an `InlinedApi` *warning*, not an error, which is why `lintDebug` passing is not on its own evidence that a minSdk drop is safe. The two API-29 items that would bite next are `Window.isNavigationBarContrastEnforced` in `ui/theme/Theme.kt` and `android:Theme.DeviceDefault.DayNight` in `themes.xml`, and biometric 1.1.0 does not support `BIOMETRIC_STRONG or DEVICE_CREDENTIAL` below API 30. Unit tests live in `app/src/test/java/com/checkin/app/` and are pure JVM (no Robolectric). The suite mocks nothing — every seam is stood up with a hand-written fake in `Fakes.kt` — so JUnit and the coroutines test dispatcher are the only test dependencies, and there is **no `androidTest` source set**, which is why no instrumentation dependency is declared either.

**Versioning** is centralized in `gradle.properties` (`VERSION_CODE` / `VERSION_NAME`), read by `app/build.gradle.kts` (with `-P` override support). **`VERSION_CODE`** is the integer Play orders builds by — scheme is **`YYYYMMDD` of the release day, set manually** (must be strictly higher than any code already uploaded, app-wide; users never see it). One uploadable build per day; for a rare same-day rebuild, `+1` or append a 2-digit counter (`YYYYMMDDNN`). **`VERSION_NAME`** is the user-facing SemVer `MAJOR.MINOR.PATCH` label — bump when meaningful. Promoting the *same* `.aab` across tracks (internal → production) reuses its code; only a rebuild needs a new one.

**`verifyDocMap` keeps this file honest about the tree.** It fails when a main-source `.kt` is not named anywhere in CLAUDE.md, and when CLAUDE.md names a `.kt` path that does not resolve. Only the file-name half is mechanical — what a file *does* stays prose, exactly as with the licence list — but that half is where the drift is: two navigability audits months apart both found the same shape of defect, a paragraph naming a symbol that had moved or died and a file the map had never mentioned. It reads files and nothing else, so it runs beside `staticAnalysis` rather than with the classpath tasks, and it declares an output stamp so it is UP-TO-DATE when neither the doc nor the tree changed. There is deliberately **no allowlist**: a new file earns a line in Key Source Paths, which is the whole point. Note it cannot check a bare symbol name — this file names plenty of deliberately deleted ones — so only backticked filenames ending in .kt are checked in that direction. **A third direction reads the comments in the sources themselves** (and in `app/build.gradle.kts`, which is how a phantom constant survived there a whole round after being fixed here): a comment naming `SomeType.member` fails the build when `SomeType` is a top-level project type and `member` is declared nowhere. Both halves are narrow on purpose. Only *top-level* types count as owners, which keeps out the platform names the prose legitimately discusses without ever calling (`Intent.ACTION_SEND`, `Face.getScore`) and keeps out a nested type whose simple name collides with a platform one — `ServiceReconciler.Result` is the live example, since `NudgeWorker` rightly writes `Result.failure()` for a method it never calls. What it deliberately does **not** catch is a reference whose *owner* is gone entirely, which was exactly the `AuthGate.BIOMETRIC_FALLBACK_AFTER_MS` case: telling a deleted project type from a platform one needs a rule that, measured on this tree, flagged 14 real platform references for every true finding. That is left uncaught rather than gated dishonestly — the same call `UnusedResources` documents in the build script. (Writing such a name in prose therefore asserts the file exists — this sentence is the guard catching its own documentation, which is the behaviour working.)

**CI** (`.github/workflows/ci.yml`) runs `staticAnalysis` first — it needs no compiled classpath, so a style or smell failure reports in seconds instead of after a full assemble — then `:app:testDebugUnitTest` + `:app:verifyLicenseCoverage` + `:app:assembleDebug`, and finally `:app:lintDebug`, on push/PR to `main`. **Android lint is a third gate, not a duplicate of the other two**: it is the only one that sees the manifest and the resources — `UnusedResources` is raised to an **error** there, since nothing else catches a resource nobody references and a warning nobody must clear is a finding that accumulates; anything referenced only indirectly takes a scoped `tools:ignore` carrying the reason, never a blanket disable — and the only one that enforces AndroidX's `@RequiresOptIn` markers — those are declared Java-side, so the Kotlin compiler ignores them entirely and `Camera2Interop` compiled for months with no opt-in at all. It needs a compiled classpath, which is why it runs last rather than with `staticAnalysis`, and it stays out of the pre-commit hook for the same reason the tests do — it costs ~25s where the hook costs ~5s. It provisions a JetBrains Runtime 21 via `actions/setup-java` (`distribution: jetbrains`) to satisfy the daemon-JVM criteria, then passes `-Dorg.gradle.java.installations.paths="$JAVA_HOME"` — the CI mirror of the local `$JBR` flag above. The Android SDK is the one preinstalled on the runner.

## Architecture

**MVVM with Jetpack Compose + Room + Foreground Service + CameraX + Camera2 face detection + BiometricPrompt.** Manual DI (no framework): `CheckInApplication` holds an `AppContainer` (`di/`) that builds the `CheckInRepository`, the side-effect seams (`platform/` — `PromptSettings`, `ServiceController`, `CsvExporter`), the `TimeSource`, and an app-wide `CoroutineScope`. The seams live in `platform/` rather than beside the container because they are Android adapters, not wiring: `di/` holds `AppContainer` alone, so nothing outside it imports from a package named for dependency injection. Each `ViewModel` is constructor-injected via a `viewModelFactory`, exposes **one** reactive `UiState` (`StateFlow` built with `stateIn`/`flatMapLatest` over Room `Flow`s), and is JVM-unit-tested with fakes.

```
UI (4-Tab Compose Screens) → ViewModel (one UiState StateFlow) → Repository → Room DAO → SQLite
                                    ↕
                           CheckInService (foreground service; timer notification only)
                                    ↕
                    Presence gate: CameraX preview + Camera2 HAL face metadata → BiometricPrompt fallback
```

- **Pure/testable core** (no Android deps, unit-tested):
  - `data/ConsistencyStats` — how far counting reaches, days shown up, and the totals. It returns no longest day and no run length: every such figure is a baseline something else is then measured against
  - `data/SessionRhythm` — the descriptive splits: which part of the day a session began in, and how many sessions a day held. Pure, zone injected
  - `data/TimeSource` (`SystemTimeSource`) — injectable clock so date logic is deterministic in tests
  - `service/SessionSchedule` — reminder cadence and day-boundary instants; `service/SessionClock` — the ongoing notification's elapsed time and chronometer origin
  - `util/TimeFormat` — the one place durations, clock times **and dates** are formatted
- **Room** — single entity `CheckInSession` (table `sessions`): `id`, `started_at`, `stopped_at` (null while active), `duration` (null until check-out), `date_key` (`yyyy-MM-dd`, the check-in day), `closed_by` (`ClosedBy`, stored as its frozen string via `ClosedByConverter`, null while the session is open). DB name `"_app"`, **version 1 with no migrations, deliberately**. It had reached version 6 across four migrations — the presence-pause columns added and then removed, and two vestigial selfie columns dropped — and all of them are collapsed into the schema the entity declares today, with the `closed_by` column that would have been the fifth landing in the same commit that collapsed the chain, because there is no install base to carry: both Play uploads reached effectively zero installs and no device holds session history anyone wants. **That exemption is now spent** — every future schema change needs a real migration, and `AppDatabase`'s KDoc carries the two things to know before writing one (`DROP COLUMN` is unavailable at minSdk 33; a new column needs `@ColumnInfo(defaultValue = ...)` matching the migration's `DEFAULT`). There is **no `androidTest` source set**, so no gate here can catch a broken migration: verify by installing the previous build, seeding it, and installing over the top. `fallbackToDestructiveMigration()` remains the backstop, and is what lets the collapse restart a development device still holding a version-6 file rather than crashing on it.
- **CheckInService** — `specialUse` foreground service showing the ongoing timer notification, and **only** that. It runs no ticker and owns neither the session reminder nor the day-boundary close: the notification's elapsed time is drawn by the platform chronometer from one post, and both alarms run through `SessionLifecycleRunner`. It posts on state changes — start, revive, refresh, teardown — a handful of times per session. Persists a render mirror in `checkin_timer_prefs` to survive process death (`START_STICKY`). The **DB row is authoritative**: those prefs are advisory cache, read only so the notification posted inside the foreground-start deadline isn't blank, and every command reconciles against the active session via `ServiceReconciler` — a closed/absent row tears the service down (no orphan notification), and an in-flight reconcile is cancelled first so a stale snapshot can't clobber fresher state. `CheckInService.isRunning` is what `SessionWatchdog` reads to tell a live service from a killed one.
- **Presence gate** — `PresenceGate` is the single entry point and the only place the **camera** permission is asked for (`POST_NOTIFICATIONS` is asked once more at first open — see the launch-ask gotcha): it renders the prominent disclosure, then the `CAMERA` + `POST_NOTIFICATIONS` request, then `PresenceCheckScreen`, and both call sites (the root gate in `ui/AppRoot`, the in-app gate in `AppNavScaffold`) go through it. `PresenceCheckScreen` binds a front-camera preview and reads the HAL's face metadata off it; the camera bind is guarded so a dismiss before the provider resolves still releases it. **The check passes itself** on the first frame reporting a face — there is no confirm button (see the nothing-to-press gotcha). `DEVICE_UNLOCK_OFFERED_AFTER_MS` (10s) of looking without finding anyone offers a device-unlock (`BiometricPrompt`) fallback, and a camera reporting no face-detection mode offers it immediately; where the device has no screen lock, the fallback is a route to the settings screen that creates one (see the no-dead-end gotcha). The wait runs off a **saved instant** (`searchStartedAt`, `SystemClock.elapsedRealtime`) with `searchTimedOut` saved beside it, so what is left of the budget survives a rotation or a trip out of the app rather than restarting — on a device whose camera misbehaves, which is the device the fallback exists for, a phone turned over in the hand would otherwise reach the escape hatch late or never and the user could neither check in nor out. **`PresenceGate` holds a blank surface while a permission dialog is up** (`requestInFlight`, ranked above the `cameraGranted` branch), because that dialog is a translucent activity that never stops this one: the preview underneath would keep streaming and pass the check while the user was still reading a system prompt. Only the post-success `onAuthSuccess` delay is composition-scoped, so a dismissed gate never auto-succeeds. The outcome is now computed inline on the main thread from a value the camera thread has already published, so the old requirement to deliver it on `applicationScope` — which existed because detection and file deletion were async work the composition could cancel — no longer applies. `MainActivity` is a `FragmentActivity` (required by `BiometricPrompt`). The root gate is driven by `PresenceCheckSignal.request` (a `Reason`: `CHECK_OUT_FROM_TIMER` or `CHECK_OUT_FROM_REMINDER` from the respective notification's action — two values rather than one plus a payload, each carrying the `ClosedBy` the closed row records — or `CHECK_IN` from a nudge tap). The gate and the nav host render **mutually exclusively** (gate XOR host), but `rememberNavController()` is **hoisted above the switch** so the gate preserves the active tab and back stack; a `BackHandler` dismisses the gate, and the triggering intent extra is consumed once so recreation doesn't replay it. On success, either check-out reason checks the active session out and `CHECK_IN` opens one.

## Gotchas & Non-Obvious Behaviors

- **There is no daily target, and adding one back would undo the point.** Days used to be classified PRESENT / HALF_DAY_LEAVE / FULL_DAY_LEAVE against a configurable per-day target, with a `TargetSchedule` log so past days kept the target they were judged under. All of it is gone: the schedule, `AttendanceRules`, `AttendanceStatus`, `DeficitCalculator`, the Settings slider and the `daily_target_hours` / `target_schedule` prefs. The reason is empirical rather than aesthetic — **targets are missed as the normal case**, so a system whose primary output is "did you clear the bar" mostly reports failure, and a 45-minute day on a bad week rendered identically to not turning up at all. That is precisely the day the app most needs to reward. What replaced it: a day counts if it has a session, the calendar shows consecutive such days as consecutive marks, and hours are shown as a quantity everywhere they used to be graded — see the no-direction gotcha below, which finished the job by taking the grading out of *how* hours are drawn. Anything reintroducing a threshold — a minimum session length, a "real day" cutoff, a goal ring — brings the failure mode back under another name.
- **The first launch runs a welcome tour, and its only job is to give the one launch-time ask a reason.** `AppRoot` (in `ui/AppRoot.kt`) ranks three full-screen surfaces — `ui/welcome/WelcomeScreen`, then the presence gate, then the nav host — and `FirstRun.step` (pure, `FirstRunTest`) decides when the first is owed. Before it, the `POST_NOTIFICATIONS` dialog was the very first thing a fresh install put on screen: a user was asked to accept notifications from an app that had not yet said a word about itself. The tour is three `HorizontalPager` pages — the thesis (a day counts because it has a session), the camera (checked on this device, no photo taken), the reminders (at most twice a day, off with a long press) — and the third exists so the dialog that follows it has just been explained. **The ordering is enforced structurally, not by branch position**: `NotificationPermissionOnFirstOpen` is composed only when `step == ASK_NOTIFICATIONS`, because a rule that held only because one branch was written above another is a rule no test can see and any edit can undo. **The tour outranks the gate**, and the reachable case is what settles it. On a *fresh* install the two cannot meet at all — a never-launched app is in the stopped state, so no alarm is armed and no nudge can be posted or tapped — but every install *updated* onto this build owes the tour while its alarms are armed and its notifications live, so a nudge tap raises the gate with the tour still owed. Gate-first delivers the tour *after* the user has checked in: an introduction to an app they have just used, whose last page promises a dialog that `notifications_asked` has already suppressed. Tour-first costs that user a few seconds; the presence request survives the read, since its 10-minute fuse only retires in `onStart`, so the check-in follows immediately after. Two states go away with the ordering: nothing can preempt the tour, so `rememberPagerState`'s saveable entry cannot be disposed mid-read (leaving a composition discards saveable state — the failure `rememberNavController` is hoisted above the switch to avoid), and a pending `CheckOutSignal` can no longer draw a celebration over the tour, because every check-out path now sits behind it. `FirstRun.step` tests `!seenWelcome` **first**, so an install updated onto this build — which already carries `notifications_asked` while `welcome_seen` defaults false — sees the tour once rather than never. Reading that flag as "an update, skip it" was the alternative and it couples the two: anything that later set `notifications_asked` earlier would silently disable the tour for everyone, with nothing failing. The tour is deliberately **not** in `onStart`'s `expireIfStale` pair — it is a fact about the install, not a reaction to a moment the user chose — and it is the one full-screen surface with **no `BackHandler`** at its root, so back leaves the app and the tour is owed again; only finishing or skipping writes the flag. The page *index* does have one, because back on page 2 must mean page 1. **Skipping and finishing are not the same ending.** Both retire the tour, but only a tour read through releases the `POST_NOTIFICATIONS` dialog — `FirstRun.asksNotificationsAfter(Exit)` is that rule, and a skip additionally writes `notifications_asked` so the launch-time ask is settled without ever being raised. A skip firing the dialog anyway is the original defect in one tap, on page 1, with nothing said; it costs the user no notifications, because `PresenceGate` still asks at the first check-in. **The button label reads `settledPage`, never `currentPage`** — the latter flips as soon as a scroll passes halfway, so on page 2 the label became "Get started" mid-animation and the second tap of an ordinary double-tap finished the tour, skipping the very page that explains the dialog it releases. The tour does not replace `CheckInScreen`'s first-run `EmptyState` ("Ready when you are"), which is a different thing: the Check-In tab's state for a user who has passed the tour but not yet checked in.
- **Nothing is asked for at launch — after the welcome tour, the app opens straight into the nav host.** The disclosure and both runtime permissions were once a blocking startup sequence; they now live inside `PresenceGate` and are raised only when a check actually needs them, which in practice is the first check-in. History, Reports and Settings are therefore fully browsable by a user who has never granted anything, and a *revoked* camera permission no longer locks the whole app out — it surfaces at the next check. Consequences worth knowing before moving any of it back: the gate must ask on entering the "disclosed but ungranted" state rather than only on the disclosure's Continue button, or a permission revoked between sessions strands the user on a recovery screen that never prompts; a `LifecycleResumeEffect` re-reads the grant because the recovery screen's escape hatch is system settings, which returns with no result; and `CameraDisclosureScreen` now carries a **Not now** button, since a screen that interrupts a check-in needs an exit that isn't the back gesture. Only the camera decides whether a check can run — a refused `POST_NOTIFICATIONS` costs the timer notification and the reminder, both already guarded by `Notifier`.
- **No image is captured, and that is a property of the mechanism rather than a promise the app keeps.** Face detection is done by the camera HAL: `PresenceHardware.faceDetectingPreview` asks the HAL for `CaptureRequest.STATISTICS_FACE_DETECT_MODE` through `Camera2Interop`, and `PresenceCheckScreen` reads `CaptureResult.STATISTICS_FACES` off each result, so frames never leave the camera pipeline and the app only ever sees a count. There is no file to delete, nothing to strand when the gate is dismissed mid-check, and nothing to sweep at startup. The predecessor wrote a JPEG to `filesDir/selfies/`, decoded it, ran ML Kit over it and deleted it — which needed `SelfieStorage`, a startup `sweep()` for frames orphaned by process death between write and delete, and detection pinned to `applicationScope` so a dismissed gate could not strand the file. All of it is gone with the capture. The disclosure copy changed with it: "photos are checked on this device, then deleted" was the honest claim only while a JPEG briefly existed, and is now "no photo is taken". **Nothing here may say photo, capture or selfie again** without a mechanism that actually takes one.
- **The camera decides, so the camera's answer has to be treated as optional.** `FaceDetectSupport` (pure, `FaceDetectSupportTest`) picks the mode and decides what counts as a face. `SIMPLE` is preferred over `FULL` because the gate reads a count and nothing looks at landmarks or tracking ids, and both are tested because the platform does not promise a camera offering `FULL` also offers `SIMPLE`; `OFF` is a mode but not a detector, so a camera offering only it yields null. **What the camera advertises and what it runs with are separate answers, and both are read**: `preferredMode` takes `STATISTICS_INFO_AVAILABLE_FACE_DETECT_MODES` before the bind, and `isDetecting` then checks `CaptureResult.STATISTICS_FACE_DETECT_MODE` on the results — a HAL that lists `SIMPLE` and then runs `OFF` reports an empty frame forever, which is indistinguishable from a wall, so it is routed to the fallback rather than left to time out. **A camera that cannot detect faces is offered device unlock immediately** rather than being made to wait `DEVICE_UNLOCK_OFFERED_AFTER_MS` for an answer that is already known — a countdown that cannot be won is worse than no countdown. That verdict needs `NON_DETECTING_RESULTS` (10) consecutive results to reach, and `resultIsDetecting` reads the faces alongside the mode: the results around session configuration can carry `OFF` on a camera that then works perfectly, and a result carrying face rectangles came from a detector whatever its mode field claims, so concluding from either alone strands a working camera on the fallback while a live detector runs behind it. A camera taken back by a later detecting result is un-written-off for the same reason.
  - **There is no score floor, and reintroducing one in any form breaks the gate on real hardware.** `someonePresent` counts every reported face, because the platform gives the confidence score no meaning a caller can rely on. `Face.getScore` is declared `@IntRange(from = SCORE_MIN, to = SCORE_MAX)` with **`SCORE_MIN = 1`**, and the `SIMPLE` contract states exactly what that mode does *not* support — the face id is `ID_UNSUPPORTED`, the eye and mouth positions are null — while requiring nothing at all of the score. A HAL that does not grade may therefore return the legal minimum forever, and one does: probed on the MediaTek front camera this app was developed against, every genuine face — squarely framed, well lit, bounds tracking the user as they moved — came back scored **1**. `MIN_SCORE = 50` rejected all of it, which is what made the gate appear unable to see a face at all; **lowering the floor is not the fix either**, since 20 rejects the identical frames. Nor is an "unscored means zero" escape, which cannot fire against an `@IntRange(from = 1)` value. What discriminates is the rectangle: the HAL emits one only where it already believes a face is, and the same probe showed empty frames reported as zero faces with the user's arrival reported the very next second. A wall was never going to pass this check; a user was.
  - **There is nothing to press: the check passes itself on the first frame that reports a face.** `snapshotFlow { facePresent && !usingDeviceUnlock }.first { it }`, then the `SUCCESS_CONFIRMATION_MS` confirmation, then `onAuthSuccess`. That effect is keyed on `Unit` and latched by `first`, **never on the live value** — a `LaunchedEffect`'s coroutine dies with its key, so keying it on `facePresent` would cancel the confirmation the instant the user lowered the phone, undoing a check that had already passed with the very movement that follows passing it. Asking for a tap was worse than redundant: the button sat at the bottom of the screen, so reaching it tilted the face toward the edge of the front camera's field of view for exactly the frames around the tap, which is why the check used to sample a 1.5s window (`PRESENCE_WINDOW_MS` / `stillPresent`) rather than the latest result. No tap, no reach, no window — all of it is deleted, along with `presence_confirm`, `presence_no_face` and `presence_face_in_frame`, and `facePresentFlow` now just carries `someonePresent(faces.size)` frame by frame. What the screen says while it looks is `presence_looking`, shown from the moment the gate opens rather than from the first capture result, and `presence_looking_slow` once the wait runs out so the fallback appearing with it is explained rather than simply there: a camera still being bound has not found anyone either, and the alternative is a bare preview stating nothing for as long as the bind takes.
  - **With no tap there is no attempt to count, so the fallback is on a timer.** It is one constant — `DEVICE_UNLOCK_OFFERED_AFTER_MS` (10s), in `ui/presence/DeviceUnlock` beside the prompt it gates — and carries no test, because a timeout has no logic to pin; the three-failure ladder, `failCount`, `shouldShowHint`/`attemptsLeft` and the `presence_attempts_remaining` plural all went with the button. Something had to replace it, and this is the no-dead-end rule below applied to a state that is otherwise invisible: a camera detecting perfectly well but never resolving *this* user — unlit room, obscured lens — would leave the gate with no exit but Dismiss. **The wait is measured from the gate opening, not from the camera streaming, and that reversal is the load-bearing part.** Timing it from the first capture result spends nothing on a slow bind, which is the obvious reading and the wrong one: a camera that binds successfully and then never delivers a result — a stalled HAL, a front camera another app is holding — starts no clock at all, so `cameraUsable` stays true, the fallback is never offered, and Dismiss is the only control left on a screen check-out also routes through. A bind costs a fraction of the budget where it works; where it does not, composition is the only anchor that still ends in something. Two latches keep the offer from being taken back once made: the elapsed-time check runs off a saved instant rather than a fresh countdown (so a rotation resumes the wait instead of restarting it), and `cameraUsable == false` sets `searchTimedOut` too, so a HAL that reports `OFF` for its first results and then starts detecting cannot pull the button out from under a user already reaching for it — the explanatory message goes, since it has stopped being true, but the escape hatch stays. The button is additionally withdrawn while `usingDeviceUnlock` is set, which covers the gap between a device unlock succeeding and the caller's state reaching the screen, where a second tap would otherwise raise a second prompt.
  - **The camera keeps streaming behind the device-unlock prompt, and that is the one race auto-success introduces.** `usingDeviceUnlock` is set for the life of the `BiometricPrompt` and cleared on any error, cancel included, and the success effect reads it: without it a face found while the user is answering the prompt passes the check *under* the dialog, leaving a live prompt over a screen that has already moved on and a second `onAuthSuccess` behind it if they then complete it. **The flag is `rememberSaveable`, and that is only safe because the prompt is built in composition rather than on the button tap.** A prompt outlives a recreation of the activity beneath it — `MainActivity` declares no `configChanges`, so rotating with the credential UI up rebuilds this screen — and a flag left un-saved comes back false, which is the race again with the dialog still on screen. Saving it alone is worse: `BiometricPrompt` registers its callback against the activity, so a callback captured at tap time belongs to the composition the rotation discarded, the cancel that follows writes to dead state, and the restored `true` has no writer left alive — the camera path is then shut for good. `remember(activity)` around the construction re-registers a live callback on every recreation, which is what makes the saved flag clearable. `authenticate` is wrapped in `runCatching` for the same reason: only an error callback clears the flag, and a prompt the platform refuses outright delivers none. It is also what still makes the `ON_STOP` clear of `facePresent` load-bearing — that is now the only way a stale `true` survives, and a gate backgrounded with a face in frame and the prompt then cancelled would otherwise pass on a frame from before the camera reopened. `cameraUsable` and `facePresent` are `StateFlow`s and the non-detecting run an `AtomicInteger`, because the capture callback is not the main thread; `facePresent` is safe to write every frame since a `StateFlow` drops a write equal to what it holds, so a steady face costs nothing.
- **The gate must never be a dead end, and the fallback is not always there to offer.** Device unlock needs a screen lock to exist: on a device with none, `canAuthenticate(BIOMETRIC_STRONG or DEVICE_CREDENTIAL)` returns `BIOMETRIC_ERROR_NONE_ENROLLED`, and an unusable camera then left this screen with no way to pass the check, its biometric button unrendered, and nothing but Dismiss — with **every** check-in and check-out in the app routed through it. Check-out is the sharper half: the session stays open until the day boundary writes a full day's `duration` onto a row nothing can edit. So **anything short of `BIOMETRIC_SUCCESS`** renders a **Set up screen lock** button onto `Settings.ACTION_SECURITY_SETTINGS` instead — not just `NONE_ENROLLED`, because every other status has the same recovery and the same alternative, and the settings intent needs no `FragmentActivity`, unlike `BiometricPrompt`. That is what leaves no status for which this screen offers nothing. Un-gating the check was the alternative and is not available — check-in is never un-gated — so the escape has to be a route to the missing credential rather than a way around it. It also means the wait always ends in something: whatever the device's status, the fallback that appears after `DEVICE_UNLOCK_OFFERED_AFTER_MS` is a control the user can act on. The status is **re-read in a `LifecycleResumeEffect`**, exactly as `PresenceGate` re-reads the camera grant and for the same reason: the recovery is a round trip through system settings, which returns no result and recreates no activity, so a value cached at first composition would still say "no device unlock" to a user who had just set one up. `ActivityNotFoundException` from the settings intent falls back to the `biometric_unavailable` message rather than throwing. Newly reachable state to keep in mind: this only became a real lockout with the HAL migration — ML Kit detected in software on every device, whereas `STATISTICS_INFO_AVAILABLE_FACE_DETECT_MODES` reports `[OFF]` on a real slice of front cameras.
- **`androidx.fragment:fragment:1.8.2` is a version floor, not a dependency, and deleting it crashes every runtime permission request.** No source file imports anything from `androidx.fragment` except `FragmentActivity`, which `biometric` re-exports on its own API surface — so it reads exactly like the unreachable weight this repo deletes on sight, and it is the opposite. `biometric` 1.1.0 (still the newest stable) pins fragment **1.2.5**, whose `FragmentActivity.startActivityForResult` rejects any request code above 16 bits, while `ActivityResultRegistry` — which every `rememberLauncherForActivityResult` goes through — generates them from 65536 up. `MainActivity` is a `FragmentActivity` because `BiometricPrompt` requires one, so the pair crashes the app outright at both asks: `POST_NOTIFICATIONS` after the welcome tour, and `CAMERA` inside `PresenceGate`. Nothing else in the graph pulls fragment forward — **but something used to, and that is how this arrived.** v1.1 resolved fragment to **1.3.6**, dragged there by the ML Kit stack, and in 1.3.6 `validateRequestPermissionsRequestCode` compiles to a bare `return`: the restriction is a no-op and the shipped release was never affected. Removing ML Kit is what dropped the graph back onto biometric's pin and *created* the crash, one commit before the floor fixed it. So the general lesson is not about fragment: **deleting a dependency can lower a version another dependency was silently relying on**, and nothing in the build reports it. Verify with `./gradlew :app:dependencies --configuration releaseRuntimeClasspath` after any removal, and check the bytecode rather than the version number when a range looks dangerous — `javap -c` on the class in the Gradle cache settles in seconds what a changelog may not mention. It is declared as a plain `implementation` rather than a `constraints { }` block only because the comment above it carries the reason; if that line is ever tidied, the constraint form is the one that says "floor" unambiguously.
- **Two SharedPreferences namespaces, and neither holds a fact about the record.** `prompt_prefs` (`camera_disclosure_seen`, `notifications_asked`, `welcome_seen` — namespace, keys and accessors all inside `platform/PromptSettings`, which is the seam; the keys used to sit in a separate `data/PromptPrefs`, which put the reads in one package and the writes in another for no gain. **A new one-time prompt is a new key here, never a new prefs file**: the backup rules exclude `prompt_prefs.xml` by name, so a key inherits that, while a separate namespace needs the same exclusion added to two XML files and missing either restores onto a device asserting a prompt was raised where it never was); and `checkin_timer_prefs` (the live timer's render mirror plus `SessionAlarms.remindersSent`). **`engagement_prefs` is gone** — it held only the variant-bucketing install id, and variants went with the analytics that were the only thing able to read which arm won. Some installs still hold `master_enabled` and `nudge_enabled_<NUDGE_NAME>` in that file, left by in-app nudge toggles deleted earlier; nothing reads or clears them, and a wipe would be code running forever against a population of roughly zero. **None of those three names may ever be reused**, since a read under any of them would hand those installs a stale opt-out they never made. Everything in `prompt_prefs` records that a one-time prompt has already been raised, which is why the file is named for prompts and not for tracking: **`tracking_start_date` used to live there and is gone**, along with the `tracking_prefs` name, `attendance_prefs` before it, and the `migrateFromLegacy` copy between them. See the tracking-start entry below for why. **`checkin_timer_prefs` and `prompt_prefs` are excluded from cloud backup**, alongside the sessions DB: the first mirrors rows a restore does not bring, and the second would assert that prompts were already raised on a device where they never were — a cloud restore carries no runtime permission grants, so a restored `notifications_asked` leaves the timer notification, the session reminder and every nudge silently dead. Device-to-device transfer keeps both, because there the DB and the grants move too. `nudges.db` is deliberately **not** excluded: it holds only today's nudge sends, so the worst a restore can do is suppress a nudge on the day it happens.
- **Two databases, and the second one is scheduler state rather than analytics.** `_app` (v1, no migrations) holds the sessions. `nudges.db` (v1, no migrations) holds **one thing**: which nudge was sent, and when. It stays a *separate* Room database so no change to it can put a user's session records at migration risk or widen the CSV export, and `fallbackToDestructiveMigration` is a safe backstop there in a way it never is for `_app` — the most a wipe costs is a duplicate nudge on the day it happens. **It is a new file, not a renamed one.** Renaming a database does not move it, so `NudgeSendDatabase.RETIRED_DB` (`engagement.db`) is deleted rather than left on disk holding rows nothing will open again — by `NudgeSendDatabase.deleteRetiredFile`, called once per process from `CheckInApplication.onCreate` on the application scope. **Not from `getDatabase`**, which is where it used to sit: that runs on the main thread of every cold start, since the check-in path reaches it through the container's lazies, and this is blocking filesystem work whose result nothing waits on. Carrying the old file forward would have meant a migration off a schema whose every other column had no reader — code that runs exactly once and is then both wrong to delete and impossible to reach. The cost is the current day's sends on the one upgrade where it happens: at worst a duplicate nudge that day. The single read is `NudgeSendLog.sentSince(startOfDay)`, and it exists because the frequency rules must know what was already sent today. **Nothing write-only may be added back.** The predecessor recorded opens, dismissals, conversions, per-variant buckets, session reminders and foreground-service lifecycle events across three `EngagementSource` values, needing `AttributionRules` to attribute conversions in Kotlin (the sessions table being in another database) and a `source` column to keep the three streams from consuming each other's slots. A full trace found **not one reader** for any of it: `SERVICE` and `PRESENCE` rows were scoped out of both queries by definition, `OPENED` was never read, `CONVERTED` was read only by the next `CONVERTED` write's own dedup check, and `DISMISSED` existed only to suppress a `CONVERTED`. The app declares no `INTERNET` permission and shipped no surface that displayed any of it, so there was no reader off-device either. All of it is deleted, along with the whole `notify/log/` package it lived in.

- **The nav scaffold owns the screen title.** `AppNavScaffold` renders a `CenterAlignedTopAppBar` whose title is the active `Screen.titleRes`, driven by the same back-stack subscription as the bottom nav — screens never draw their own heading, and they receive the combined top inset through the Scaffold's `innerPadding`. `Screen` splits into `Tab` (a bottom-nav destination) and `Detail` (pushed above a `parent` tab: back arrow instead of a centred-only title, and the parent stays lit below so a sub-screen still reads as part of its section). **A new destination must be added to `allScreens` (in `ui/navigation/Screen.kt`, alongside the hierarchy itself), not just to the nav graph in `NavigationGraph.kt`** — the title lookup falls back to `Screen.CheckIn`, so a route missing from that list renders a screen labelled "Check In" rather than failing. `allScreens` is the one list to add to: `tabs` and `titledScreens` are both derived from it, so they cannot disagree, and `ScreenTest` pins the rest (unique routes, every screen titled, every `Detail.parent` a `Tab`). It cannot pin the registration itself — that needs `sealedSubclasses`, which needs `kotlin-reflect`, which the test classpath deliberately does not carry. **A route string is not a free rename.** It doubles as the destination id a saved back stack is restored against (`route.hashCode()`), and `NavController` throws when a restored entry names a destination the graph no longer has — so an install updated while parked on a renamed route can crash on launch until the task is cleared. The `attendance` → `history` rename shipped with that hazard knowingly, on the premise that nothing had reached Play — **and that premise was wrong: v1.1 (code 20260725) was live, and it carries the `attendance` route.** So 2.0 was the first update in this app's history to rename a route out from under installs that may hold it in a saved back stack, and it shipped (tag `v2.0`, code 20260820). Whether that is reachable turns on whether a Play update preserves the task's saved instance state or force-stops the package and discards it, which is an AOSP question nobody here has answered — **do not close it from recall.** It was raised before 2.0 shipped and the risk was **accepted deliberately**: the worst case is a crash on launch for an install parked on that tab, recoverable by clearing the task from Recents, against a v1.1 install base of ~0. That is a judgement about this release's install base and **not a precedent** — the same rename against a real one is a different decision. From here on the rule has no escape clause: **a route string is frozen once a version code carrying it is uploaded**, and a rename needs the old string registered as a redirect destination. **A tab tap pops any open `Detail` before it navigates**, because the bar's `popUpTo(start) { saveState = true }` + `restoreState = true` would otherwise save the detail *into* its parent tab's back stack — tapping the lit Settings tab from Licenses would then restore Licenses, and the tab would read as dead. Settings is the one tab with **no** ViewModel at all: it holds no state, so `SettingsScreen` renders the About card and nothing else.
- **The tracking start is derived, not stored, and storing it again would reopen the bug it was deleted for.** It is `SELECT MIN(date_key) FROM sessions` — `CheckInRepository.trackingStartFlow()` (plus a suspend `trackingStart()` for the CSV export) — so it is definitionally the first session's day, null while there are none, and reactive: the first check-in starts the record by being written, with nothing seeded beside it. Open sessions count, and the query is deliberately **not** filtered to completed ones, because a first check-in still running is still the day tracking began. It used to be `tracking_start_date` in prefs, seeded at the first check-in by `TrackingSettings.seedTrackingStartIfNeeded()`, and that made it a second copy of a fact the table already held. The two could then disagree, and one restore path was enough: brought back without the sessions it indexes, the app reported **every day since as one the user did not show up for** — on a fresh install, on the one screen they check their consistency in, with no UI to correct it. Excluding the pref from backup only closed the paths anyone had thought of; the legacy `attendance_prefs` file was not excluded, and `migrateFromLegacy` copied the key straight back out of it, with the "already migrated" guard sitting in the very file the restore had skipped. Read off the sessions, the disagreement is unrepresentable and there is nothing to exclude, guard, or reconcile. Consequences that follow: `HistoryUiState.trackingStartDate` and `ReportsUiState.trackingStartDate` are **nullable**, `CalendarGrid` treats null as "no day is inside the tracked window" (the whole month draws as days the record does not cover, never as days that were missed), and neither screen can seed the answer synchronously any more — Reports renders nothing while `loading` rather than flashing an empty state, and History carries no such flag: it seeds a null start, which `CalendarGrid` draws as a month the record does not cover, and `CheckInScreen` holds the gauge's slot rather than showing the first-run welcome to a user with months of history. There is still no UI to change the start (by design); there is now no value to change.
- **Every window ends at `ConsistencyStats.countedThrough`, and that is today only once today has been checked out of.** One pure function decides it — `today` when `summaries` holds today's key, otherwise yesterday — and History, Reports and the CSV export all end there, so they cannot drift. A completed session therefore lands in the days-shown-up count, the totals, the splits and the calendar **the moment it is checked out**, with no resume and no wait for midnight. **The conditional half is the load-bearing half.** A window that simply ended at `today` would open every morning with a missed day and a dipped count, then take both back at the first check-out — the failure-first reading the daily target was deleted for (see the no-target gotcha above). Ending at yesterday until today has produced something means the numbers only ever move upward during a day, and an in-progress day still counts for nothing anywhere. **The test is free, and that is why it is written this way**: the aggregate queries filter `stopped_at IS NOT NULL`, so a row for today exists *iff* today holds a completed session — `summaries.containsKey(todayKey)` **is** the predicate, needing no extra query and correctly ignoring an open session. It follows that the map can hold no key past `countedThrough`, which is why `totalWorkedMs`/`showedUpDays` take no range and filter nothing. It is also why **History reads a one-day aggregate flow** rather than the whole record: `countedThrough` is the only all-record question that screen still asks, since every figure it used to ring against is gone. One consequence to keep in mind: `ReportScope.resolve` must return null rather than an empty window before anything divides by `window.days`, since the record's first day is unfinished until it isn't and the count would be 0 — which is why `ReportsViewModel` never clamps for itself. History divides by nothing at all now. The "today" boundary itself still comes from an injectable day clock (`TimeSource.currentDay()`), so at midnight the screens roll over **live** — and a day already counted at check-out must read identically after the rollover, neither re-counted nor reset. Only the History *displayed month* stays put until the user navigates.
- **The nudge layer is structurally isolated, and that is the point.** `notify/` may *read* tracking state to build a `NudgeSnapshot`, but it never writes to `sessions`. The entire decision surface is `NudgeEligibility.select(snapshot)` — a pure function of a plain value object, no clock, no DB, no Android — so a change to timing, capping or targeting is a change to one unit-tested function. **There is no app-level quiet-hours window and adding one back would be a mistake**: Android's per-channel settings already give the user that control, and the app's own version only ever applied to nudges while the session reminder and the timer notification ignored it — a promise ("Nothing is sent between…") the app did not keep. **Frequency is bounded three ways, and the checkpoint hours are not one of them.** The daily cap (`maxPerDay`) limits the day's total; `alreadySentToday` stops one checkpoint being sent twice; and `minGapMs` keeps two *different* checkpoints apart. Assuming the hours space deliveries out is the bug this replaced twice over — the alarm is `setAndAllowWhileIdle`, so Doze can hold the morning one until 13:57 and the afternoon one lands three minutes later, and the bands are hours wide so the hourly worker re-asks inside the one that already fired. That second case is the sharper one: without per-checkpoint dedup an 11:00 pass reposted the 10:00 nudge under the same id with identical copy, re-alerting on a high-importance channel and spending the day's second slot, so the afternoon and evening copy never fired at all. All three read from one query — `NudgeSendLog.sentSince` returns the day's sends and the snapshot derives the count, the set and the last instant from it, because three queries is how three rules come to disagree about where the day started. **The pass itself is serialised by a `Mutex` in `NudgeDispatcher`**, because two independent triggers reach it — the checkpoint alarm and the hourly worker — and a pass reads the day's sends before recording one: unserialised, both read an empty ledger and both record, which shows a single notification (the ids match) while spending both of the day's slots on it, leaving the later checkpoints unreachable. A per-nudge *cooldown* is still the wrong shape and stays deleted: it measured a rolling 20-hour window against the cap's calendar day. Two places deliberately touch app code: `PresenceCheckSignal.Reason.CHECK_IN` (nudge tap → gate) and the `PostedNudges` seam. `retireAll` is called from **both** check-in writers — `CheckInViewModel.executeCheckIn` and `MainActivity.onRootGatePassed` — and from the nudge tap, because nothing the app posts is `autoCancel` and a nudge asking for a check-in is stale whichever way the check-in was made; left posted, tapping it later runs the user through the full presence gate only to reach a session already open. It is implemented by `NudgeDispatcher` itself, since retiring a nudge is cancelling ids that class already owns and a second implementation would be free to disagree with `runOnce` about which ids exist. This is all that remains of `EngagementReporter`: its other job was recording conversions, which had no reader. **Nudges default ON**, and the channel is the switch. Opt-in reads as the cautious choice and is not: every nudge that exists tells a user they have not checked in today, and a user who has not formed the habit is precisely the one who never goes hunting through settings to enable a reminder about it — off by default meant the feature reached nobody it was built for. Turning it off is one long-press on the notification, and the frequency rules bound it to two messages a day regardless, hours apart, with `NudgeDispatcher.runOnce` cancelling the earlier checkpoints only once the later one has actually posted, so at most one is ever in the tray — clearing before the post would take a still-actionable notification away on a pass whose post is then refused. `NudgeEligibility` therefore holds **no** enabled/disabled test at all: whether the user wants nudges is the channel's question, and `Notifier` already refuses a post to a blocked one. **There is likewise no tracking-started gate**: requiring a first check-in before the app would say anything locked the nudge away from exactly the user it exists for. The isolation used to need runtime enforcement too — `CheckInService.logService` swallowed a failed write so a corrupt `engagement.db` could not take the foreground service, and the user's running timer, down with it. That whole path is gone with the service rows: the service now touches no database but `_app`.
- **A nudge tap is still gated.** `LaunchExtras.CHECK_IN` opens the root presence gate exactly like the reminder and check-out paths; success then checks in. Check-in is never un-gated, and the handler re-checks for an active session first, since the user may have checked in between the notification being posted and tapped. `repository.checkIn()` is the backstop for that check: it returns the open session rather than inserting a second, because two rows with `stopped_at IS NULL` would leave one open forever. A presence request is never queued and never outlives its tap. `PresenceGate` owns the disclosure and both permissions, so the gate always opens on the spot — there is no screen a reason could sit behind. What it can still do is go unanswered: the gate parks indefinitely on the disclosure, the camera-recovery screen or the presence check itself, and pressing Home leaves the reason set on a process-global flow nothing else clears. So `PresenceCheckSignal.raise` stamps the request and `MainActivity.onStart` calls `expireIfStale`, dropping anything older than `EXPIRY_MS` (10 minutes) before it can reopen. **The check is on start, not on stop**, because leaving the app is exactly what the gate's legitimate path does — the recovery screen sends the user to system settings and expects them back — and only elapsed time separates that round trip from abandonment. Without it a nudge tapped at 09:00 and abandoned reopens that evening and, on success, writes a check-in stamped at whatever day it had become, onto a row the app deliberately gives no way to edit. `PresenceCheckSignalTest` pins the boundary and the round trip.
- **`POST_NOTIFICATIONS` is asked for at first open — behind the welcome tour — and that is a second ask, not a moved one.** `AppRoot`'s `NotificationPermissionOnFirstOpen` requests it once on the first launch that reaches the nav host, which is now the launch *after* the tour rather than the first frame of a fresh install (see the welcome-tour entry above); `PresenceGate` still asks for it alongside the camera at the first check-in. Both exist because nudges now default on and the timer notification is the app's main surface — waiting for a check-in would leave a new user with every notification silently dead, including the one telling them they have not checked in. It is asked **once**, tracked by `notifications_asked` in prefs rather than inferred from the grant, because a refusal and a never-asked are indistinguishable through `PackageManager` and Android drops the dialog silently after two refusals, so re-asking each cold start would be invisible noise. It renders only outside the gate — two stacked system dialogs is a dialog nobody can answer — and only when the tour was read through rather than skipped (see the welcome-tour entry above). **Nothing else is asked at launch**: the camera and its prominent disclosure stay behind the gate, where a check actually needs them.
- **A nudge is delivered by an alarm, and the hourly worker is only the backstop. Do not put the trigger back on the worker.** This is the fix for a real install that got one nudge and then went silent for days. The rule was `hourOfDay >= 10`, asked once per `NudgeWorker` pass — and a `PeriodicWorkRequest`'s interval is a *request*: an app the user is not opening falls through Android's standby buckets (`working_set` ≈ 2h → `frequent` ≈ 8h → `rare` ≈ once a day) and a deferred periodic job settles at a **consistent** hour, often in an overnight Doze maintenance window. A single daily pass landing at 05:00 makes that condition false every day, permanently, and the failure is self-reinforcing — the user the nudge exists for is exactly the one whose worker has stopped running. **A time-of-day trigger needs a time-of-day primitive**: `NudgeAlarms` keeps one inexact `setAndAllowWhileIdle` alarm set for the next `NudgeSchedule.Checkpoint`, and `NudgeAlarmReceiver` re-arms from inside the pass it just fired, in a `finally` so a throwing pass still schedules the next one. The worker stays because `reviveIfNeeded` and `prune` have to hang somewhere and a second chance costs nothing — but "costs nothing" is `alreadySentToday` doing the work, not the daily cap, which at `maxPerDay = 2` happily allowed a repeat pass to resend the same checkpoint. Its `armNext` call is wrapped in its own `runCatching` like every other arming site, so a throw past the platform's alarm cap cannot skip the dispatch and the prune sharing its `try`. It still returns `Result.success()` on failure: `failure()` is *terminal* for periodic work, so one transient error would cancel every future pass.
- **A receiver's class name is a component name, and moving one is not a free rename.** An armed alarm holds a `PendingIntent` naming the receiver's *fully qualified* class, so relocating `NudgeAlarmReceiver` or `SessionAlarmReceiver` to another package changes what an already-armed alarm points at — and one armed by the previous install points at a class that no longer exists, so it is dropped rather than delivered. `notify/engagement/` → `notify/nudge/` did exactly this and is safe only because every arming site is idempotent and runs unprompted: `CheckInApplication.onCreate` re-arms on every process start and `SessionRestoreReceiver` re-arms on `MY_PACKAGE_REPLACED`, so the worst case is one missed checkpoint on the update itself. Confirmed on device — `dumpsys alarm` shows the old `PendingIntent` cancelled (`Reason=pi_cancelled`) at replace time and a fresh `NUDGE_CHECKPOINT_DUE` armed under the new component. **All three retirements were then verified as a real upgrade**, by installing the preceding commit, letting it create its channel, database and work, and installing this one over it: the channel flipped to `mDeleted=true`, `engagement.db` was replaced by `nudges.db`, and the old work name went to state 5 (CANCELLED) beside the new one at state 0 (ENQUEUED).
- **That rename also spent the app's last free pass at two persisted names, and there are no more.** Both moved with the package, and each needed a *retirement* rather than an edit, because each is a key some other system persists and neither rename reaches what is already stored. `NudgeWorker.WORK_NAME` is `nudge_pass`; the old `engagement_nudge_pass` is `RETIRED_WORK_NAME` and is explicitly cancelled in `schedule()` **before** the enqueue. A unique name is WorkManager's own key, so renaming does not rename the existing work — it enqueues new work and leaves the old `WorkSpec` standing. Because the worker class moved packages in the same change, that orphan names a class that no longer resolves, so WorkManager fails it on a schedule forever rather than running it; had only the *name* changed it would have been worse still, with `KEEP` leaving two live hourly passes that double every revive, re-arm and prune. `NotificationChannels.NUDGE` is `nudge_channel`, with both prior ids in `RETIRED_NUDGE_CHANNELS` and deleted in `ensureAll` so neither lingers in the user's settings as a switch controlling nothing. Note what deletion actually does: the record is **tombstoned, not removed** (`mDeleted=true` in `dumpsys notification`), which is precisely why an id can never be safely reused — a recreated channel would inherit the old one's settings. **The exemption that made both free is now spent.** It was never a general licence: this app reached Play at effectively zero installs (v1.1, then v2.0), so no user had a per-channel choice to lose or a schedule to disturb. A further rename of either charges real users — a channel id resets every per-channel setting made against it, and importance can *only* be revised by minting a new id. Treat both as frozen, and append to the retired lists rather than replacing them.
- **`NudgeAlarms` is stateless, and `SessionAlarms` is not, for a reason.** The session seam persists its armed instants in `checkin_timer_prefs` because they derive from a session and cannot be recomputed without one. A checkpoint is pure clock maths, so the next one is always derivable from now — there is nothing to persist, nothing to reconcile against an `AlarmManager` that cannot be asked what it holds, no new prefs namespace and no new backup exclusion. `armNext` is idempotent, which is why four callers can fire it freely: `NudgeAlarmReceiver` (re-arming from inside the pass it just fired, which is what makes the chain self-sustaining), `CheckInApplication.onCreate` (every process start), `NudgeWorker` (the deferrable repair), and `SessionRestoreReceiver` (boot and package replace, both of which *cancel* alarms). It is also **stateless in the literal sense**: it stores nothing at all, not even the instant it last armed, because the only thing that ever read that back was a debug card that no longer exists.
- **Checkpoint bands are ranges, not thresholds, and that is load-bearing.** `NudgeSchedule.checkpointAt` returns the *last* checkpoint at or before the hour, so 10–13 is MORNING, 14–18 AFTERNOON, 19–23 EVENING, and 00–09 is null. `NudgeEligibility` takes the first matching nudge in declaration order, so with `hour >= checkpoint` tests every hour past 10:00 would resolve to MORNING and the afternoon and evening copy would be unreachable for good — three nudges declared, given ids and copy, two of them dead, and nothing failing. The null band before the first checkpoint is also what keeps a nudge out of the small hours **without** an app-level quiet-hours window, which the app deliberately does not have. `NudgeSchedule` is the single source of truth for these hours, read by both the alarm and the rule: two copies is how an alarm comes to fire at an instant the rule then declines to act on, which is indistinguishable from an alarm that never fired. `NudgeConfigTest` now pins the one cross-file claim that was left in prose — that `NudgeConfig.DEFAULT_MIN_GAP_MS` stays under the smallest gap between two checkpoints — by reading both files' constants rather than restating them. **Note the name collision, and do not unify it**: `data/SessionRhythm`'s `StartBucket` also has MORNING/AFTERNOON/EVENING, breaking at 12/17 against these 10/14/19. They answer different questions — one describes when a session the user already started began, the other decides when to send a message — and each file now points at the other.
- **Presence is "today has a row", never "a session is open", and the difference is one whole class of bug.** `NudgeSnapshot.hasCheckedInToday` is the only presence question the rules ask, and `NudgeDispatcher` builds it from `getSessionsByDate(today)` rather than `getActiveSession()`. A session cannot legitimately outlive the midnight of its own `date_key` — the day-boundary close ends it — so one that has is a session whose alarms were lost to a force stop or a package replace. Suppressing on "a row is open" meant such a session silenced every nudge for as long as it stayed open, which is indefinitely on a device the user has stopped opening, and the nudge it silenced was the one that would have brought them back to fix it. Note the *first* fix for this was an `openSessionOverdue` flag and an `isPresent` property beside `isCheckedIn`, and it was dead weight: `getSessionsByDate` does not filter `stopped_at`, so a session open *today* is already in today's rows, and one open from an earlier day is necessarily overdue — `isPresent` therefore implied `hasCheckedInToday` and could never change a decision. Reading the day's rows is the whole fix; a second presence concept beside it is a distinction a reader has to learn and then discover is inert.
- **The calendar is binary: a day has a session or it does not, and nothing renders red.** One hue, one strength (`RECORDED_DAY_ALPHA`, capped so the day number stays legible on top of it), applied to every day inside `trackingStart..countedThrough` that has a summary. **Today takes its colour at check-out** and carries its marker alone until then; `today` stays a separate parameter from `countedThrough` because today is drawn as today either way, and the future is measured from it. This replaced a `DayIntensity.fractionOf(totalMs, peakMs)` ramp that drew each day at a strength proportional to its hours against the user's **all-time longest day**, and the reason it is gone is the ratchet: one nine-hour day permanently re-rendered every ordinary day behind it as a partial version of that one, and a forgotten check-out — auto-closed at midnight, on a row the app gives no way to edit — set that baseline for good. `DayIntensity`, `ConsistencyStats.peakDayMs` and the `dayColor(fraction)` overload were all deleted with it; **do not reintroduce any of them, or a normalizer of any other kind.** A day with no sessions is transparent. **The cell's `contentDescription` still states the hours** — not because colour is carrying them any more, but because a screen reader should still get the figure. **Only days *outside* the tracked window are faded** (`OUTSIDE_WINDOW_ALPHA`): the future, and the days before the user began. Fading the past instead is the mistake that treatment exists to avoid — a day drawn fainter for holding nothing is the verdict this calendar never renders. What it separates is "no record kept" from "in the record", and it is allowed to be colour-only because a date after today already reads as the future from the number itself.
- **Hours are a quantity with no direction, and every mechanism that gave them one has been deleted.** The test to apply to any displayed number: *is there a direction in which higher reads as better?* For hours the answer must be no — no ring fill, no colour ramp, no size that scales with them beyond a chart's own axis, no superlative, and above all no comparison against a figure the user previously achieved. For **presence** the answer may be yes: days shown up is the app's thesis, it is the hero of Reports, and it is fine that more is better. Note that **the app now draws no arc at all**: History's flattening left `CircularProgressRing` with one caller, the Check-In gauge, and 3.0 replaced that gauge's sweep with the brand lattice — so the ring was deleted rather than left standing with none. A new ring fill therefore has no precedent anywhere in the tree to point at, which is the strongest form this rule has taken. What was removed and must not return: the calendar's intensity ramp, the longest-day and best-streak rings, `statRatio`, the month and all-time averages as ring baselines, current and best streak as displayed figures (and as computations — nothing outside the UI ever consumed them), and the "Best day" superlative in a chart's screen-reader text. **The word "streak" appears in no user-facing string.** The argument is the same one that deleted the daily target, one level up: a target grades a day against a fixed bar, and a personal-best baseline grades it against the user's own best day, which is worse — it **ratchets**. Beat it once and every ordinary day behind it re-renders as a partial version of that one, and the baseline can be set by an accident: a session the user forgot to close is auto-closed at midnight onto a row nothing can edit, and it was silently the yardstick everything else was drawn against. Reports' stat table is the shape a figure with no natural denominator is allowed to take: hours per tracked day and sessions per day shown up are **rows**, never arcs, because the only denominator available to fill one against is the user's own all-time equivalent — a personal best under another name. What replaced the two removed charts is deliberately descriptive: a start-time split and a sessions-per-day split, both plain counts, both styled with three hues of equal weight rather than one hue at three strengths — because a ramp is exactly how a rank gets back in. There is no "best time to start" and no right number of blocks to break a day into.
- **Charts are hand-rolled, and the maths is separate from the drawing.** `ui/components/charts/ChartGeometry` is pure Kotlin (no Compose, no Android) and unit-tested for the degenerate cases that would otherwise divide by zero or draw off-canvas: empty series, all-zero series, a single point, values above the ceiling. The `Canvas` composables only translate its output into draws. There is no charting dependency — adding one would be the first third-party UI library in the project. **An all-zero window must read as a row of zeros, not as a chart that failed to draw**, and that is a real state: a 30-day window with no sessions in it is what a user who has stopped checking in sees. So `LineChart` insets its plot by a full stroke and draws inside that — a series pinned to the floor otherwise loses the outer half of its line to the canvas edge and reads as blank — and `BarChart` draws a `baselineColor` rule whether or not any bar has height, since a zero-height bar is skipped entirely (a rounded rect with no height renders as a stray lens shape). Both insets come out of the composable, not out of `ChartGeometry`, which still works in the plot box it is handed. Every chart takes a `contentDescription` that states its values, because a `Canvas` is otherwise invisible to a screen reader. **`DonutChart` bounds its centred `content` itself, and that is not a convenience.** The hole is round, so its full diameter is only available along the centre line; a caption bounded by the diameter still overhangs the arc at the top and bottom of its own height. The bound is the *inscribed square* (`ChartGeometry.INSCRIBED_SQUARE`, `hole × 0.707`), applied inside the composable — the two call sites previously disagreed, with History constraining to a square 72dp and Reports not constraining at all, so its caption ran out over the ring. That constant lives in `ChartGeometry` rather than in either drawing, because the Check-In gauge deliberately did *not* apply it — its 45sp clock is wider than the square and must not wrap, which is the same measurement that later moved the readout out of a hole altogether — and the bound therefore lives in `DonutChart` rather than at a call site. It is currently **dormant**: History's stat tiles were the last caller to pass `content`, and with History flattened every donut in the app leaves the hole empty. Keep the bound where it is rather than deleting it with the last caller — the next caption to go in a hole is exactly the case it exists for. Sizes live in `DonutChartDefaults` for the same reason: one stroke width, one diameter, stated once beside the reasoning that fixes them rather than as bare literals in the Composable. The diameter grows with `LocalDensity.fontScale` and caps, because the caption is `sp` while the ring would otherwise be fixed `dp` — past the cap the caption ellipsizes rather than being clipped mid-word.
- **Reports is the tab that derives, and one resolved window is what it derives over.** `ReportScope` is either a `Month` or `AllTime`, and `ReportScope.resolve(trackingStart, countedThrough)` turns it into the `ReportWindow` every figure, every chart and the CSV export read. **Two scope kinds and no more**, so each card has one rule per kind rather than a matrix of them — `Hours by Month` is the worked example: under a month there is one bar to draw, which is not a chart, so `monthlySeries` comes back empty and the card is not rendered. `resolve` clamps both ends and returning null is a real answer, rendered as an empty scope rather than a set of zeros — zeros would assert the user showed up on none of some number of days, a verdict on days the record does not cover. **The window is resolved in exactly one place, and that is the point of the type.** The screen and the export used to clamp separately with their own arithmetic, and the export is the half nobody re-reads. Note the mechanism: `CsvExporter.export` takes two plain `date_key` strings plus the summaries for that range, and knows nothing about scopes — the clamp is `ReportScope.resolve`, and the screen's state flow and the export path each call it against the same `scope`, so neither can invent its own arithmetic. The invariant is that the file and the screen it was exported from describe the same days; it holds because there is one clamp, not because `platform/` imports `ReportScope`. `ReportsViewModel` then combines `dailyAggregatesFlow` with `sessionStartsFlow` **over that window**; the **identical scoping is still the point**: the aggregates say which days count and the starts say when within them the work began, so a range that differed between the two would let the start-time split describe sessions the rest of the screen had excluded. The starts query exists because `DailyAggregate.firstCheckIn` is each day's *first* session, so a day worked in three blocks would contribute one start instead of three. `countedThrough` still comes from a **one-day** aggregate query — `summaries.containsKey(todayKey)` *is* the predicate — so the whole record is never read just to find where counting stops. The tab **opens on the current month**, not on all time. Both series are gap-filled: a day or month with no sessions is emitted as a real zero, since a hole in a line chart reads as missing data rather than an absence. Missed-day counts come from subtracting the days that *have* entries out of the window. The daily chart's dashed reference line is the window's own **mean**, not a target. Its screen-reader text names the window and stops — it used to end "Best day 8h 12m", which ranked one of the user's days against the others. **The daily series is capped only under all time** (`DAILY_WINDOW_DAYS`, 30): a month plots its own days, and a line with a point per day of a multi-year record is a solid block. **No card title may name a span** — `chart_split_title` was "All-Time Split" and said so while rendering one month the day the scope landed; the selector states which span is active and nothing else may.
- **The History calendar is sized from the viewport.** `CalendarGrid` owns the month's geometry — `startOffsetIn` and `weekRowsIn`, `internal` because the screen must size a cell *before* the grid is composed, and two derivations of the same row count is how a height comes to be computed for a different number of rows than the grid then draws. `CalendarGrid` takes a `cellHeight` that `HistoryScreen` derives inside a `BoxWithConstraints` from the **real** viewport — `maxHeight` less the chrome, the month selector, the weekday header and the day-detail slot that has to stay on screen beside it — divided by the month's actual row count (4–6, so the grid doesn't jump between months) and clamped to `48.dp..80.dp`. A cell is only ~53dp wide, so an uncapped height stretches it into a ribbon. Deriving it from `LocalConfiguration.screenHeightDp` instead is the bug this replaced: that is the whole physical screen, so it over-counted by the app bar and bottom nav and pushed the slot off the bottom. The `48.dp` floor deliberately wins over fitting — it is the minimum tap target, so a 6-row month on a small screen scrolls slightly rather than shrinking its days below it. `DETAIL_SLOT_HEIGHT` is a constant rather than a measurement because the grid has to be sized before the slot below it is laid out, so **it must be kept in step with `daySlotItems`** — 180.dp is sized to the tallest of its three states, which is the placeholder `EmptyState` (24dp padding at each end, a 48dp icon, a title and a two-line message) rather than a date over three ledger rows. Over-stating it wastes grid height, under-stating it pushes the slot off the bottom, and the two errors are not symmetric: the first is absorbed by the 48dp cell floor scrolling, the second clips the slot. `TEXT_CONTENT_HEIGHT` is deliberately generous for the same reason — the slot is text all the way down, so at a large font scale it grows without bound and the figure is set to err high.
- **History is flat: a calendar, and the sessions of whichever day you tap. It derives nothing, and that is the split with Reports.** The tab used to carry a month summary card — days shown up as a hero `CircularProgressRing` filled to `showedUpRatio(showedUp, trackedDaysInMonth)`, over two tiles ringed as frames for worked time per tracked day and sessions per day shown up. `MonthSummaryCard`, `MonthTiles`, `computeMonthTiles`, `showedUpRatio` and `HistoryUiState.trackedDaysInMonth` are all deleted. The reason is a division of labour rather than a defect in the card: **Reports is where derivation lives** — dense, accurate, rarely opened — and History is what a user reaches for to answer "what did I do on the 12th", which a ring cannot answer. Two tabs computing the same class of figure at two scopes is how they come to disagree. What is left is the calendar, and a slot below it holding the selected day's rows, drawn by the shared `SessionIntervalRow` so a session renders identically on whichever tab you meet it. The day's own total is printed above those rows and is the **sum of the rows themselves**, which is why it is computed in the composable rather than in the ViewModel: an arithmetic restatement of what is on screen cannot drift from it, whereas a second query could. Two consequences worth keeping. **The slot has three states, and the middle one is the point** — every cell in the grid is tappable, including an empty day and a future one, so "selected but holding nothing" needs its own message; falling back to something else there, as this screen did to the summary card, makes the tap read as though it did nothing. And **`showedUpRatio` was the app's last measuring ring fill**, leaving `CircularProgressRing` with one caller whose sweep was documented as motion rather than measurement; 3.0 replaced that caller's form too and deleted the ring — so nothing in the app fills an arc at all, which is the no-grading rule in its strongest form. Do not reintroduce a summary, an average or a ratio onto this tab; that work belongs on Reports, and the two averages that died with the card now live there as plain rows under whatever scope is selected.
- **Every check-out states what ended it, and `checkOutAt` has no default for it.** `ClosedBy` has four values — `IN_APP` (the Check-In screen's button), `TIMER_NOTIFICATION` and `REMINDER_NOTIFICATION` (the two notification actions, through the root gate), `DAY_BOUNDARY` (the midnight alarm) — and each has exactly one writer: `CheckInViewModel.executeCheckOut`, `MainActivity.onRootGatePassed` (which reads it off the `Reason`), and `SessionLifecycleRunner.onDayBoundaryFired`. **The parameter is deliberately un-defaulted.** Its predecessor was `autoClosed: Boolean = false`, which was harmless while there were two endings and one was the default, and is a wrong answer now that there are four: a new check-out path that says nothing would silently claim to be the default one. Without a default it does not compile. The `storedValue` strings are **frozen** — they are the CSV's cells and what any future migration would match on, and the DAO's `CASE WHEN` sums spell them out because an annotation cannot read an enum property. Two things this must not become. It is **not displayed anywhere**, and nothing may ever compare the values in front of the user: preferring one surface over another is a grade on how someone uses the app, which is the deleted daily target one level out. And it records what ended a session, never how the day went — see the no-Status-column half of the CSV entry. The reason it is worth carrying at all is `DAY_BOUNDARY`: that row's stop instant is a plausible time **nobody chose**, on a session the app gives no way to edit, and nothing else in the export distinguishes it from one the user made. The other three are the same question asked with the resolution the schema can now afford. There is no back-fill to reason about: the schema was collapsed to version 1 rather than migrated, so every row that exists was written by one of the four writers.
- **Only completed sessions aggregate** — every summary/total query filters `stopped_at IS NOT NULL`; an active session contributes nothing until check-out.
- **There is no mid-session presence check and no pause, and reintroducing either would be a regression.** The check verified the user was still there and *stopped their clock* when they didn't answer — so a question nobody saw silently deleted hours they had worked, on a row the app gives no way to edit. Nothing now subtracts from a session: `duration` is exactly `stopped_at - started_at`. Check-in and check-out remain gated; only the mid-session interrogation is gone, along with `paused_ms`, `pause_started_at`, `beginPause`/`resumeFromPause`, the retry/refusal ladders, the in-app Resume button and both Settings toggles.
- **An open session keeps two inexact alarms, and they do different jobs.** `SessionLifecycleRunner.arm` schedules both through `SessionAlarms`, and `SessionAlarmReceiver` handles each **itself** rather than waking the service — the alarms' whole purpose is to work when the service is gone, and starting a foreground service from a background broadcast would be refused in exactly that case.
  - The **reminder** fires every `SessionSchedule.REMINDER_INTERVAL_MS` (2h) and only asks: it posts "still checked in?" with a gated **Check Out** action, and ignoring it costs nothing at all. Only the first of a session alerts (`SessionAlarms.remindersSent`); the rest post silently so a session running overnight accumulates on the shade rather than buzzing every two hours. A **refused post** returns `Outcome.Refused` and re-arms **without advancing the count**, so restoring notifications means the first reminder the user can actually see still alerts — silence is not an answer.
  - The **day boundary** closes the session at local midnight, and it is the only thing that ends a forgotten one. **It stamps the session's own midnight, never the fire time** — the alarm is inexact and may land hours late, and stamping when it fired would hand a forgotten session hours on a day it does not belong to. The instant it uses is **the one that was armed** (`SessionAlarms.dayBoundaryAt`), with `dayBoundaryFor`/`SessionSchedule.dayBoundaryOf` as the fallback when nothing is stored — and that order is load-bearing rather than an optimisation. Recomputing unconditionally reads the device's **current** zone, while the alarm was armed from the zone at check-in, which is the zone the session's `date_key` names: a session that crossed a zone change in between would be stamped hours into the future travelling west, or hours short travelling east, and stamping short **silently deletes worked hours** from a row nothing can edit. `dayBoundaryOf` goes through the calendar rather than adding 24h, so a DST day still ends at midnight, and the result is clamped to now as a last guard, since a stop instant in the future is never right whatever produced it. An instant already past is otherwise left as-is: the platform delivers a past-due alarm immediately, which is what closes a session that outlived its boundary while the process was dead.
- **The day-boundary close is the one un-gated check-out in the app.** Every other path runs the presence gate. This one cannot: the point is to close a session the user has forgotten, and a forgotten session is precisely the one nobody is present to authenticate. It is safe in a way no other check-out is — it can only ever *end* a session, always follows a gated check-in, and writes an instant fixed by the calendar rather than by anything the caller chooses. The cost to accept: a session started at 23:50 closes ten minutes later.
- **Why inexact:** neither instant needs to be hit precisely — the reminder is a cadence, and the boundary stamps from `date_key` regardless of when it lands — while `SCHEDULE_EXACT_ALARM` is denied by default from Android 14 and `USE_EXACT_ALARM` is restricted by Play to alarm-clock apps. What *is* needed is the wake: `setAndAllowWhileIdle` fires through Doze. **Never `setAlarmClock`** — it is the only alarm API that shows a status-bar alarm icon and a lock-screen entry.
- **An open session with no service is a real state, and three callers fix it.** `START_STICKY` is best effort — a force stop, an OEM background-management kill or a crash all leave the process dead with the row still open — and nothing used to restart the service afterwards: it was started at check-in and nowhere else. Opening the app did not help either, because the Check-In screen renders from the row, so it showed a cheerfully running timer with nothing behind it. `SessionWatchdog.reviveIfNeeded` now runs from `MainActivity.onStart`, `SessionRestoreReceiver`, and the hourly `NudgeWorker` pass, in that order of reliability: **a visible Activity is always allowed to start a foreground service, `BOOT_COMPLETED` and `MY_PACKAGE_REPLACED` are exempt, and a worker may be refused outright.** A refusal is absorbed rather than thrown — there is nowhere left to report it, and the next caller retrying *is* the recovery — which is why there are three and not one. `ServiceController.revive` returns a `Boolean` for exactly this, and `reviveIfNeeded` catches everything: its callers are fire-and-forget `launch`es on a scope with no exception handler, so a throw would kill the process this exists to recover. **The revive is `ACTION_REVIVE`, never `ACTION_START`** — the check-in path takes its timing from the intent, which is right for a session that hasn't begun and wrong for one already running.
- **The service and the alarms are lost separately, so they are repaired separately.** `reviveIfNeeded` calls `SessionLifecycleRunner.ensureArmed` **before** it even looks at whether the service is running, and this ordering is the fix for a wrong premise the code used to state outright ("a killed process does not cancel alarms, so there is nothing to re-arm"). A plain process kill leaves alarms standing; **a force stop and a package replace cancel them**. Since `arm` was reachable only from `ACTION_START` and the boot receiver, an open session that survived an app update kept its timer and silently lost its day-boundary close — and that close is the only thing that ends a forgotten session, so it ran until the user noticed and then wrote a multi-day `duration` onto a row nothing can edit. `ensureArmed` is separate from `arm` because it must be safe to call on every app open: it re-arms **the instants already stored** (`next_reminder_at` / `day_boundary_at` in `checkin_timer_prefs`, since `AlarmManager` cannot be asked what is still set), never touches `remindersSent`, and re-derives a reminder only when its instant has already passed. Re-anchoring unconditionally would push the reminder past every repair, so a user who opens the app hourly would never get one. The **boundary is re-armed even when it is in the past** — the platform delivers a past-due alarm immediately, which is what closes a session that outlived its boundary while nothing was armed.
- **Whoever writes the row arms it.** `arm` is called from `CheckInViewModel.executeCheckIn` and `MainActivity.onRootGatePassed`, not from `CheckInService.handleStart` where it used to live. `ServiceController.startTimer` is documented to be refusable — a restricted standby bucket, an OEM that declines a `specialUse` foreground start — and neither writer inspects that `Boolean`, so arming inside the service meant a refused start silently produced a session with no alarms at all. Writing the row cannot be refused. Check-out cancels for the mirror-image reason: `ServiceController.stop()` is a caught no-op when the service is already dead, so leaving the cancel to `tearDown` stranded both alarms over a closed session.
- **`CheckInService.isRunning` tracks the notification, not the object.** It is set from a *successful* `startForeground` and cleared when that call throws (it is guarded — a background-start refusal or a foreground-type restriction must not kill a running session), on teardown, and in `onDestroy`. Setting it in `onCreate` instead is the bug this replaced: a caught `startForeground` failure left the instance alive with nothing on the shade, reporting itself healthy forever, and `SessionWatchdog` skipped the one state it exists to repair.
- **`serviceScope` carries a `SupervisorJob` *and* an exception handler, and it needs both — even though the handler's body is now empty.** A `CoroutineExceptionHandler` absorbs a failure; it does not contain one. Under a plain `Job()` the first uncaught throw in any `serviceScope.launch` cancels the scope permanently, and every later command — reconcile, arm — becomes a silent no-op for the life of the service. That is worse than the crash it replaces: the reconcile that would tear down an orphaned notification launches onto a dead scope, and nothing happens, then or ever. The throw sources are real (`getActiveSession` on SQLite, `setAndAllowWhileIdle` past the 500-alarm cap). **Do not delete the handler because it looks like dead code**: with no handler at all, an uncaught throw reaches the thread's default handler and kills the process this scope exists to keep alive. It used to write a `DEGRADED` row, which is why the `log*` helpers ran on `applicationScope` — that scope outlives `onDestroy`, and half of what was recorded happened as the service ended. Both helpers and the row are gone; nothing in the app reads a failure record, so there is nothing to give the handler to do.
- **Reboots and updates need their own handler.** `START_STICKY` survives neither, and neither do alarms, so `SessionRestoreReceiver` handles `BOOT_COMPLETED` **and** `MY_PACKAGE_REPLACED` — both are among the few contexts allowed to start a foreground service from the background. It no longer arms anything itself; it makes the same `reviveIfNeeded` call as every other caller, and that is what fixed the reboot resetting the alert ladder: `arm`'s leading `cancelAll()` cleared `remindersSent`, so the first reminder after a restart alerted at full volume in the small hours over a session left running on purpose. The hourly worker would eventually repair a package replace on its own (WorkManager reschedules itself across one), but it is deferrable and an update at 23:00 could miss midnight entirely.
- **There is no debug UI, and there is no `BuildConfig.DEBUG` branch anywhere in the app.** Settings once carried two debug-only cards: a diagnostics card (`DebugSnapshot`/`DebugSnapshotReader` — open session, service flag, both armed instants, `remindersSent`, per-channel deliverability, `warnings()` naming the wrong states, plus the event log and a **Copy report** button) and a nudge harness (force-send per variant, run a pass, clear the log). Both are deleted, along with the log's `recent`/`clear` and their DAO queries, `NudgeDispatcher.forceSend` and the `NudgeTrigger` seam that existed to keep the harness off a `Context`, and `AndroidNudgeAlarms.nextCheckpointAt`. The reason is that a debug surface is only worth its weight if someone actually reads it, and **this one was never wired to anything that runs** — a card the developer has to open on a debug build, on the one device it is installed on, at the moment a silent failure happens to be live. It reported nothing, so it caught nothing. The state it named is still worth naming, but the way to have it is real wiring (attach a trace to `Feedback.draft`, or one that genuinely ships) rather than a screen that must be visited on the off-chance. **That argument was then applied to the rows themselves.** Keeping the writes was justified as "cheap, and the record if a trace is ever wired up" — but a record nothing reads is not a record, and the same sentence that condemned the card condemns them. Every write-only row is deleted; see the two-databases entry. `NudgeDispatcher.runOnce` remains the **only** way a nudge is ever posted, so the copy a device shows is whatever eligibility produces — `NudgeDispatcherTest` pins that the posted spec carries the nudge's own id, channel and registered copy.
- **Three separate switches silence a notification, and the permission is only one of them.** A user can hold `POST_NOTIFICATIONS` and still have notifications off for the whole app, or set an individual channel to "None" — which is exactly what "I had everything enabled" turns out to mean. So `AndroidNotifier.canPost` checks all three (permission, `areNotificationsEnabled()`, channel importance, plus a missing channel, since a post to one that was never created is discarded) and a refused post is a real outcome every caller handles: `SessionLifecycleRunner` re-arms **without advancing `remindersSent`**, and `NudgeDispatcher` records no send in the ledger. **Settings no longer says any of this.** A `NotificationsCard` used to render there in every state — healthy, it named where the switches are; blocked, it distinguished *everything off* from *the timer channel muted* and said so, since a denied `POST_NOTIFICATIONS` silently takes out the running timer, the session reminder and every nudge while every screen looks normal. It is deleted along with `NotificationBlock` and its seven strings. What it argued for is still true, and if the blocked state ever needs surfacing again it should be surfaced **where the user is**, not filed in a Settings screen nobody opens with a working app: the Check-In screen already knows a session is running, and that is the screen where a missing timer notification is a question the user actually has. The one thing not to rebuild is a card whose healthy state is a paragraph about where Android keeps the switches.
- **A notification's opt-out is its channel, and nowhere else. This is the rule for every notification the app ever adds.** There is no in-app switch for the timer, the session reminder or the check-in reminders, and Settings now holds no notification surface at all — a long-press on any of them opens its channel, which is nearer than Settings ever was. Two reasons, and neither is taste. **First, an app pref is subordinate to the channel and so can only agree with it or lie.** `NotificationDelivery.canDeliver` already refuses a post to a blocked channel, so channel-off plus pref-on sends nothing while the UI reads "on" — the pref is the half that lies, and it is the half the user was looking at. Nudges carried exactly this: a master switch *and* a per-nudge row, which with the single `Nudge` the enum then held were the same switch twice, both collapsing to the same `emptySet()` and both outranked by the channel. **Second, an in-app opt-out is a one-way door.** Android has no API to block or lower a channel — an app can only create one — so a stored opt-out can never be migrated into the system, and deleting the toggle later silently re-enables the notification for everyone who had used it. That is why this shipped at ~0 installs: it is the only moment the migration is free. Consequences that follow. A **new** notification gets a **new channel**, and a nudge wanting independent control gets its own channel too — never a flag in prefs; `NudgeEligibility` decides *timing*, never *consent*. Channel **name and description are updatable** after creation and should carry the words a user hunting for the switch would search for (hence `nudge_channel_name` is "Check-In Reminders", not the internal "Encouragement"), while the **id and importance are frozen** — see the timer-channel entry. That name sits one row from "Session Reminders" and the two are near-synonyms to anyone outside this codebase, so the **descriptions** carry the difference: turning off the wrong one costs the prompt that catches a forgotten open session. And discoverability does not regress: a long-press on the notification shows its channel and turns it off in one tap, which is nearer than Settings ever was, and channel-level control satisfies Play's easy-opt-out requirement for promotional notifications.
- **Gated check-out from the notification.** The ongoing timer notification's "Check Out" action opens `MainActivity` with `LaunchExtras.CHECK_OUT_FROM_TIMER`, and the session reminder's with `LaunchExtras.CHECK_OUT_FROM_REMINDER` (not a silent `ACTION_STOP`), so it runs the root presence gate and checks out on success — check-out is **never** un-gated. `ServiceController.stop()` (`ACTION_STOP`) now only ends the service *after* a check-out has already been written.
- **`checkOutAt` exists for the day boundary, and `checkOut` delegates to it.** Both are read-modify-write over the row (matching the original `checkOut` pattern); the only difference is whether the stop instant is "now" or one the caller computed. Duration is floored at zero, because a stop before the start is a changed system clock or a corrupt row and a negative duration would poison every total that sums it. All three (`checkOut`, `checkOutAt`, `checkOutActiveSession`) **return the closed row**, so a caller that reports what was recorded reads the stored figure instead of subtracting again — a second subtraction at the call site is a second copy of the flooring rule, free to disagree with the row it describes.
- **The Check-In gauge is the current session, never the day's total — and that is why it carries no label.** It reads zero between sessions and counts up from zero at check-in, which is unambiguous by convention; a clock resuming from the day's accumulated total read as a *paused* stopwatch, implying the one mechanic the app deliberately deleted (see the no-pause gotcha), and left a user mid-session subtracting to answer "how long have I actually been sitting here". The day's volume is stated directly below by `TodaySessions`, whose header is **outside** the `AnimatedVisibility` and therefore always on screen, collapsed or not: `n sessions · Xh Ym today`, gap-free because it adds the open interval's live elapsed to the completed ones. That header is now the only place the day appears on this screen, which is why it is a centred, contained pill rather than a full-width row with a chevron — and why its **touch height is floored at 48.dp on the `Surface` while the visual padding is tighter**, since making a target look smaller must never make it smaller. A consequence worth keeping: the notification's chronometer counts from `started_at` and so now shows *the same figure the gauge does*; before this they disagreed by the day's completed total, and they could not be converged the other way, because a platform chronometer can only count from a fixed instant and a running day total would need the banned per-second service ticker.
- **The expanded session list is a ledger of two columns, and nothing in it ticks.** Each row is the clock range and what it came to — the range weighted, the amount column a fixed width, so the amounts stack into a column instead of ragging with the text. That width **scales with `fontScale` and caps** (`DURATION_COLUMN` to `DURATION_COLUMN_MAX`), because the column is `dp` while the text inside it is `sp`: the duration is `maxLines = 1` with no ellipsis, so at a raised font size a fixed column rendered "2h 15m" as "2h" — a wrong number on screen rather than a clipped one. Past the cap the *range* gives way instead, which it is built for; it ellipsizes and says so. **A third column was tried and removed, and the reason generalises**: each candidate only paraphrased a column already there. A word for where in the day it fell ("Morning", from a pure seven-bucket `SessionPeriod` mapping) restates the start time sitting immediately beside it, and an ordinal `#n` restates both the row order and the `n sessions` in the pill directly above. Labelling by *length* instead — a "quick one" against a "deep dive" — is worse than redundant: it grades the session, which nothing in this app may do. The open interval shows `ongoing` in place of an end time and a pulse (`OngoingPulse`) in place of a duration: a second live number beside the gauge is one the user has to reconcile with the one above it, and the gauge is where elapsed time is read. **The pulse is drawn, not an emoji** — a glyph varies by device font, ignores the theme colour and sits on its own baseline — and it holds still when `ANIMATOR_DURATION_SCALE` is 0, since an infinite animation ignoring "remove animations" is what that setting exists to stop. The day's total *does* still include the open interval, so the pill keeps counting while the rows do not; `ongoing` is what explains the difference. Each row carries one `clearAndSetSemantics` description, because read as separate nodes it arrives as fragments; an open row needs no join, since the range already ends in "ongoing" and the pulse speaks nothing. The row lives in `ui/components/SessionIntervalRow` rather than beside either screen, because History's selected day is the same ledger over a different day — a second copy is how the two would come to render a session differently depending on which tab you met it from. History's selected day prints a header rather than a pill — `n sessions · Xh Ym`, where the count is the rows on screen and the total is the sum of the durations those rows print, so the open row contributes to the first and not to the second. It needs no `ongoing` caveat for the total, because the row it omits is the row already showing `ongoing` instead of a figure. The consequence to know: **on today, History's total and the Check-In pill's differ by the open interval's elapsed time**, since the pill adds it live and History cannot without a ticker this list is forbidden.
- **The mark is drawn twice, and the second copy is deliberate.** `play-store-assets/generate_icons.py` owns the geometry and emits `pathData` for the launcher, splash and notification drawables; `ui/components/BrandGrid` restates the same four constants (3 cells a side, `FILL_FRAC` 0.88, `CORNER_FRAC` 0.22, and the two cells left out) in Compose. It is a copy rather than a shared source because a `pathData` string is a single flattened path — exactly the thing that cannot be addressed cell by cell — and addressing the cells is the whole reason the composable exists. **Change the constants in both or the marks drift**, which is the failure the adaptive icon and the splash already had once under two resource types of the same name. Nothing gates this: `verifyDocMap` checks filenames, not values.
- **The Check-In gauge is the brand lattice breathing, and it says one thing: whether a session is open.** A wave of brightness travels the seven filled cells once every three seconds (`waveLevel`, pure, `BrandGridTest`); with no session the grid sits at track alpha and is still. **No cell's place in the pass means anything, and that is why the shape is legal.** The first version of this lit one cell at a time and advanced it once an hour, which encoded how far into the hour the session was — a figure nothing was permitted to read, moving one step per 8.5 minutes and so invisible anyway: a positional encoding with no reader, at a speed with no viewer. A wave has no current cell to leak such a figure and none for a later reader to give a meaning to. **Nothing may accumulate here either**: a lattice lighting cell after cell until it is full is a completion bar, i.e. the deleted daily target as geometry, and it would additionally turn the mark's own two gaps into a shortfall rather than the honest part. Every cell traces the identical curve a beat apart — a wave whose cells differed in height or dwell would be a ranking of cells — and `BrandGridTest` pins that, the wrap, and that no two peak together. It is the idiom `OngoingPulse` already uses one file over for the same claim, so the two read as one statement at two sizes, and it honours the system animation scale for the same reason; with animations off the running state is every cell at full colour, flat but still unmistakably not the rest state, which is the property that has to survive. The description states the elapsed time and nothing about the mark. **Two constants tune it and they interact**: `WAVE_MS` (3s a pass, so the crest steps a cell every ~430ms) and `CREST_POWER` (2.0), which squares the raised cosine to contract the bright band from about three cells to two and put real dark behind it — a plain cosine reads as a swell where you see *that* something moves without seeing *what*, and the squared crest gives the pass a front and a tail so the running state is unmistakable in peripheral vision. Sharpening the crest makes the motion more insistent, so a faster pass and a narrower crest must not both be dialled up; `^2` at two seconds was too much. Note the ceiling on the pass as well as the floor — past roughly five seconds the cells drift far enough apart in phase to stop reading as one wave and start reading as seven cells fading independently, which is the impression the shape exists to create.
- **The readout sits below the mark, and the split is a fit-budget decision as much as a visual one.** It used to sit in the ring's hole, which bounded it: `ChartGeometry.INSCRIBED_SQUARE` is deliberately not applied there because a 45sp clock is wider than the square, so at a raised font scale the clock had the whole screen to spill into and nothing stopping it. Below the mark it simply has the room. The consequence for `CheckInScreen` is that **the gauge is two budget terms rather than one**: the mark's side (`COMPACT_MARK`/`MARK_MIN`/`MARK_MAX`, subtracted directly, and taken from a smaller fraction of the viewport than the old ring since it no longer contains the number) and the readout's height plus its gap (counted into `FIXED_CONTENT_HEIGHT`, with the readout's growth charged through `TEXT_CONTENT_HEIGHT` — it is the largest type on the screen and so the term that moves that figure most). One constant standing for both is what stops being true the moment the user raises their font size, because only one of the two grows.
- **The celebration's settle is the only motion the app spends anything on, and it plays once.** `BrandGrid(settle = true)` lands the seven cells in reading order over ~680ms, with the last one — the newest entry in the record — taking a small `EaseOutBack` overshoot while the rest simply arrive. That is the whole point of the treatment: what the user watches is the record gaining a cell, not a congratulation animating in, so it says the one thing the copy is allowed to say and stays silent about how long the session was. It is driven by **one `Animatable` cursor over a fixed schedule** rather than seven animations, so two cells cannot disagree about where in the sequence they are, and the schedule is the pure `cellProgress` that `BrandGridTest` pins. It honours `animationsEnabled` like the ongoing pulse, and there is nothing to retire — it rests where it lands and the surface still waits for a tap. **It must not warm with the duration**, which is the same rule the copy is under: an arrival that got livelier as the number grew is the deleted daily target returning as a congratulation threshold.
- **The check-out celebration is raised by both writers, and never by the day boundary.** `CheckOutSignal` is process-global for the same reason `PresenceCheckSignal` is: a check-out is written from `CheckInViewModel.executeCheckOut` **and** from `MainActivity.onRootGatePassed` (the notification's action, via the root gate), so state owned by the Check-In screen's ViewModel would simply not appear for the notification path. Both go through the one `raiseCheckOutCelebration` helper so they cannot drift, and it reads the day figures against the **closed session's own `date_key`** rather than today — a session belongs wholly to the day it began on, so one closed after midnight reports the day holding the work rather than the empty one it ended in. The day-boundary close reaches neither writer and so celebrates nothing, which is correct: it closes a session the user forgot, usually at midnight with the app dead, and praising them for the one check-out they did not make is the wrong message. **The copy must never grade.** It is identical in wording, emphasis and icon at twenty minutes and at nine hours; a message that warmed as the number grew would be the deleted daily target returning as a congratulation threshold. `CheckOutCelebration` renders *over* the nav host rather than replacing it, so the user's tab survives, and **nothing retires it on a timer** — a tap anywhere and the back gesture are the only ways out. It held for a 2.5s dwell before, which meant a countdown racing the reader, a dwell that restarted on rotation, and a second check-out inheriting whatever was left of the first one's; an explicit dismiss has none of those states. Waiting indefinitely is what makes a staleness stamp necessary, so `CheckOutSignal` carries one exactly as `PresenceCheckSignal` does: `raise` stamps, and `MainActivity.onStart` calls `expireIfStale` on both. The write and the raise complete on a scope that outlives the composition, so pressing Home in the instant after a check-out leaves the flow set with nobody to dismiss it, and the next launch would open on a full-screen congratulation for a session closed long ago. Its `EXPIRY_MS` is **2 minutes against the gate's 10**, and the gap is the point — the gate is waiting on a legitimate round trip out of the app (system settings and back), while this is a reaction to something the user just did and nothing about it survives the moment.
- **The Check-In screen is a fixed, non-scrolling layout — keep it that way.** The gauge and the primary button must both be reachable in one viewport and one thumb reach, so the screen is a weighted `Column`, not a `LazyColumn`, and the day's sessions collapse behind a tap. A weighted `Column` *clips* rather than scrolls when content outgrows the viewport, so `BoxWithConstraints` picks a compact scrolling branch below `560.dp` of height (landscape, very small phones, large font scales) and sizes the gauge from the available height. **A `Column` measures its non-weighted children in declaration order**, so anything declared above the button claims space before it and can coerce it to zero height — which is why the expanded session list is capped at what's left after the chrome, the gauge and the 64.dp action, and why the screen falls back to scrolling when that remainder is too small to be worth showing. `FIXED_CONTENT_HEIGHT` is a hand-derived estimate of that non-list chrome, so **anything that changes the collapsed sessions pill's height has to move it too** — it is 168.dp because the pill's touch target is floored at 48.dp. Adding anything to this screen means re-checking that it still fits — and note the scrolling branch cannot host a `LazyColumn` (it would be measured with unbounded height and crash), which is why the expanded session list has two renderings.
- **The Check-In screen colours the action, never the outcome.** The primary button is a start/stop control: `startActionColors()` (green) to check in or resume, `stopActionColors()` (red) to check out, animated across the switch so it reads as one control changing state. Both come from `ui/theme/Color.kt`; green is the same hue the calendar draws a recorded day in, and each container/label pair clears WCAG AA. Red there is the stop half of start/stop, **not** `colorScheme.error` and not a verdict — no day is ever drawn in it. The screen exists to invite the next check-in, not to grade the user.
- **One 1-second ticker, on screen only.** The Check-In screen runs a composition-scoped `LaunchedEffect` that ticks the on-screen elapsed time while that screen is visible. The service has **no** ticker: its notification uses `setUsesChronometer(true)` + `setWhen(started_at)`, so the platform draws the running clock from a single post and keeps counting correctly through deep sleep. Both share the same origin — the DB row's `started_at`, passed to the service via `EXTRA_START_TIME` — and both now measure the same thing (the open session, not the day), so they agree rather than drifting by the check-in→service-start latency or by the day's completed total. **Do not reintroduce a service-side ticker.** The old one re-issued `startForeground` every second, which over a 16-hour session was ~57,000 main-thread binder calls into system_server, ~57,000 unguarded chances to throw inside a scope with no exception handler, and the behavioural signature OEM background management kills apps for — while still freezing in deep sleep, because a coroutine `delay` is scheduled on uptime and uptime stops when the CPU does. The chronometer costs one post and has none of those properties. Note the body copy must **not** also print the elapsed time while running (`notification_running`, not a formatted duration): the chronometer renders in the timestamp slot, so printing it twice shows it twice, and the printed one would be frozen.
- **Midnight attribution:** a session belongs wholly to its check-in `date_key`, even if it ends the next day (immutable single row). Asserted in `CheckInRepositoryTest`.
- **CSV export** writes to `cacheDir/exports/` and shares via `FileProvider`; it fills gap days with zeros. **The column order is append-only** — people script against this file, so a column is never renamed, retyped or moved, and `csvHeader()`/`csvRow()` live in `platform/CsvFormat.kt`, top-level and pure precisely so a JVM test can pin them (`DefaultCsvExporter` needs a `Context` and cannot be tested) — and the exporter writes its header through `csvHeader()` rather than reading the constant, so the bytes the test pins are the bytes the file gets. The last four columns say **what ended** each of the day's sessions — `Day Boundary Check Outs`, `In App Check Outs`, `Timer Notification Check Outs`, `Reminder Notification Check Outs`, one per `ClosedBy` value and each named for the value it counts, summing to `Session Count`; the first is written by `SessionLifecycleRunner.onDayBoundaryFired` alone. A fifth ending means a tenth column on the end rather than a re-cut of these. They are per-*day* counts because these rows are days, and they are **not** the Status column returning: they record what happened to a session, not how the day went — and **nothing user-facing may ever compare them**, since "you mostly check out from the notification" grades how a person uses the app. There is deliberately **no Status column** — it carried the old PRESENT/HALF_DAY_LEAVE/FULL_DAY_LEAVE verdict, and inventing replacement wording would smuggle the same judgement into the one artifact that leaves the device; zero hours and zero sessions already say a day held nothing. **The range is the active scope's window, resolved by `ReportScope.resolve` — the same call the screen reads**, so the file and the screen it was exported from cannot describe different days. The old This month / All time button pair is gone with the `ExportRange` enum; one button follows the selector, which also makes an **arbitrary past month exportable**, something the pair could not express. **The window is clamped at both ends and the gap-filling is exactly why** — unclamped, the late end writes every remaining day of the month out as an empty recorded day including dates that have not happened, and the early end does the same for days before the user had ever opened the app. Both ends therefore **include today once it has been checked out of** and stop at yesterday while it is still in progress, through the same `ConsistencyStats.countedThrough` the screens use (fed by a one-day aggregate query, since the export path holds no summaries map) — a file that stopped short of a day the screen was already counting would contradict the screen it was exported from, and one whose last row was an empty today would assert an absence that is merely a day still being worked. The cost accepted is that an export is a snapshot: check in again after exporting and the file is stale. **A range holding no completed day returns `ExportResult.Nothing`** (a distinct outcome, *not* a `Failure` — nothing went wrong) and writes no file. That test is on the *query result*, not just on an inverted range: a week of abandoned check-ins gives a perfectly well-formed range whose CSV would be pure gap-fill. `ReportsViewModelTest` pins each case.
- **One drawable is the launcher icon, the splash icon and the themed icon.** `drawable/ic_launcher_foreground.xml` is referenced by the adaptive icon *and*, through `drawable/ic_splash_icon.xml`, by `windowSplashScreenAnimatedIcon` in `themes.xml`, so they cannot drift. **`ic_splash_icon` is an `<inset>` and holds no geometry** — it is the same foreground at `-15%` a side, which *expands* rather than pads (scale 1.30). The splash wants its own size and only its own size: the launcher foreground is deliberately sized against the 72dp window a launcher shows, leaving room inside the 66dp safe circle so it doesn't read oversized beside other icons, whereas the splash has no neighbours and the mark was filling about two thirds of the 192dp circle Android's guidance gives it. The inset is a **fraction**, so it resolves against whatever icon bounds the platform hands it rather than assuming 288dp. Do not fix a splash-size complaint by scaling the mark itself — that changes the launcher icon and the notification silhouette with it. They did before: the adaptive icon pointed at `@mipmap/ic_launcher_foreground` (a raster) while the splash pointed at `@drawable/ic_launcher_foreground` (a different vector) — same name, different resource type, two different logos, and nothing flagged it. Keep both pointing at the one drawable. The old raster was also a *baked, pre-masked* icon used as a foreground layer, which hid the background entirely and got clipped by launcher masks; the layers are now genuinely separate (flat indigo background, transparent stroke-only foreground). The mark is stroked **butt-capped and mitre-joined** (`strokeMiterLimit` 4, the platform default), not round: the ring's opening reads as a deliberate cut and the check comes to a point, which is what the splash's full-screen size exposes. That mitre is now the widest part of the mark, so `verify()` measures the safe circle against the stroked *outline* rather than padding each on-curve point by half the stroke — extent 24.46 of 33. The `<monochrome>` layer for Android 13+ themed icons points at that same foreground rather than copying its path — a second copy is precisely how the two marks drifted last time. Density-specific `mipmap-*/ic_launcher*.webp` files are **deliberately absent**: at minSdk 33 `mipmap-anydpi` always wins, so they were unreachable weight. That folder carries **no `-v26` qualifier**, also because of minSdk 33: adaptive icons need API 26, every device the app installs on is past it, and the version suffix only made lint ask why it was there.
- **The app's own code makes no network calls, every outbound link is an implicit intent, and the merged manifest holds no `INTERNET` permission.** `AndroidManifest.xml` declares six permissions and networking is not among them (`RECEIVE_BOOT_COMPLETED` is declared by the app itself, for `SessionRestoreReceiver`; there is deliberately **no** exact-alarm permission — see the session-alarm entries above); the **merged** release manifest adds four more and no network permission among them — `ACCESS_NETWORK_STATE` and `WAKE_LOCK` from `androidx.work`, `USE_FINGERPRINT` from `androidx.biometric` (deprecated at API 28 and dead weight at minSdk 33, but the library declares it unconditionally and it is auto-granted, so it costs a line in the Play permission list and nothing else), and an app-scoped `${applicationId}.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` that `androidx.core` defines and holds itself. Check `app/build/outputs/logs/manifest-merger-release-report.txt`, and grep it for `uses-permission` rather than running `strings` over the merged manifest — the latter also matches `android:permission` attributes on components (`androidx.work`'s `DUMP` and `BIND_JOB_SERVICE`), which are access controls on what the app exposes, not permissions the app requests. **`INTERNET` is not in the merged manifest at all**, so "the app holds no internet permission" is now true and checkable, and it is a claim worth protecting: it was false until the ML Kit stack left, because `transport-backend-cct` came with it and declared `INTERNET`. Any dependency that reintroduces that artifact takes the claim down with it, so the listing copy and the privacy policy both have to be re-checked if one does. `ACCESS_NETWORK_STATE` reads connectivity state and grants no network access; do not describe it as if it did, in either direction. `ui/about/ExternalLinks` is the one place app code reaches outside: the browser fetches the privacy policy, the mail app sends feedback (`ACTION_SENDTO` + `mailto:`, so it resolves to mail apps only — `ACTION_SEND` would offer every share target), and the Play app handles the rating. Adding a network call anywhere means a new Data Safety declaration — the reason the feedback path is an email the user reads and edits before sending, not a silent POST. Each launcher returns `false` instead of throwing so callers fall back to the clipboard; both `ActivityNotFoundException` (no browser, no mail app) and `SecurityException` (a handler in another profile) are real outcomes, so both are caught.
- **The open-source licence list is hand-maintained, and it is grouped on purpose.** The release runtime classpath resolves to 52 group ids that collapse into the upstream projects in `ui/about/OpenSourceLibraries`. **The list is the classpath, not the dependency block** — regenerate it with `./gradlew :app:dependencies --configuration releaseRuntimeClasspath` and group by Maven group id. Listing only the direct dependencies is the bug this replaced: `org.jetbrains:annotations`, `org.jspecify`, Guava's `listenablefuture` and AutoValue's annotations are all redistributed in the APK without appearing in the dependency block. Grouping is only sound because the licence is uniform *within* a group, which is why `androidx.camera` carries BSD alongside Apache-2.0 for the libyuv `camera-core` embeds — don't fold that into a plain Apache row. **Every entry is now Apache-2.0, the OFL, or CameraX's embedded BSD — no proprietary terms remain**, and that is a consequence of presence detection moving to the camera HAL: the ML Kit stack took `com.google.android.gms`, `com.google.android.odml`, `com.google.android.datatransport` and `com.google.firebase` off the classpath with it, and with them the `ML_KIT_TERMS` and `ANDROID_SDK_TERMS` enum values, which were the only non-open-source terms the app ever redistributed. `OpenSourceLibrariesTest` pins their absence, so re-adding any of that stack fails a test rather than quietly reintroducing proprietary terms into a screen headed "Open source licences". `OpenSourceLibrariesTest` guards the list's shape and asserts those non-Apache groups stay non-Apache, but it cannot see the Gradle graph — that half is **`./gradlew :app:verifyLicenseCoverage`**, which resolves `releaseRuntimeClasspath` and fails naming any group id no entry's `coordinates` covers — **and, since it only ever failed in that one direction, fails on the reverse too: an entry covering nothing the app ships.** That is not a licence risk, but it is a false statement in the one screen whose whole job is to be accurate about what the APK redistributes, and nothing else would ever catch it: `javax.inject` sat in the list for months after the ML Kit removal took it off the classpath. It also checks `res/font/`, because a typeface is redistributed exactly like a dependency but has no Maven coordinate — those entries carry `coordinates = "font:<resource name>"` (with a `font:family_*` wildcard covering a family's weight cuts) and are matched against `res/font/` instead, or a font dropped in would ship unattributed and pass silently. Only files aapt would package as a font count (`.ttf/.otf/.ttc/.xml`) — an unfiltered listing fails the build naming a `.DS_Store` a Finder visit left behind. It runs in CI (with the tests, not with `staticAnalysis`, which is kept free of dependency resolution) and hangs off `check`, and it declares an output stamp so it is UP-TO-DATE when neither the list nor `res/font/` changed: a task with inputs but no outputs can never be skipped, and this one resolves the whole release classpath. It parses the `coordinates = "…"` lines out of the source file, so it fails loudly if that format ever changes rather than passing on an empty parse. What it deliberately does **not** do is generate the list: a POM-reading generator produces ~220 flat rows and loses both the grouping and the hand-written notes, so drift detection is automated and the wording stays human. Licence text ships in `res/raw` rather than being linked wherever the terms oblige a copy — `apache_2_0.txt` for the code, `ofl_1_1.txt` for the typefaces — because an offline device could not otherwise read it. Which licences get that treatment is `LibraryLicense.bundled`, and the Licenses screen **loops over that flag** rather than hardcoding a block per licence; the raw-resource mapping lives in `LicensesScreen` so the enum stays plain Kotlin the unit tests can read. Each toggle names its licence, since these buttons sit below every card with no other context, and the paragraphs stay individual `items` of the `LazyColumn` — a single `Text` holding 11 KB measures all of it on the frame it appears, which is long enough to see.
- **One description of a notification, one place that builds it, one place that posts it.** All three — the ongoing timer, the session reminder and every nudge — are declared as a `NotificationSpec` and built by `NotificationFactory`; `Notifier.show()` then adds the `POST_NOTIFICATIONS` guard and posts. Building and posting are **separate** because `startForeground` needs the `Notification` object in hand and must succeed with or without the permission, so the timer goes `factory.build(...)` → `startForeground` while everything else goes through the guarded `notifier.show(...)`. **That applies to every re-post of the timer too, not just the first** — re-issuing `startForeground` updates the notification in place and is exempt from the permission, whereas routing a refresh through `notifier.show` would drop it the moment `POST_NOTIFICATIONS` is revoked while the notification itself stayed on the shade. Hand-building a notification anywhere else re-opens the bug this closed: the mid-session check used to bypass the guard, so a revoked permission meant a `SHOWN` logged for a notification nobody saw. Ids live in `NotificationIds` (service) and on `Nudge.notificationId` (one per nudge, **never reused** — a shared id makes a second nudge silently replace the first, and an ordinal-derived one reshuffles when the enum's priority order changes). A retired id for pre-per-id nudges was carried here for a while and is gone — at ~0 installs there was nothing left in any tray to retire, so it was cancelling an id nothing had ever posted under. **`PendingIntent` request codes are a namespace shared with previously installed versions**, which now spans three bands — notifications (`CONTENT_REQUEST_BASE` 1_000 / `ACTION_REQUEST_BASE` 10_000), the session alarms (20_000, 20_001) and the nudge checkpoint (20_010) —, and equality ignores extras, so `NotificationFactory` offsets them (`CONTENT_REQUEST_BASE`/`ACTION_REQUEST_BASE`) rather than using the bare notification id — the old build's reminder content intent was request code 1, which is now the timer's id, and `FLAG_UPDATE_CURRENT` would rewrite a still-posted notification's tap target across the update.
- **A refused post is not an ignored reminder.** When `notifier.show` is false — a revoked permission, notifications off app-wide, or the reminder channel blocked — `SessionLifecycleRunner` re-arms **without advancing `remindersSent`**, so restoring the permission resumes the reminders and the first one the user can actually see still alerts rather than arriving silently mid-ladder. The behaviour this descends from marked the check spent on a refusal and never asked again for the rest of the session, so a revoked permission silently disabled the whole mechanism until the next check-in.
- **"Refused" means three things, and the permission is only one of them.** `NotificationDelivery.canDeliver` — pure, and separate from `AndroidNotifier` because that class is Android-only, so on a JVM-only suite the decision every caller trusts would otherwise be the one part of the path nothing exercises. It refuses when `POST_NOTIFICATIONS` is revoked, when notifications are switched off app-wide, **or when that one channel is blocked while the rest stay on**. The platform reports none of the three: `NotificationManager.notify` drops the post and returns normally. A missing channel counts as undeliverable too — from Android 8 a post to a channel that was never created is discarded, and `ensureAll` runs at startup, so a null means something is already wrong.
- **There is no conversion attribution, and rebuilding it means building a reader first.** A nudge showing was once credited with a check-in that followed within 4h, with `AttributionRules.canCredit` refusing credit when the nudge had been swiped away, and `EngagementTag` riding both the tap and the delete intent so an open landed against the notification actually tapped. It was careful, it erred deliberately against the app, and **nothing ever read the number** — the rate it computed was written to a table no screen displayed, no export included and no network call could send. It is all deleted. If nudge effectiveness ever needs measuring, the reader is the part to build first: a metric with no consumer is what this replaced.
- **Nothing is `autoCancel`, so the app decides when a notification leaves the tray.** `NotificationFactory` always sets `setAutoCancel(false)`, and whoever handles a tap cancels explicitly — `PostedNudges.retireAll` for a nudge, the service for the reminder. That keeps each notification's cancel in one place instead of splitting it between the platform and the handler. The original reason was sharper and is gone with the analytics: the platform can deliver a delete intent when an auto-cancel *tap* removes a notification, indistinguishable from a swipe, so `autoCancel(false)` was what made everything reaching `NotificationDismissReceiver` a genuine dismissal. **No delete intent is set any more and that receiver is deleted** — a swipe is now simply a swipe, unrecorded. The session reminder is cancelled when the day boundary closes the session, and otherwise replaced in place by the next one under the same id.
- **The timer channel is `IMPORTANCE_DEFAULT`, and that buys placement rather than noise.** Below `DEFAULT` the shade files a notification into the collapsed *Silent notifications* group — and the timer carries a deliberately **stale** `when`, since the chronometer needs it pinned to `started_at`, so it sinks further the longer the session runs. The failure that closes: a user picking their phone up after a call and a dozen messages has no way to know a session is open, does not check out, and the day boundary then records hours nobody worked onto a row nothing can edit. It stays silent regardless — `setSound(null, null)` on the channel, `setSilent(true)` on the spec, and heads-up needs `IMPORTANCE_HIGH`. **Importance is frozen after creation just as the id is, and far more quietly**: it is applied only at creation, so a changed value is ignored on any install that already has the channel, and revising it for everyone means a new id, resetting every per-channel choice. It follows that **a device running an earlier build keeps the old importance until the app is uninstalled** — the first thing to check when this looks inert. The engagement channel is the worked example: it needed to become `IMPORTANCE_HIGH` so a once-or-twice-a-day message peeks instead of landing in a shade nobody reads for hours, and the only way to make that land on an existing install was a new id, with `deleteNotificationChannel` on the old one so it does not linger in the user's settings. It has since been renamed once more, to `nudge_channel`, when the package it belongs to stopped being called engagement — so `RETIRED_NUDGE_CHANNELS` now carries two ids. Both changes cost every per-channel choice made against the old channel and were free only because they happened before an install base. **A fourth id would not be**, and since importance can only ever be revised by minting one, that is the constraint to plan around rather than rediscover.
- **The timer notification survives Clear all but not a deliberate swipe, and that is why nothing re-posts it.** From Android 14 the platform allows a foreground-service notification to be swiped away **even with `setOngoing(true)`**, which the app sets. Verified on device: **Clear all leaves it alone**. On Android 13 — reachable since minSdk dropped to 33 — `setOngoing(true)` still makes it undismissible outright, so that install has strictly more coverage than the reasoning below assumes, never less; the same is true of the `specialUse` foreground-service type, which is declared in the manifest but enforced only from 34 and simply ignored on 13, so the accidental path is closed and every dismissal is an individual swipe by someone who just read "session running" beside a Check Out action. Re-posting after that — on unlock, on a ticker, on any cadence — would override a decision made with full information, so the app does none of it. Coverage without it: dismissal inside the first ~2h still meets the session reminder's **first** fire, which is the audible one (`silent = count > 1`) and stays audible even if an earlier post was refused, since a refusal re-arms without advancing the count; dismissal after that meets only silent reminders on the shade; and the day boundary closes the session in every case. The lever if this ever proves too quiet is that one predicate in `SessionLifecycleRunner.onReminderFired`, **not** a shorter interval — more frequent silent reminders achieve nothing.
- **Notification icons are the brand mark, not platform stock.** `ic_stat_checkin` (a 24dp silhouette from the same geometry) is the small icon for the timer, the reminder and every nudge; `ic_stat_check_out` matches `Icons.AutoMirrored.Filled.Logout`, which the UI already uses for that action. Status-bar icons keep only their alpha channel, so they must stay white-on-transparent.

## Conventions

- Kotlin official code style; Composables PascalCase. `./gradlew ktlintFormat` is the arbiter — don't hand-format against it.
- **Time arithmetic goes through named unit constants, never inline `60 * 60 * 1000`.** `util/TimeFormat` declares the millis/seconds/minutes/hours ladder for formatting; `platform/CsvFormat`, `TimerGauge` and `ReportsScreen` each carry their own `MILLIS_PER_HOUR` because they convert rather than format — three copies, one per file that turns a duration into a number rather than into text. Detekt's `MagicNumber` enforces this outside Composables, where dp/sp/alpha literals are exempt.
- **`ui/components/` is what a *second* screen would otherwise copy, not merely what a screen could reuse.** The rule is the reason for the move, not a usage count: something lands here when a second caller would have reinvented it wrongly (`ActionRow`'s 48dp tap target, `SessionIntervalRow`'s column-sacrifice order, `FullScreenMessage`'s spacing) or when a rule must hold in one place to be true at all (`AnimationsEnabled`). Members with a single calling screen are therefore normal and not drift — `ChartCard` is called only from Reports (seven times) and `ActionRow` only from `AboutCard`. What does *not* belong here is a composable private to one screen's layout: History's viewport sizing and Reports' cards stay in their screens. `SessionIntervalRow` is the one `internal` member, because it takes a Room entity; that is a hint about coupling, not a second tier.
- Each screen observes **one** `uiState: StateFlow<XUiState>` via `collectAsStateWithLifecycle`; VMs are constructor-injected from `AppContainer` through a `viewModelFactory`. Add a `LifecycleResumeEffect { onResumed() }` so the date window is recomputed on return to a screen; the day-rollover is handled reactively by `TimeSource.currentDay()`, not gated on the resume. **That tick is deduped in `dayTrigger` and must stay so.** Every ViewModel feeds it into a `flatMapLatest` that builds the screen's whole graph of Room flows, so an emission closes every one of those subscriptions and opens fresh ones — and an emission per resume did that on the return from the device-credential prompt, which lands as the check-in it authorised is committing. Room dispatches the invalidation while the observers are being swapped, the detached ones receive it, and their replacements go on serving the pre-write query they opened with: the Check-In screen then shows a green Check In button and `0m 0s` over a session that is open, until something resumes it again. Both halves of the fix are load-bearing — the dedupe closes that window, and `maxOf(day, today())` is what still makes the tick worth having, since `currentDay()` sleeps until midnight on a `delay` that does not advance in deep sleep, so re-emitting its own possibly-stale value (what a plain `combine` passes on) never moved the window the tick exists to move. `DayTriggerTest` pins all three cases. Nothing inside those graphs is read non-reactively — no prefs, no snapshots — which is why deduping costs nothing.
- All DAO/repository DB operations are `suspend` (or return `Flow`); Room via **KSP**.
- The day hue comes from `ui/theme/dayColor()` (light/dark tuned) — never hardcode it in screens, and never introduce a second colour to mean a worse day. **There is one strength and no fraction overload**: an alpha derived from a duration is an intensity ramp, and a ramp ranks the days. A caller drawing it behind text applies a fixed alpha of its own.
- **Dates the user reads are formatted in `util/TimeFormat` and nowhere else.** `dateWithYear` ("Jul 25, 2026") for a date read in isolation; `dateKeyWithWeekday` ("Saturday, Jul 25") for the nullable ISO `date_key` the screens hold, where the surroundings already supply the year and the weekday earns the space instead — it returns null rather than throwing on a malformed one, and the `LocalDate` overload behind it is **private**, because a screen holds a `date_key` and never a `LocalDate`, so keeping the parse out of the composables is the whole point. Both patterns are the same abbreviated-month family, so a date is recognisably a date wherever it appears. Scattering them across call sites is the bug this replaced: Reports printed a raw `LocalDate.toString()` ("2026-07-25") and History printed a raw `date_key` under "Sessions on". A month heading a user reads in full goes through `monthYear` — the History month selector and the Reports scope label show the same heading, and built inline in each they were free to disagree. Chart axes go through the same file — `axisDay` and `axisMonth`, the latter taking a `multiYear` flag asked once per series rather than per label, because a bare "MMM" is a lie the moment the record holds two Augusts and the all-time scope draws exactly that series. Both were bare `DateTimeFormatter`s in `ReportsScreen` until Reports gained a scope long enough to expose it. **`date_key` itself stays ISO** — `CheckInSessionDao` range queries depend on its lexicographic ordering, and the CSV `Date` column is machine-read; only the display side goes through `TimeFormat`.
- Duration/clock formatting goes through `util/TimeFormat` — do not re-implement it. `durationLive` ("0m 0s" → "59m 59s" → "1h 0m") is for a *ticking* clock only, which is now the Check-In gauge alone — the open interval deliberately shows a pulse rather than a second live figure; everything settled (totals, reports, CSV, past sessions) uses `durationShort`, where seconds would be noise.
- **Two bundled typefaces, split by reading size** (`ui/theme/Type.kt`): **Outfit** on display/headline/title, **Manrope** on body/label. The split follows from their x-heights (0.460 em vs 0.540) — Outfit reads as elegant on the 45sp gauge and thin in a 12sp row, Manrope the reverse; swapping them is the mistake the arrangement exists to prevent. Each weight is a **static instance cut from the upstream variable font**, four per family. The variable files would be 331 KB smaller, but selecting a weight out of one needs `FontVariation.Settings`, which is `@ExperimentalTextApi` — and without pinning the axis the file loads at its default instance and the platform fakes the heavier weights by smearing glyphs. Real cuts buy a stable API and genuine weights; **don't "optimise" this back to two variable files without reintroducing that opt-in.** Only `fontFamily` is overridden — every M3 size, line height and letter spacing is untouched. **`TextStyle.tabularFigures()` on the ticking clock is load-bearing, not polish:** Outfit's default `1` is 321 units against `0` at 659, a 2.05x spread that makes the gauge lurch sideways once a second without `tnum`. Both families resolve the feature to uniform widths (Outfit 590, Manrope 1240), and instancing preserves it along with the embedded copyright notice — check both if the cuts are ever regenerated. Bundling costs 608 KB of resources and means the app no longer honours a device font *choice* — font *scale* is still honoured, everything stays in `sp`.
- **String casing follows the header comment in `strings.xml`.** Section and card titles are Title Case ("The Numbers", "Days Split"), and so are **notification channel names** — Android renders all three as the titles of one list, where a lone sentence-case entry reads as an oversight; everything read as a line rather than a heading — row labels, buttons, help text, empty states — is sentence case ("Grant access", "Showed up"). The only exceptions are the product name CheckIn and the "Check In"/"Check Out" actions it is named after. The Reports stat rows are the drift this rule was written from: they were Title Case with a sentence-case parenthetical bolted on ("Current Streak (target met)") while every Settings and About row beside them was sentence case.
- **A count the user reads goes through a `<plurals>`, including in a `contentDescription`.** "1 days showed up" is reachable on a first tracked month and in a one-day export window, and a screen reader states it out loud. Where a string carries **more than one** count (`cd_days_split` two, `cd_start_time_split` three, `cd_sessions_per_day_split` three plus a mean), no one of them can be the plural's own quantity, so each count is worded through its own plural first — `days_count` or `sessions_count`, whichever the figure counts — and the sentence takes them as `%s` — that is the shape to copy rather than picking one count to inflect and leaving the other bare.
- Material 3 with a **fixed brand color scheme** (indigo seed, `ui/theme/Theme.kt`) — dynamic color is intentionally not used — plus system dark mode and a branded splash. Large screens are width-capped (`ui/components/ConstrainedContent`) and History goes two-pane on expanded widths (`WindowSizeClass`).
- **The brand mark is generated, not drawn.** `play-store-assets/generate_icons.py` owns the geometry and emits the `pathData` for `drawable/ic_launcher_foreground.xml` and `ic_stat_checkin.xml`, plus the 512px Play icon — change it there and paste the printed paths back, never hand-edit a path. Its `verify()` asserts the adaptive-icon safe circle on every run, measured off the stroked outline. The Play raster is stroked by hand (`stroke_polygons`) because **Pillow has neither line-cap nor line-join control**, and the raster has to be the same shape as the vector the app ships — one quad per segment plus a mitre wedge per join, matching `strokeLineCap="butt"`/`strokeLineJoin="miter"`. Two things there are load-bearing: `MITER_LIMIT` must equal the drawables' `strokeMiterLimit`, or the two disagree at exactly the corner the eye lands on; and each polygon's boundary is redrawn over its fill (`SEAM_PAD`), because Pillow's polygon fill drops boundary pixels and leaves pinholes at shallow junctions that the downsample smears into a faint seam along the ring.
