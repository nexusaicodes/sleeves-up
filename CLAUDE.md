# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A native Android check-in/check-out tracker built around **showing up**, not around hours cleared. It records auth-gated check-in/out intervals, shows what each day held, and counts consecutive days shown up for. The app is branded **CheckIn**.

**Rules:**
- Net time = sum of all completed check-in/out intervals per day (open intervals between check-ins are excluded). Nothing is ever subtracted from an interval
- Every day counts (7 days/week — no weekends/holidays exemption)
- **A day counts because it has a session, not because its hours cleared a bar.** There is no target, no half-day tier, and no leave deficit. A 45-minute day counts as a day shown up for exactly as much as a nine-hour one — see the gotcha below before adding any threshold back
- Hours stay fully visible everywhere (totals, charts, calendar shading, CSV); they are a quantity, never a grade
- **Sessions are immutable** — no edit/delete/manual entry by design
- Every check-in AND check-out is gated by a presence check: an on-device ML Kit face detection (offline), with **device biometric** as a fallback after repeated face failures
- Self-contained: Room-only persistence, no backend; CSV export via share sheet

## Build Commands

The Gradle wrapper is checked in and pinned to **Gradle 8.13** (the project's Kotlin 1.9.20 + AGP 8.13.2 are incompatible with Gradle 9.x, which removed `HasConvention`).

`gradle/gradle-daemon-jvm.properties` requires a **JetBrains vendor JDK 21** for the daemon — the one bundled with Android Studio (`/Applications/Android Studio.app/Contents/jbr/Contents/Home`). Android Studio finds it automatically. For **CLI builds**, point Gradle's toolchain detection at it:

```bash
export JBR="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
./gradlew :app:testDebugUnitTest -Dorg.gradle.java.installations.paths="$JBR"  # JVM unit tests
./gradlew :app:assembleDebug     -Dorg.gradle.java.installations.paths="$JBR"  # Build debug APK
./gradlew :app:installDebug      -Dorg.gradle.java.installations.paths="$JBR"  # Install on a device
./gradlew staticAnalysis         -Dorg.gradle.java.installations.paths="$JBR"  # ktlint + detekt
./gradlew :app:verifyLicenseCoverage -Dorg.gradle.java.installations.paths="$JBR"  # licence list vs classpath
./gradlew ktlintFormat           -Dorg.gradle.java.installations.paths="$JBR"  # Auto-fix formatting
```

Run a single test class: `./gradlew :app:testDebugUnitTest --tests "com.checkin.app.ConsistencyStatsTest"`.

**Static analysis** is **ktlint** (via `org.jlleitschuh.gradle.ktlint`, engine pinned to 1.5.0) and
**detekt** 1.23.8, applied to every project including the root build script. `staticAnalysis` is the
one task CI and the pre-commit hook both call. Formatting rules come from `.editorconfig`
(`intellij_idea` style, matching `kotlin.code.style=official`; 120 columns; `@Composable` exempted
from ktlint's camelCase `function-naming` rule). Detekt's overrides are `config/detekt/detekt.yml`
with `buildUponDefaultConfig = true`, so the file only states what differs, and nothing there
duplicates a ktlint check (`MaxLineLength` is off for exactly that reason). **There is deliberately
no detekt baseline file** — `baseline.xml` is wired up in the root build script but does not exist,
because the tree is clean. Adding one would convert a finding into permanent, invisible debt; the
intended responses to a new finding are a real fix or a site-level `@Suppress` carrying the reason
(see `CheckInService.logService`, `DefaultCsvExporter.export`, `SelfieCaptureScreen`).

A **pre-commit hook** (`githooks/pre-commit`, enabled per clone with `git config core.hooksPath
githooks`) runs the same `staticAnalysis` task. It exits early when no `.kt`/`.kts` file is staged,
and refuses outright to commit a `*.jks` / `keystore.properties` / `local.properties` — `git add -f`
can otherwise defeat `.gitignore`, and a leaked upload key is unrecoverable. Tests are deliberately
not in the hook; they are CI's job.

Toolchain: **JDK 17** source/target compatibility. Android **SDK 36** (`compile`/`target`, Android 16 — Play's target-API floor from 2026-08-31), **min SDK 34** (Android 14). Unit tests live in `app/src/test/java/com/checkin/app/` and are pure JVM (no Robolectric).

**Versioning** is centralized in `gradle.properties` (`VERSION_CODE` / `VERSION_NAME`), read by `app/build.gradle.kts` (with `-P` override support). **`VERSION_CODE`** is the integer Play orders builds by — scheme is **`YYYYMMDD` of the release day, set manually** (must be strictly higher than any code already uploaded, app-wide; users never see it). One uploadable build per day; for a rare same-day rebuild, `+1` or append a 2-digit counter (`YYYYMMDDNN`). **`VERSION_NAME`** is the user-facing SemVer `MAJOR.MINOR.PATCH` label — bump when meaningful. Promoting the *same* `.aab` across tracks (internal → production) reuses its code; only a rebuild needs a new one.

**CI** (`.github/workflows/ci.yml`) runs `staticAnalysis` first — it needs no compiled classpath, so a style or smell failure reports in seconds instead of after a full assemble — then `:app:testDebugUnitTest` + `:app:verifyLicenseCoverage` + `:app:assembleDebug` on push/PR to `main`. It provisions a JetBrains Runtime 21 via `actions/setup-java` (`distribution: jetbrains`) to satisfy the daemon-JVM criteria, then passes `-Dorg.gradle.java.installations.paths="$JAVA_HOME"` — the CI mirror of the local `$JBR` flag above. The Android SDK is the one preinstalled on the runner.

## Architecture

**MVVM with Jetpack Compose + Room + Foreground Service + CameraX + ML Kit + BiometricPrompt.** Manual DI (no framework): `CheckInApplication` holds an `AppContainer` (`di/`) that builds the `CheckInRepository`, the side-effect seams (`platform/` — `PromptSettings`, `ServiceController`, `CsvExporter`), the `TimeSource`, and an app-wide `CoroutineScope`. The seams live in `platform/` rather than beside the container because they are Android adapters, not wiring: `di/` holds `AppContainer` alone, so nothing outside it imports from a package named for dependency injection. Each `ViewModel` is constructor-injected via a `viewModelFactory`, exposes **one** reactive `UiState` (`StateFlow` built with `stateIn`/`flatMapLatest` over Room `Flow`s), and is JVM-unit-tested with fakes.

```
UI (4-Tab Compose Screens) → ViewModel (one UiState StateFlow) → Repository → Room DAO → SQLite
                                    ↕
                           CheckInService (foreground service; timer notification only)
                                    ↕
                           Presence gate: CameraX + ML Kit face detection → BiometricPrompt fallback
```

- **Pure/testable core** (no Android deps, unit-tested):
  - `data/ConsistencyStats` — streak/summary math, plus the all-time peak day the calendar shades against
  - `ui/history/components/DayIntensity` — a day's hours as a `0f..1f` share of that peak
  - `data/TimeSource` (`SystemTimeSource`) — injectable clock so date logic is deterministic in tests
  - `service/SessionSchedule` — reminder cadence and day-boundary instants; `service/SessionClock` — the ongoing notification's elapsed time and chronometer origin; `ui/presence/AuthGate` — biometric-fallback decisions
  - `util/TimeFormat` — the one place durations, clock times **and dates** are formatted
- **Room** — single entity `CheckInSession` (table `sessions`): `id`, `started_at`, `stopped_at` (null while active), `duration` (null until check-out), `date_key` (`yyyy-MM-dd`, the check-in day). DB name `"_app"`, version 5 (v2→v3 `MIGRATION_2_3` added the pause columns; v3→v4 `MIGRATION_3_4` drops the former vestigial `punch_in_selfie`/`punch_out_selfie` columns; v4→v5 `MIGRATION_4_5` drops `paused_ms`/`pause_started_at` along with the mechanism that wrote them — every migration preserves data; `fallbackToDestructiveMigration()` remains the backstop).
- **CheckInService** — `specialUse` foreground service showing the ongoing timer notification, and **only** that. It runs no ticker and owns neither the session reminder nor the day-boundary close: the notification's elapsed time is drawn by the platform chronometer from one post, and both alarms run through `SessionReminderRunner`. It posts on state changes — start, revive, refresh, teardown — a handful of times per session. Persists a render mirror in `checkin_timer_prefs` to survive process death (`START_STICKY`). The **DB row is authoritative**: those prefs are advisory cache, read only so the notification posted inside the foreground-start deadline isn't blank, and every command reconciles against the active session via `ServiceReconciler` — a closed/absent row tears the service down (no orphan notification), and an in-flight reconcile is cancelled first so a stale snapshot can't clobber fresher state. `CheckInService.isRunning` is what `SessionWatchdog` reads to tell a live service from a killed one.
- **Presence gate** — `PresenceGate` is the single entry point and the only place either runtime permission is asked for: it renders the prominent disclosure, then the `CAMERA` + `POST_NOTIFICATIONS` request, then `SelfieCaptureScreen`, and both call sites (the root gate in `MainActivity`, the in-app gate in `AppNavScaffold`) go through it. `SelfieCaptureScreen` captures a front-camera frame; `FaceDetectionHelper` (ML Kit) must find a face. The image is **deleted as soon as the outcome is known** (detection, deletion **and the outcome they produce** all run on the app-wide `AppContainer.applicationScope`, not the composition, so a mid-capture dismiss can strand neither the file nor the result); the camera bind is guarded so a dismiss before the provider resolves still releases it. `AuthGate.BIOMETRIC_FALLBACK_AFTER` (3) consecutive failures — of any kind, no-face **or** capture error — offer a device-unlock (`BiometricPrompt`) fallback. **The outcome must not be delivered on the composition scope**: `failCount` is `rememberSaveable` precisely so the attempt budget survives a config change, so an outcome dropped because the gate was mid-teardown is a failure that never counts toward the fallback — on a device whose camera errors reliably, which is the device the fallback exists for, the escape hatch would then never be offered and the user could neither check in nor out. Only the post-success `onAuthSuccess` delay stays composition-scoped, so a dismissed gate never auto-succeeds. `MainActivity` is a `FragmentActivity` (required by `BiometricPrompt`). The root gate is driven by `PresenceCheckSignal.request` (a `Reason`: `CHECK_OUT` from the timer or session-reminder notification's action, or `CHECK_IN` from a nudge tap). The gate and the nav host render **mutually exclusively** (gate XOR host), but `rememberNavController()` is **hoisted above the switch** so the gate preserves the active tab and back stack; a `BackHandler` dismisses the gate, and the triggering intent extra is consumed once so recreation doesn't replay it. On success, `CHECK_OUT` checks the active session out and `CHECK_IN` opens one.

## Gotchas & Non-Obvious Behaviors

- **There is no daily target, and adding one back would undo the point.** Days used to be classified PRESENT / HALF_DAY_LEAVE / FULL_DAY_LEAVE against a configurable per-day target, with a `TargetSchedule` log so past days kept the target they were judged under. All of it is gone: the schedule, `AttendanceRules`, `AttendanceStatus`, `DeficitCalculator`, the Settings slider and the `daily_target_hours` / `target_schedule` prefs. The reason is empirical rather than aesthetic — **targets are missed as the normal case**, so a system whose primary output is "did you clear the bar" mostly reports failure, and a 45-minute day on a bad week rendered identically to not turning up at all. That is precisely the day the app most needs to reward. What replaced it: a day counts if it has a session, streaks count consecutive such days, and hours are shown as a quantity everywhere they used to be graded. Anything reintroducing a threshold — a minimum session length, a "real day" cutoff, a goal ring — brings the failure mode back under another name.
- **Nothing is asked for at launch — the app opens straight into the nav host.** The disclosure and both runtime permissions were once a blocking startup sequence; they now live inside `PresenceGate` and are raised only when a check actually needs them, which in practice is the first check-in. History, Reports and Settings are therefore fully browsable by a user who has never granted anything, and a *revoked* camera permission no longer locks the whole app out — it surfaces at the next check. Consequences worth knowing before moving any of it back: the gate must ask on entering the "disclosed but ungranted" state rather than only on the disclosure's Continue button, or a permission revoked between sessions strands the user on a recovery screen that never prompts; a `LifecycleResumeEffect` re-reads the grant because the recovery screen's escape hatch is system settings, which returns with no result; and `CameraDisclosureScreen` now carries a **Not now** button, since a screen that interrupts a check-in needs an exit that isn't the back gesture. Only the camera decides whether a check can run — a refused `POST_NOTIFICATIONS` costs the timer notification and the reminder, both already guarded by `Notifier`.
- **Selfies are transient.** The captured JPEG is deleted immediately after face detection resolves (success or failure) — nothing accumulates in `filesDir/selfies/`, and no image is ever displayed. `SelfieStorage` owns the directory and its `sweep()` runs once at startup (from `AppContainer`) to clear any file orphaned by process death between the frame write and that delete.
- **Three SharedPreferences namespaces, and none of them holds a fact about the record.** `prompt_prefs` (`camera_disclosure_seen`, `notifications_asked` — namespace, keys and accessors all inside `platform/PromptSettings`, which is the seam; the keys used to sit in a separate `data/PromptPrefs`, which put the reads in one package and the writes in another for no gain); `checkin_timer_prefs` (the live timer's render mirror plus `SessionAlarms.remindersSent`); `engagement_prefs` (the variant-bucketing install id and **nothing else** — behind the `EngagementInstall` seam; the per-nudge send history went with the cooldown, since nothing read it once the cap counted from the log, and the nudge opt-ins went with the in-app toggles, since an opt-out is a channel — see the channel-opt-out entry below. Its `NAME` and `install_id` key are frozen: a rename hands every install a fresh id and reshuffles the variant assignment of an experiment already in flight). Everything in `prompt_prefs` records that a one-time prompt has already been raised, which is why the file is named for prompts and not for tracking: **`tracking_start_date` used to live there and is gone**, along with the `tracking_prefs` name, `attendance_prefs` before it, and the `migrateFromLegacy` copy between them. See the tracking-start entry below for why. **`checkin_timer_prefs` and `prompt_prefs` are excluded from cloud backup**, alongside the sessions DB: the first mirrors rows a restore does not bring, and the second would assert that prompts were already raised on a device where they never were — a cloud restore carries no runtime permission grants, so a restored `notifications_asked` leaves the timer notification, the session reminder and every nudge silently dead. Device-to-device transfer keeps both, because there the DB and the grants move too. `engagement_prefs` stays backed up for the same symmetry: `engagement.db` is not excluded either.
- **Two databases.** `_app` (v5) holds the sessions. `engagement.db` (v2 — `MIGRATION_1_2` adds the `source` column) holds only notification analytics and is deliberately a *separate* Room database — an experiment redesign can drop and recreate it with `fallbackToDestructiveMigration` without ever putting a user's session records at migration risk, and no schema change there widens the CSV export. The cost is that conversion attribution can't be a SQL join, so it happens in Kotlin via `AttributionRules`. **Session reminders are logged here too, and the `source` column is what keeps them harmless.** `countOfTypeSince` (the nudge daily cap) and `latestOfType` (conversion attribution, and the tap fallback) are both scoped to `source = 'NUDGE'`; unscoped, a session reminder would consume a nudge slot or take credit for a check-in it never caused. Service-lifecycle rows use a third source, `SERVICE`, and are scoped out of the same two queries for the same reason. `recent()` is deliberately unscoped so the diagnostics card shows everything. `FakeEngagementLog` mirrors the same scoping — otherwise a test could only ever prove the fake right — and `EngagementLogSourceTest` pins all of it. The names are now a half-truth (`EngagementLog`, `engagement.db`, `engagement_events`, `engagement_prefs` all hold session-reminder rows too) and are kept anyway: a rename means a new DB file, which orphans the very rows the daily cap counts from.
- **The nav scaffold owns the screen title.** `AppNavScaffold` renders a `CenterAlignedTopAppBar` whose title is the active `Screen.titleRes`, driven by the same back-stack subscription as the bottom nav — screens never draw their own heading, and they receive the combined top inset through the Scaffold's `innerPadding`. `Screen` splits into `Tab` (a bottom-nav destination) and `Detail` (pushed above a `parent` tab: back arrow instead of a centred-only title, and the parent stays lit below so a sub-screen still reads as part of its section). **A new destination must be added to `titledScreens` (in `ui/navigation/Screen.kt`, alongside the hierarchy itself), not just to the nav graph in `NavigationGraph.kt`** — the title lookup falls back to `Screen.CheckIn`, so a route missing from that list renders a screen labelled "Check In" rather than failing. **A route string is not a free rename.** It doubles as the destination id a saved back stack is restored against (`route.hashCode()`), and `NavController` throws when a restored entry names a destination the graph no longer has — so an install updated while parked on a renamed route can crash on launch until the task is cleared. The `attendance` → `history` rename shipped with that hazard knowingly, because nothing had reached Play; a route change after a release needs the old string kept or a redirect destination registered. **A tab tap pops any open `Detail` before it navigates**, because the bar's `popUpTo(start) { saveState = true }` + `restoreState = true` would otherwise save the detail *into* its parent tab's back stack — tapping the lit Settings tab from Licenses would then restore Licenses, and the tab would read as dead. `SettingsViewModel` is the one VM that is prefs-only (no Room `Flow`), so it re-reads on resume and after each write rather than building a reactive pipeline.
- **The tracking start is derived, not stored, and storing it again would reopen the bug it was deleted for.** It is `SELECT MIN(date_key) FROM sessions` — `CheckInRepository.trackingStartFlow()` (plus a suspend `trackingStart()` for the CSV export) — so it is definitionally the first session's day, null while there are none, and reactive: the first check-in starts the record by being written, with nothing seeded beside it. Open sessions count, and the query is deliberately **not** filtered to completed ones, because a first check-in still running is still the day tracking began. It used to be `tracking_start_date` in prefs, seeded at the first check-in by `TrackingSettings.seedTrackingStartIfNeeded()`, and that made it a second copy of a fact the table already held. The two could then disagree, and one restore path was enough: brought back without the sessions it indexes, the app reported **every day since as one the user did not show up for** — on a fresh install, on the one screen they check their consistency in, with no UI to correct it. Excluding the pref from backup only closed the paths anyone had thought of; the legacy `attendance_prefs` file was not excluded, and `migrateFromLegacy` copied the key straight back out of it, with the "already migrated" guard sitting in the very file the restore had skipped. Read off the sessions, the disagreement is unrepresentable and there is nothing to exclude, guard, or reconcile. Consequences that follow: `HistoryUiState.trackingStartDate` and `ReportsUiState.trackingStartDate` are **nullable**, `CalendarGrid` treats null as "no day is inside the tracked window" (the whole month draws as days the record does not cover, never as days that were missed), and neither screen can seed the answer synchronously any more — both render nothing while `loading` rather than flashing an empty state, and `CheckInScreen` holds the gauge's slot rather than showing the first-run welcome to a user with months of history. There is still no UI to change the start (by design); there is now no value to change.
- **Every window ends at `ConsistencyStats.countedThrough`, and that is today only once today has been checked out of.** One pure function decides it — `today` when `summaries` holds today's key, otherwise yesterday — and History, Reports and the CSV export all end there, so they cannot drift. A completed session therefore lands in the streak, the showed-up count, both averages, the peak and the calendar shade **the moment it is checked out**, with no resume and no wait for midnight. **The conditional half is the load-bearing half.** A window that simply ended at `today` would open every morning with a missed day, a dipped average and a streak of 0, then take all three back at the first check-out — the failure-first reading the daily target was deleted for (see the no-target gotcha above). Ending at yesterday until today has produced something means the numbers only ever move upward during a day, and an in-progress day still counts for nothing anywhere. **The test is free, and that is why it is written this way**: the aggregate queries filter `stopped_at IS NOT NULL`, so a row for today exists *iff* today holds a completed session — `summaries.containsKey(todayKey)` **is** the predicate, needing no extra query and correctly ignoring an open session. It follows that the map can hold no key past `countedThrough`, which is why `totalWorkedMs`/`peakDayMs`/`showedUpDays` take no range and `computeMonthTiles` filters nothing. Two consequences to keep in mind: **both ViewModels must guard `start.isAfter(countedThrough)`** before dividing by the tracked-day count, since the record's first day is unfinished until it isn't and `trackedDays` would be 0 (a crash the old `yesterday` anchor made unreachable); and today *can* now set `peakDayMs`, so a personal-best day re-shades the whole calendar mid-day, possibly more than once. The "today" boundary itself still comes from an injectable day clock (`TimeSource.currentDay()`), so at midnight the screens roll over **live** — and a day already counted at check-out must read identically after the rollover, neither re-counted nor reset. Only the History *displayed month* stays put until the user navigates.
- **The engagement layer is structurally isolated, and that is the point.** `notify/` may *read* tracking state to build an `EngagementSnapshot`, but it never writes to `sessions`. The entire decision surface is `NudgeEligibility.select(snapshot)` — a pure function of a plain value object, no clock, no DB, no Android — so experiments in timing, capping and targeting are changes to one unit-tested function. **There is no app-level quiet-hours window and adding one back would be a mistake**: Android's per-channel settings already give the user that control, and the app's own version only ever applied to nudges while the session reminder and the timer notification ignored it — a promise ("Nothing is sent between…") the app did not keep. Frequency is bounded by the daily cap and the checkpoint spacing alone — a per-nudge cooldown sat beside them and was removed, because it measured a rolling 20-hour window against the cap's calendar day, so the two could disagree about where a day ended. Two places deliberately touch app code: `PresenceCheckSignal.Reason.CHECK_IN` (nudge tap → gate) and the `EngagementReporter` seam. That seam's `onCheckedIn` is called from **both** check-in writers — `CheckInViewModel.executeCheckIn` and `MainActivity.onRootGatePassed` — because a nudge the user acted on from inside the app converted just as much as one they tapped; wiring it only to the tap path would report 0% for a nudge that worked. It also cancels the now-stale nudge notification, since nothing the app posts is `autoCancel`. **Nudges default ON**, and the channel is the switch. Opt-in reads as the cautious choice and is not: the only nudge that exists tells a user they have not checked in today, and a user who has not formed the habit is precisely the one who never goes hunting through settings to enable a reminder about it — off by default meant the feature reached nobody it was built for. Turning it off is one long-press on the notification, and the daily cap bounds it to two messages a day regardless — spaced hours apart by the checkpoints, with `NudgeDispatcher` cancelling the earlier before posting the later, so at most one is ever in the tray. `NudgeEligibility` therefore holds **no** enabled/disabled test at all: whether the user wants nudges is the channel's question, and `Notifier` already refuses a post to a blocked one. **There is likewise no tracking-started gate**: requiring a first check-in before the app would say anything locked the nudge away from exactly the user it exists for. The isolation is enforced at runtime too: `CheckInService` writes its lifecycle rows through `logService`, which swallows a failed write, because `serviceScope` has no exception handler and a full or corrupt `engagement.db` would otherwise take the foreground service — and with it the user's running timer — down with it.
- **A nudge tap is still gated.** `EXTRA_CHECK_IN` opens the root presence gate exactly like the reminder and check-out paths; success then checks in. Check-in is never un-gated, and the handler re-checks for an active session first, since the user may have checked in between the notification being posted and tapped. `repository.checkIn()` is the backstop for that check: it returns the open session rather than inserting a second, because two rows with `stopped_at IS NULL` would leave one open forever. A presence request is never queued and never outlives its tap. `PresenceGate` owns the disclosure and both permissions, so the gate always opens on the spot — there is no screen a reason could sit behind. What it can still do is go unanswered: the gate parks indefinitely on the disclosure, the camera-recovery screen or the capture, and pressing Home leaves the reason set on a process-global flow nothing else clears. So `PresenceCheckSignal.raise` stamps the request and `MainActivity.onStart` calls `expireIfStale`, dropping anything older than `EXPIRY_MS` (10 minutes) before it can reopen. **The check is on start, not on stop**, because leaving the app is exactly what the gate's legitimate path does — the recovery screen sends the user to system settings and expects them back — and only elapsed time separates that round trip from abandonment. Without it a nudge tapped at 09:00 and abandoned reopens that evening and, on success, writes a check-in stamped at whatever day it had become, onto a row the app deliberately gives no way to edit. `PresenceCheckSignalTest` pins the boundary and the round trip.
- **`POST_NOTIFICATIONS` is asked for at first open, and that is a second ask, not a moved one.** `MainActivity.NotificationPermissionOnFirstOpen` requests it once on the first launch that reaches the nav host; `PresenceGate` still asks for it alongside the camera at the first check-in. Both exist because nudges now default on and the timer notification is the app's main surface — waiting for a check-in would leave a new user with every notification silently dead, including the one telling them they have not checked in. It is asked **once**, tracked by `notifications_asked` in prefs rather than inferred from the grant, because a refusal and a never-asked are indistinguishable through `PackageManager` and Android drops the dialog silently after two refusals, so re-asking each cold start would be invisible noise. It renders only outside the gate — two stacked system dialogs is a dialog nobody can answer. **Nothing else is asked at launch**: the camera and its prominent disclosure stay behind the gate, where a check actually needs them.
- **A nudge is delivered by an alarm, and the hourly worker is only the backstop. Do not put the trigger back on the worker.** This is the fix for a real install that got one nudge and then went silent for days. The rule was `hourOfDay >= 10`, asked once per `NudgeWorker` pass — and a `PeriodicWorkRequest`'s interval is a *request*: an app the user is not opening falls through Android's standby buckets (`working_set` ≈ 2h → `frequent` ≈ 8h → `rare` ≈ once a day) and a deferred periodic job settles at a **consistent** hour, often in an overnight Doze maintenance window. A single daily pass landing at 05:00 makes that condition false every day, permanently, and the failure is self-reinforcing — the user the nudge exists for is exactly the one whose worker has stopped running. **A time-of-day trigger needs a time-of-day primitive**: `NudgeAlarms` keeps one inexact `setAndAllowWhileIdle` alarm set for the next `NudgeSchedule.Checkpoint`, and `NudgeAlarmReceiver` re-arms from inside the pass it just fired, in a `finally` so a throwing pass still schedules the next one. The worker stays because `reviveIfNeeded` and `prune` have to hang somewhere and a second chance costs nothing — the cap counts from the log, so a pass landing after the alarm already fired sends nothing. It still returns `Result.success()` on failure: `failure()` is *terminal* for periodic work, so one transient error would cancel every future pass.
- **`NudgeAlarms` is stateless, and `SessionAlarms` is not, for a reason.** The session seam persists its armed instants in `checkin_timer_prefs` because they derive from a session and cannot be recomputed without one. A checkpoint is pure clock maths, so the next one is always derivable from now — there is nothing to persist, nothing to reconcile against an `AlarmManager` that cannot be asked what it holds, no new prefs namespace and no new backup exclusion. `armNext` is idempotent, which is why three callers can fire it freely: `CheckInApplication.onCreate` (every process start), `NudgeWorker` (the deferrable repair), and `SessionRestoreReceiver` (boot and package replace, both of which *cancel* alarms). `AndroidNudgeAlarms.nextCheckpointAt` is process-local and exists only for the diagnostics card, so a 0 there after a cold start means the arming call did not run — not that the alarm is missing.
- **Checkpoint bands are ranges, not thresholds, and that is load-bearing.** `NudgeSchedule.checkpointAt` returns the *last* checkpoint at or before the hour, so 10–13 is MORNING, 14–18 AFTERNOON, 19–23 EVENING, and 00–09 is null. `NudgeEligibility` takes the first matching nudge in declaration order, so with `hour >= checkpoint` tests every hour past 10:00 would resolve to MORNING and the afternoon and evening copy would be unreachable for good — three nudges declared, given ids and copy, two of them dead, and nothing failing. The null band before the first checkpoint is also what keeps a nudge out of the small hours **without** an app-level quiet-hours window, which the app deliberately does not have. `NudgeSchedule` is the single source of truth for these hours, read by both the alarm and the rule: two copies is how an alarm comes to fire at an instant the rule then declines to act on, which is indistinguishable from an alarm that never fired.
- **An open session past its own day boundary is not evidence the user is present.** `EngagementSnapshot.isCheckedIn` is the raw fact; `isPresent` is what the rules read, and it is false once `openSessionOverdue` is set. A session cannot legitimately outlive the midnight of its own `date_key` — the day-boundary close ends it — so one that has is a session whose alarms were lost to a force stop or a package replace. Counted as "checked in" it suppressed every nudge for as long as it stayed open, which is indefinitely on a device the user has stopped opening, and the nudge it silenced was the one that would have brought them back to fix it.
- **The calendar shades by intensity, and nothing renders red.** `DayIntensity.fractionOf(totalMs, peakMs)` maps a day's hours to `0f..1f` against the user's **all-time longest day** (`ConsistencyStats.peakDayMs`, carried on `HistoryUiState.peakDayMs`), and `dayColor(fraction)` turns that into one hue at varying alpha. A cell shades when it is inside `trackingStart..countedThrough`, so **today takes its colour at check-out** and carries its marker alone until then; `today` stays a separate parameter from `countedThrough` because today is drawn as today either way, and the future is measured from it. All-time rather than per-month so a day reads the same however it is navigated to; the cost is that a new personal best re-shades the history once, which is acceptable now a shade is a quantity rather than a verdict — and since today counts from its first check-out, a record-breaking today can do that more than once in a day. Two floors matter: `MIN_FRACTION` keeps the shortest session visibly a day shown up for rather than an empty cell, and `BACKGROUND_STRENGTH` in `CalendarGrid` caps the fill so the day number stays legible on top of it. A day with no sessions is transparent. **The cell's `contentDescription` states the hours**, because the shade stands for a quantity and colour must never be its only carrier. **Only days *outside* the tracked window are faded** (`OUTSIDE_WINDOW_ALPHA`): the future, and the days before the user began. Fading the past instead is the mistake that treatment exists to avoid — days with sessions already carry the hue, so the fade would land on exactly the empty days the record covers, and a day drawn fainter for holding nothing is the verdict this calendar never renders. What it separates is "no record kept" from "in the record". It is the one mark here allowed to be colour-only, because the fact is already stated: a date after today reads as the future from the number itself, unlike the intensity shade, which encodes hours nothing else on the cell says.
- **Charts are hand-rolled, and the maths is separate from the drawing.** `ui/components/charts/ChartGeometry` is pure Kotlin (no Compose, no Android) and unit-tested for the degenerate cases that would otherwise divide by zero or draw off-canvas: empty series, all-zero series, a single point, values above the ceiling. The `Canvas` composables only translate its output into draws. There is no charting dependency — adding one would be the first third-party UI library in the project. **An all-zero window must read as a row of zeros, not as a chart that failed to draw**, and that is a real state: a 30-day window with no sessions in it is what a user who has stopped checking in sees. So `LineChart` insets its plot by a full stroke and draws inside that — a series pinned to the floor otherwise loses the outer half of its line to the canvas edge and reads as blank — and `BarChart` draws a `baselineColor` rule whether or not any bar has height, since a zero-height bar is skipped entirely (a rounded rect with no height renders as a stray lens shape). Both insets come out of the composable, not out of `ChartGeometry`, which still works in the plot box it is handed. Every chart takes a `contentDescription` that states its values, because a `Canvas` is otherwise invisible to a screen reader. **`DonutChart` bounds its centred `content` itself, and that is not a convenience.** The hole is round, so its full diameter is only available along the centre line; a caption bounded by the diameter still overhangs the arc at the top and bottom of its own height. The bound is the *inscribed square* (`ChartGeometry.INSCRIBED_SQUARE`, `hole × 0.707`), applied inside the composable — the two call sites previously disagreed, with History constraining to a square 72dp and Reports not constraining at all, so its caption ran out over the ring. That constant lives in `ChartGeometry` rather than in either drawing, because `CircularProgressRing` deliberately does *not* apply it — the Check-In gauge's 45sp clock is wider than the square and must not wrap — so the History stat tiles bound their own content by the same figure, and a second copy is how the two would drift. Sizes live in `DonutChartDefaults` for the same reason: one stroke width, one diameter, both donuts. The diameter grows with `LocalDensity.fontScale` and caps, because the caption is `sp` while the ring would otherwise be fixed `dp` — past the cap the caption ellipsizes rather than being clipped mid-word.
- **Reports derives three charts from one query.** `ReportsViewModel` runs a single `dailyAggregatesFlow(trackingStart, today)` and builds the daily series, the monthly series, and the all-time split from it — the query reaches today, and `countedThrough` decides per emission how much of it counts. Reports holds the app's only **current streak** display, which is what makes that the visible payoff: it extends on the check-out rather than the next morning. Both series are gap-filled: a day or month with no sessions is emitted as a real zero, since a hole in a line chart reads as missing data rather than an absence. Missed-day counts come from subtracting the days that *have* entries out of the tracked window — days without sessions never reach the map at all. The daily chart's dashed reference line is the window's own **mean**, not a target: it shows where the window sits relative to itself rather than against a bar a day could fall short of.
- **The History calendar is sized from the viewport.** `CalendarGrid` takes a `cellHeight` that `HistoryScreen` derives inside a `BoxWithConstraints` from the **real** viewport — `maxHeight` less the chrome, the month selector, the weekday header and the summary card — divided by the month's actual row count (4–6, so the grid doesn't jump between months) and clamped to `48.dp..80.dp`. A cell is only ~53dp wide, so an uncapped height stretches it into a ribbon. Deriving it from `LocalConfiguration.screenHeightDp` instead is the bug this replaced: that is the whole physical screen, so it over-counted by the app bar and bottom nav and pushed the summary card off the bottom. The `48.dp` floor deliberately wins over fitting — it is the minimum tap target, so a 6-row month on a small screen scrolls slightly rather than shrinking its days below it. Selecting a day **replaces** the month-summary card rather than appending below it, so picking a date never adds height. `SUMMARY_CARD_HEIGHT` is a constant rather than a measurement because the grid has to be sized before the card below it is laid out, so **it must be kept in step with `MonthSummaryCard`** — over-stating it wastes grid height, under-stating it pushes the card off the bottom.
- **The month summary is four rings, and every baseline is the user's own record.** `MonthSummaryCard` lays out a 2×2 of `CircularProgressRing` tiles: days shown up (of the month's tracked days), best streak, average day and longest day — each a month figure ringed against its all-time equivalent, so a full ring means "this month matches your best", never "you cleared a bar". A configured denominator would be the deleted daily target under another name; `statRatio` (pure, in `MonthTiles.kt`) clamps to `0f..1f` and returns 0 for an absent baseline, so a month with nothing behind it draws four bare tracks rather than dividing by zero. Averages are per *tracked* day, which keeps missed days in the denominator; the all-time average, `peakDayMs` and `allTimeBestStreak` all come off the one range query, so the calendar's shading normalizer costs nothing extra. The month's own best streak is measured over `trackedWindow` — the same window the tracked-day count uses, so the two cannot disagree about where the month starts *or* about whether today is in it — which truncates a run crossing a month boundary, as a per-month figure has to. `computeMonthTiles` takes **no** `todayKey` and filters nothing: an in-progress today is absent from the aggregates to begin with, so the map is already exactly the counted set, and both it and `trackedDaysInMonth` widen together off the one `countedThrough`. **The missed count is no longer on the face of the card**, only in the showed-up tile's `contentDescription`: it is a fact worth having, but a tile counting up toward it would be a progress bar toward failure. The track colour is `outline`, not `outlineVariant` — the latter *is* `surfaceVariant`, the card's own container, in the dark scheme, so the old missed segment and its legend dot were painted in the background and were invisible.
- **Only completed sessions aggregate** — every summary/total query filters `stopped_at IS NOT NULL`; an active session contributes nothing until check-out.
- **There is no mid-session presence check and no pause, and reintroducing either would be a regression.** The check verified the user was still there and *stopped their clock* when they didn't answer — so a question nobody saw silently deleted hours they had worked, on a row the app gives no way to edit. Nothing now subtracts from a session: `duration` is exactly `stopped_at - started_at`. Check-in and check-out remain gated; only the mid-session interrogation is gone, along with `paused_ms`, `pause_started_at`, `beginPause`/`resumeFromPause`, the retry/refusal ladders, the in-app Resume button and both Settings toggles.
- **An open session keeps two inexact alarms, and they do different jobs.** `SessionReminderRunner.arm` schedules both through `SessionAlarms`, and `SessionAlarmReceiver` handles each **itself** rather than waking the service — the alarms' whole purpose is to work when the service is gone, and starting a foreground service from a background broadcast would be refused in exactly that case.
  - The **reminder** fires every `SessionSchedule.REMINDER_INTERVAL_MS` (2h) and only asks: it posts "still checked in?" with a gated **Check Out** action, and ignoring it costs nothing at all. Only the first of a session alerts (`SessionAlarms.remindersSent`); the rest post silently so a session running overnight accumulates on the shade rather than buzzing every two hours. A **refused post** logs `DEGRADED` and re-arms **without advancing the count**, so restoring notifications means the first reminder the user can actually see still alerts — silence is not an answer.
  - The **day boundary** closes the session at local midnight, and it is the only thing that ends a forgotten one. **It stamps the instant derived from the session's own `date_key`, never the fire time** — the alarm is inexact and may land hours late, and stamping when it fired would hand a forgotten session hours on a day it does not belong to. `SessionSchedule.dayBoundaryOf` goes through the calendar rather than adding 24h, so a DST day still ends at midnight. An instant already past is left as-is: the platform delivers a past-due alarm immediately, which is what closes a session that outlived its boundary while the process was dead.
- **The day-boundary close is the one un-gated check-out in the app.** Every other path runs the presence gate. This one cannot: the point is to close a session the user has forgotten, and a forgotten session is precisely the one nobody is present to authenticate. It is safe in a way no other check-out is — it can only ever *end* a session, always follows a gated check-in, and writes an instant fixed by the calendar rather than by anything the caller chooses. The cost to accept: a session started at 23:50 closes ten minutes later.
- **Why inexact:** neither instant needs to be hit precisely — the reminder is a cadence, and the boundary stamps from `date_key` regardless of when it lands — while `SCHEDULE_EXACT_ALARM` is denied by default from Android 14 and `USE_EXACT_ALARM` is restricted by Play to alarm-clock apps. What *is* needed is the wake: `setAndAllowWhileIdle` fires through Doze. **Never `setAlarmClock`** — it is the only alarm API that shows a status-bar alarm icon and a lock-screen entry.
- **An open session with no service is a real state, and three callers fix it.** `START_STICKY` is best effort — a force stop, an OEM background-management kill or a crash all leave the process dead with the row still open — and nothing used to restart the service afterwards: it was started at check-in and nowhere else. Opening the app did not help either, because the Check-In screen renders from the row, so it showed a cheerfully running timer with nothing behind it. `SessionWatchdog.reviveIfNeeded` now runs from `MainActivity.onStart`, `SessionRestoreReceiver`, and the hourly `NudgeWorker` pass, in that order of reliability: **a visible Activity is always allowed to start a foreground service, `BOOT_COMPLETED` and `MY_PACKAGE_REPLACED` are exempt, and a worker may be refused outright.** A refusal is logged as `DEGRADED` rather than thrown, and the next caller retries — which is why there are three and not one. `ServiceController.revive` returns a `Boolean` for exactly this, and `reviveIfNeeded` catches everything: its callers are fire-and-forget `launch`es on a scope with no exception handler, so a throw would kill the process this exists to recover. **The revive is `ACTION_REVIVE`, never `ACTION_START`** — the check-in path takes its timing from the intent, which is right for a session that hasn't begun and wrong for one already running.
- **The service and the alarms are lost separately, so they are repaired separately.** `reviveIfNeeded` calls `SessionReminderRunner.ensureArmed` **before** it even looks at whether the service is running, and this ordering is the fix for a wrong premise the code used to state outright ("a killed process does not cancel alarms, so there is nothing to re-arm"). A plain process kill leaves alarms standing; **a force stop and a package replace cancel them**. Since `arm` was reachable only from `ACTION_START` and the boot receiver, an open session that survived an app update kept its timer and silently lost its day-boundary close — and that close is the only thing that ends a forgotten session, so it ran until the user noticed and then wrote a multi-day `duration` onto a row nothing can edit. `ensureArmed` is separate from `arm` because it must be safe to call on every app open: it re-arms **the instants already stored** (`next_reminder_at` / `day_boundary_at` in `checkin_timer_prefs`, since `AlarmManager` cannot be asked what is still set), never touches `remindersSent`, and re-derives a reminder only when its instant has already passed. Re-anchoring unconditionally would push the reminder past every repair, so a user who opens the app hourly would never get one. The **boundary is re-armed even when it is in the past** — the platform delivers a past-due alarm immediately, which is what closes a session that outlived its boundary while nothing was armed.
- **Whoever writes the row arms it.** `arm` is called from `CheckInViewModel.executeCheckIn` and `MainActivity.onRootGatePassed`, not from `CheckInService.handleStart` where it used to live. `ServiceController.startTimer` is documented to be refusable — a restricted standby bucket, an OEM that declines a `specialUse` foreground start — and neither writer inspects that `Boolean`, so arming inside the service meant a refused start silently produced a session with no alarms at all. Writing the row cannot be refused. Check-out cancels for the mirror-image reason: `ServiceController.stop()` is a caught no-op when the service is already dead, so leaving the cancel to `tearDown` stranded both alarms over a closed session.
- **`CheckInService.isRunning` tracks the notification, not the object.** It is set from a *successful* `startForeground` and cleared when that call throws (it is guarded — a background-start refusal or a foreground-type restriction must not kill a running session), on teardown, and in `onDestroy`. Setting it in `onCreate` instead is the bug this replaced: a caught `startForeground` failure left the instance alive with nothing on the shade, reporting itself healthy forever, and `SessionWatchdog` skipped the one state it exists to repair.
- **`serviceScope` carries a `SupervisorJob` *and* an exception handler, and it needs both.** A `CoroutineExceptionHandler` reports a failure; it does not contain one. Under a plain `Job()` the first uncaught throw in any `serviceScope.launch` cancels the scope permanently, and every later command — reconcile, arm — becomes a silent no-op for the life of the service. That is worse than the crash it replaces: the reconcile that would tear down an orphaned notification launches onto a dead scope, and nothing happens, then or ever. The throw sources are real (`getActiveSession` on SQLite, the engagement-log write, `setAndAllowWhileIdle` past the 500-alarm cap). For the same reason the two `log*` helpers launch on **`applicationScope`**, not here — half of what is worth recording happens as the service ends (`STOPPED`, and the `DEGRADED` row the handler itself writes), and `onDestroy` cancels `serviceScope`.
- **Reboots and updates need their own handler.** `START_STICKY` survives neither, and neither do alarms, so `SessionRestoreReceiver` handles `BOOT_COMPLETED` **and** `MY_PACKAGE_REPLACED` — both are among the few contexts allowed to start a foreground service from the background. It no longer arms anything itself; it makes the same `reviveIfNeeded` call as every other caller, and that is what fixed the reboot resetting the alert ladder: `arm`'s leading `cancelAll()` cleared `remindersSent`, so the first reminder after a restart alerted at full volume in the small hours over a session left running on purpose. The hourly worker would eventually repair a package replace on its own (WorkManager reschedules itself across one), but it is deferrable and an update at 23:00 could miss midnight entirely.
- **The diagnostics card is debug-only, and it reads state before it reads history.** It shipped in release for a while, on the argument that failures in `service/` and `notify/` are silent so a user hitting one has nothing else to report. The premise was right; the loop never closed. The rows read `DEGRADED PRESENCE_CHECK`, which no user can interpret, and `Feedback.draft` carries only the app and device build — so the evidence never travelled, and the card paid for a consumer Settings surface while collecting nothing. Either finish that loop (attach the log to the feedback body) or scope it to whoever is debugging; the latter is what happened. **The state block is the half that earns it.** `DebugSnapshot` says what is true now — open session, service flag, both armed instants, `remindersSent`, per-channel deliverability — and `warnings()` names the wrong states outright: open session with no service, a boundary unarmed or long past due, a boundary disagreeing with the session's `date_key`, alarms stranded over a closed session, an orphan service. Each renders as a completely normal app, which is why they must be stated rather than inferred. The split follows `NotificationDelivery`/`NotificationBlock`: `DebugSnapshot` is pure and unit-tested, `DebugSnapshotReader` does the Room and prefs reads, and the channel switches arrive as parameters because they need a `Context`. Nothing it reads is reactive, so it re-reads on resume and on an explicit Refresh; **Copy report** puts the snapshot, warnings and log on the clipboard. Two details worth keeping: rows print `source`, which the release card dropped even though it scopes the daily-cap and attribution queries; and **both debug cards keep their text as Kotlin literals**, since R8 folds the `BuildConfig.DEBUG` branch away and a literal then leaves the APK entirely, whereas resource shrinking kept all 12 debug strings in release and would have offered them to a translator as product copy.
- **Three separate switches silence a notification, and the permission is only one of them.** A user can hold `POST_NOTIFICATIONS` and still have notifications off for the whole app, or set an individual channel to "None" — which is exactly what "I had everything enabled" turns out to mean. So `AndroidNotifier.canPost` checks all three (permission, `areNotificationsEnabled()`, channel importance, plus a missing channel, since a post to one that was never created is discarded), and `NotificationsCard` checks the same ground: it distinguishes *everything off* from *the timer channel muted* and says so, since the copy for one is wrong for the other. Neither the reminder nor the engagement channel is in that check, and the reason is the same for both — **muting them is a preference, not a fault.** The reminder only ever asks, and the day-boundary close ends a forgotten session with no notification involved. Their channels *are* their opt-outs, so excluding them is mandatory rather than merely defensible: the card's whole job is to point at Android's notification settings, and nagging about a choice the user made there, in the same breath as sending them back to make it, would be worse than no card. **The card renders in every state, not only the bad one** — healthy, it answers "how do I stop this?" where a user looks for the answer, which is the entire in-app notification surface now that no switch lives here. `NotificationBlock.NONE` therefore carries real copy rather than `0` — and that copy **names the timer as the one switch the card will warn about**, because the card sends the user to Android's settings and then flips to a warning if they mute that channel there. Listing all three as equally free choices is the version this replaced: it invited an action and then scolded them for taking it, in the same breath as telling them where to take it. `POST_NOTIFICATIONS` is asked for in exactly two places (first open, then `PresenceGate` at the first check-in) and Android stops showing the dialog after two refusals, so without the card an install can sit permanently with the timer, the session reminder and every nudge silently dead while every screen looks normal. The card re-reads on resume, because its only escape hatch is system settings, which returns with no result.
- **A notification's opt-out is its channel, and nowhere else. This is the rule for every notification the app ever adds.** There is no in-app switch for the timer, the session reminder or the check-in reminders; Settings holds one card whose only control opens Android's notification settings. Two reasons, and neither is taste. **First, an app pref is subordinate to the channel and so can only agree with it or lie.** `NotificationDelivery.canDeliver` already refuses a post to a blocked channel, so channel-off plus pref-on sends nothing while the UI reads "on" — the pref is the half that lies, and it is the half the user was looking at. Nudges carried exactly this: a master switch *and* a per-nudge row, which with one `Nudge` in the enum were the same switch twice, both collapsing to the same `emptySet()` and both outranked by the channel. **Second, an in-app opt-out is a one-way door.** Android has no API to block or lower a channel — an app can only create one — so a stored opt-out can never be migrated into the system, and deleting the toggle later silently re-enables the notification for everyone who had used it. That is why this shipped at ~0 installs: it is the only moment the migration is free. Consequences that follow. A **new** notification gets a **new channel**, and a nudge wanting independent control gets its own channel too — never a flag in prefs; `NudgeEligibility` decides *timing*, never *consent*. Channel **name and description are updatable** after creation and should carry the words a user hunting for the switch would search for (hence `engagement_channel_name` is "Check-In Reminders", not the internal "Encouragement"), while the **id and importance are frozen** — see the timer-channel entry. That name sits one row from "Session Reminders" and the two are near-synonyms to anyone outside this codebase, so the **descriptions** carry the difference: turning off the wrong one costs the prompt that catches a forgotten open session. And discoverability does not regress: a long-press on the notification shows its channel and turns it off in one tap, which is nearer than Settings ever was, and channel-level control satisfies Play's easy-opt-out requirement for promotional notifications.
- **Gated check-out from the notification.** The ongoing timer notification's "Check Out" action opens `MainActivity` with `EXTRA_CHECK_OUT` (not a silent `ACTION_STOP`), so it runs the root presence gate and checks out on success — check-out is **never** un-gated. `ServiceController.stop()` (`ACTION_STOP`) now only ends the service *after* a check-out has already been written.
- **`checkOutAt` exists for the day boundary, and `checkOut` delegates to it.** Both are read-modify-write over the row (matching the original `checkOut` pattern); the only difference is whether the stop instant is "now" or one the caller computed. Duration is floored at zero, because a stop before the start is a changed system clock or a corrupt row and a negative duration would poison every total that sums it. All three (`checkOut`, `checkOutAt`, `checkOutActiveSession`) **return the closed row**, so a caller that reports what was recorded reads the stored figure instead of subtracting again — a second subtraction at the call site is a second copy of the flooring rule, free to disagree with the row it describes.
- **The Check-In gauge is the current session, never the day's total — and that is why it carries no label.** It reads zero between sessions and counts up from zero at check-in, which is unambiguous by convention; a clock resuming from the day's accumulated total read as a *paused* stopwatch, implying the one mechanic the app deliberately deleted (see the no-pause gotcha), and left a user mid-session subtracting to answer "how long have I actually been sitting here". The day's volume is stated directly below by `TodaySessions`, whose header is **outside** the `AnimatedVisibility` and therefore always on screen, collapsed or not: `n sessions · Xh Ym today`, gap-free because it adds the open interval's live elapsed to the completed ones. That header is now the only place the day appears on this screen, which is why it is a centred, contained pill rather than a full-width row with a chevron — and why its **touch height is floored at 48.dp on the `Surface` while the visual padding is tighter**, since making a target look smaller must never make it smaller. A consequence worth keeping: the notification's chronometer counts from `started_at` and so now shows *the same figure the gauge does*; before this they disagreed by the day's completed total, and they could not be converged the other way, because a platform chronometer can only count from a fixed instant and a running day total would need the banned per-second service ticker.
- **The expanded session list is a ledger of two columns, and nothing in it ticks.** Each row is the clock range and what it came to — the range weighted, `DURATION_COLUMN` fixed, so the amounts stack into a column instead of ragging with the text. **A third column was tried and removed, and the reason generalises**: each candidate only paraphrased a column already there. A word for where in the day it fell ("Morning", from a pure seven-bucket `SessionPeriod` mapping) restates the start time sitting immediately beside it, and an ordinal `#n` restates both the row order and the `n sessions` in the pill directly above. Labelling by *length* instead — a "quick one" against a "deep dive" — is worse than redundant: it grades the session, which nothing in this app may do. The open interval shows `ongoing` in place of an end time and a pulse (`OngoingPulse`) in place of a duration: a second live number beside the gauge is one the user has to reconcile with the one above it, and the gauge is where elapsed time is read. **The pulse is drawn, not an emoji** — a glyph varies by device font, ignores the theme colour and sits on its own baseline — and it holds still when `ANIMATOR_DURATION_SCALE` is 0, since an infinite animation ignoring "remove animations" is what that setting exists to stop. The day's total *does* still include the open interval, so the pill keeps counting while the rows do not; `ongoing` is what explains the difference. Each row carries one `clearAndSetSemantics` description, because read as separate nodes it arrives as fragments; an open row needs no join, since the range already ends in "ongoing" and the pulse speaks nothing.
- **The check-out celebration is raised by both writers, and never by the day boundary.** `CheckOutSignal` is process-global for the same reason `PresenceCheckSignal` is: a check-out is written from `CheckInViewModel.executeCheckOut` **and** from `MainActivity.onRootGatePassed` (the notification's action, via the root gate), so state owned by the Check-In screen's ViewModel would simply not appear for the notification path. Both go through the one `raiseCheckOutCelebration` helper so they cannot drift, and it reads the day figures against the **closed session's own `date_key`** rather than today — a session belongs wholly to the day it began on, so one closed after midnight reports the day holding the work rather than the empty one it ended in. The day-boundary close reaches neither writer and so celebrates nothing, which is correct: it closes a session the user forgot, usually at midnight with the app dead, and praising them for the one check-out they did not make is the wrong message. **The copy must never grade.** It is identical in wording, emphasis and icon at twenty minutes and at nine hours; a message that warmed as the number grew would be the deleted daily target returning as a congratulation threshold. `CheckOutCelebration` renders *over* the nav host rather than replacing it, so the user's tab survives, and **nothing retires it on a timer** — a tap anywhere and the back gesture are the only ways out. It held for a 2.5s dwell before, which meant a countdown racing the reader, a dwell that restarted on rotation, and a second check-out inheriting whatever was left of the first one's; an explicit dismiss has none of those states. Waiting indefinitely is what makes a staleness stamp necessary, so `CheckOutSignal` carries one exactly as `PresenceCheckSignal` does: `raise` stamps, and `MainActivity.onStart` calls `expireIfStale` on both. The write and the raise complete on a scope that outlives the composition, so pressing Home in the instant after a check-out leaves the flow set with nobody to dismiss it, and the next launch would open on a full-screen congratulation for a session closed long ago. Its `EXPIRY_MS` is **2 minutes against the gate's 10**, and the gap is the point — the gate is waiting on a legitimate round trip out of the app (system settings and back), while this is a reaction to something the user just did and nothing about it survives the moment.
- **The Check-In screen is a fixed, non-scrolling layout — keep it that way.** The gauge and the primary button must both be reachable in one viewport and one thumb reach, so the screen is a weighted `Column`, not a `LazyColumn`, and the day's sessions collapse behind a tap. A weighted `Column` *clips* rather than scrolls when content outgrows the viewport, so `BoxWithConstraints` picks a compact scrolling branch below `560.dp` of height (landscape, very small phones, large font scales) and sizes the gauge from the available height. **A `Column` measures its non-weighted children in declaration order**, so anything declared above the button claims space before it and can coerce it to zero height — which is why the expanded session list is capped at what's left after the chrome, the gauge and the 64.dp action, and why the screen falls back to scrolling when that remainder is too small to be worth showing. `FIXED_CONTENT_HEIGHT` is a hand-derived estimate of that non-list chrome, so **anything that changes the collapsed sessions pill's height has to move it too** — it is 168.dp because the pill's touch target is floored at 48.dp. Adding anything to this screen means re-checking that it still fits — and note the scrolling branch cannot host a `LazyColumn` (it would be measured with unbounded height and crash), which is why the expanded session list has two renderings.
- **The Check-In screen colours the action, never the outcome.** The primary button is a start/stop control: `startActionColors()` (green) to check in or resume, `stopActionColors()` (red) to check out, animated across the switch so it reads as one control changing state. Both come from `ui/theme/Color.kt`; green is the same hue the calendar draws a recorded day in, and each container/label pair clears WCAG AA. Red there is the stop half of start/stop, **not** `colorScheme.error` and not a verdict — no day is ever drawn in it. The screen exists to invite the next check-in, not to grade the user.
- **One 1-second ticker, on screen only.** The Check-In screen runs a composition-scoped `LaunchedEffect` that ticks the on-screen elapsed time while that screen is visible. The service has **no** ticker: its notification uses `setUsesChronometer(true)` + `setWhen(started_at)`, so the platform draws the running clock from a single post and keeps counting correctly through deep sleep. Both share the same origin — the DB row's `started_at`, passed to the service via `EXTRA_START_TIME` — and both now measure the same thing (the open session, not the day), so they agree rather than drifting by the check-in→service-start latency or by the day's completed total. **Do not reintroduce a service-side ticker.** The old one re-issued `startForeground` every second, which over a 16-hour session was ~57,000 main-thread binder calls into system_server, ~57,000 unguarded chances to throw inside a scope with no exception handler, and the behavioural signature OEM background management kills apps for — while still freezing in deep sleep, because a coroutine `delay` is scheduled on uptime and uptime stops when the CPU does. The chronometer costs one post and has none of those properties. Note the body copy must **not** also print the elapsed time while running (`notification_running`, not a formatted duration): the chronometer renders in the timestamp slot, so printing it twice shows it twice, and the printed one would be frozen.
- **Midnight attribution:** a session belongs wholly to its check-in `date_key`, even if it ends the next day (immutable single row). Asserted in `CheckInRepositoryTest`.
- **CSV export** writes to `cacheDir/exports/` and shares via `FileProvider`; it fills gap days with zeros. There is deliberately **no Status column** — it carried the old PRESENT/HALF_DAY_LEAVE/FULL_DAY_LEAVE verdict, and inventing replacement wording would smuggle the same judgement into the one artifact that leaves the device; zero hours and zero sessions already say a day held nothing. **Both ranges are still clamped to the tracked window at both ends** — the gap-filling is exactly why. "This Month" is `max(1st, tracking_start) .. min(end-of-month, countedThrough)`: unclamped, the late end wrote every remaining day of the month out as an empty recorded day including dates that had not happened, and the early end did the same for days before the user had ever opened the app — the same file the All Time export got right. "All Time" runs `tracking_start .. countedThrough`. Both ends therefore **include today once it has been checked out of** and stop at yesterday while it is still in progress, through the same `ConsistencyStats.countedThrough` the screens use (fed by a one-day aggregate query, since the export path holds no summaries map) — a file that stopped short of a day the screen was already counting would contradict the screen it was exported from, and one whose last row was an empty today would assert an absence that is merely a day still being worked. The cost accepted is that an export is a snapshot: check in again after exporting and the file is stale. **A range holding no completed day returns `ExportResult.Nothing`** (a distinct outcome, *not* a `Failure` — nothing went wrong) and writes no file. That test is on the *query result*, not just on an inverted range: a week of abandoned check-ins gives a perfectly well-formed range whose CSV would be pure gap-fill. `ReportsViewModelTest` pins each case.
- **One drawable is the launcher icon, the splash icon and the themed icon.** `drawable/ic_launcher_foreground.xml` is referenced by the adaptive icon *and* by `windowSplashScreenAnimatedIcon` in `themes.xml`, so they cannot drift. They did before: the adaptive icon pointed at `@mipmap/ic_launcher_foreground` (a raster) while the splash pointed at `@drawable/ic_launcher_foreground` (a different vector) — same name, different resource type, two different logos, and nothing flagged it. Keep both pointing at the one drawable. The old raster was also a *baked, pre-masked* icon used as a foreground layer, which hid the background entirely and got clipped by launcher masks; the layers are now genuinely separate (flat indigo background, transparent stroke-only foreground). The `<monochrome>` layer for Android 13+ themed icons points at that same foreground rather than copying its path — a second copy is precisely how the two marks drifted last time. Density-specific `mipmap-*/ic_launcher*.webp` files are **deliberately absent**: at minSdk 34 `mipmap-anydpi-v26` always wins, so they were unreachable weight.
- **The app's own code makes no network calls, and every outbound link is an implicit intent — but the merged manifest is not permission-free.** `AndroidManifest.xml` declares six permissions and networking is not among them (`RECEIVE_BOOT_COMPLETED` is now declared by the app itself, for `BootReceiver`; there is deliberately **no** exact-alarm permission — see the session-alarm entries above); the **merged** release manifest, however, adds `INTERNET`, `ACCESS_NETWORK_STATE` and `WAKE_LOCK` from transitive dependencies (`INTERNET` comes from `transport-backend-cct`, pulled in by ML Kit — check `app/build/outputs/logs/manifest-merger-release-report.txt`). So the honest claim is "session data never leaves this device", **not** "the app holds no internet permission" — the second is checkable by any user in system settings and is false. `ui/about/ExternalLinks` is the one place app code reaches outside: the browser fetches the privacy policy, the mail app sends feedback (`ACTION_SENDTO` + `mailto:`, so it resolves to mail apps only — `ACTION_SEND` would offer every share target), and the Play app handles the rating. Adding a network call anywhere means a new Data Safety declaration — the reason the feedback path is an email the user reads and edits before sending, not a silent POST. Each launcher returns `false` instead of throwing so callers fall back to the clipboard; both `ActivityNotFoundException` (no browser, no mail app) and `SecurityException` (a handler in another profile) are real outcomes, so both are caught.
- **The open-source licence list is hand-maintained, and it is grouped on purpose.** The release runtime classpath resolves to ~220 artifacts that collapse into the upstream projects in `ui/about/OpenSourceLibraries`. **The list is the classpath, not the dependency block** — regenerate it with `./gradlew :app:dependencies --configuration releaseRuntimeClasspath` and group by Maven group id. Listing only the direct dependencies is the bug this replaced: it omitted seven projects, all of them redistributed in the APK, most of them dragged in under ML Kit (`com.google.android.gms`, `com.google.android.odml`, `com.google.android.datatransport`, `com.google.firebase`, plus `org.jetbrains:annotations`, `org.jspecify`, `javax.inject`). Grouping is only sound because the licence is uniform *within* a group, which is why three groups carry non-Apache terms: **ML Kit face detection is not Apache-2.0** (its POM declares "ML Kit Terms of Service"), **`com.google.android.gms` and `com.google.android.odml` declare the Android Software Development Kit License**, and `androidx.camera:camera-core` declares BSD alongside Apache-2.0 for the libyuv it embeds. Don't fold any of them back into an Apache row. `OpenSourceLibrariesTest` guards the list's shape and asserts those non-Apache groups stay non-Apache, but it cannot see the Gradle graph — that half is **`./gradlew :app:verifyLicenseCoverage`**, which resolves `releaseRuntimeClasspath` and fails naming any group id no entry's `coordinates` covers. It also checks `res/font/`, because a typeface is redistributed exactly like a dependency but has no Maven coordinate — those entries carry `coordinates = "font:<resource name>"` (with a `font:family_*` wildcard covering a family's weight cuts) and are matched against `res/font/` instead, or a font dropped in would ship unattributed and pass silently. Only files aapt would package as a font count (`.ttf/.otf/.ttc/.xml`) — an unfiltered listing fails the build naming a `.DS_Store` a Finder visit left behind. It runs in CI (with the tests, not with `staticAnalysis`, which is kept free of dependency resolution) and hangs off `check`, and it declares an output stamp so it is UP-TO-DATE when neither the list nor `res/font/` changed: a task with inputs but no outputs can never be skipped, and this one resolves the whole release classpath. It parses the `coordinates = "…"` lines out of the source file, so it fails loudly if that format ever changes rather than passing on an empty parse. What it deliberately does **not** do is generate the list: a POM-reading generator produces ~220 flat rows and loses both the grouping and the hand-written notes, so drift detection is automated and the wording stays human. Licence text ships in `res/raw` rather than being linked wherever the terms oblige a copy — `apache_2_0.txt` for the code, `ofl_1_1.txt` for the typefaces — because an offline device could not otherwise read it. Which licences get that treatment is `LibraryLicense.bundled`, and the Licenses screen **loops over that flag** rather than hardcoding a block per licence; the raw-resource mapping lives in `LicensesScreen` so the enum stays plain Kotlin the unit tests can read. Each toggle names its licence, since these buttons sit below every card with no other context, and the paragraphs stay individual `items` of the `LazyColumn` — a single `Text` holding 11 KB measures all of it on the frame it appears, which is long enough to see.
- **One description of a notification, one place that builds it, one place that posts it.** All three — the ongoing timer, the session reminder and every nudge — are declared as a `NotificationSpec` and built by `NotificationFactory`; `Notifier.show()` then adds the `POST_NOTIFICATIONS` guard and posts. Building and posting are **separate** because `startForeground` needs the `Notification` object in hand and must succeed with or without the permission, so the timer goes `factory.build(...)` → `startForeground` while everything else goes through the guarded `notifier.show(...)`. **That applies to the per-second update too, not just the first post** — re-issuing `startForeground` updates the notification in place and is exempt from the permission, whereas routing the tick through `notifier.show` freezes the displayed elapsed time the moment `POST_NOTIFICATIONS` is revoked while the notification itself stays on the shade. Hand-building a notification anywhere else re-opens the bug this closed: the mid-session check used to bypass the guard, so a revoked permission meant a `SHOWN` logged for a notification nobody saw. Ids live in `NotificationIds` (service) and on `Nudge.notificationId` (one per nudge, **never reused** — a shared id makes a second nudge silently replace the first, and an ordinal-derived one reshuffles when the enum's priority order changes). A retired id for pre-per-id nudges was carried here for a while and is gone — at ~0 installs there was nothing left in any tray to retire, so it was cancelling an id nothing had ever posted under. **`PendingIntent` request codes are a namespace shared with previously installed versions**, which now spans three bands — notifications (`CONTENT_REQUEST_BASE` 1_000 / `ACTION_REQUEST_BASE` 10_000), the session alarms (20_000, 20_001) and the nudge checkpoint (20_010) —, and equality ignores extras, so `NotificationFactory` offsets them (`CONTENT_REQUEST_BASE`/`ACTION_REQUEST_BASE`) rather than using the bare notification id — the old build's reminder content intent was request code 1, which is now the timer's id, and `FLAG_UPDATE_CURRENT` would rewrite a still-posted notification's tap target across the update.
- **A refused post is not an ignored reminder.** When `notifier.show` is false — a revoked permission, notifications off app-wide, or the reminder channel blocked — `SessionReminderRunner` logs a `DEGRADED` row and re-arms **without advancing `remindersSent`**, so restoring the permission resumes the reminders and the first one the user can actually see still alerts rather than arriving silently mid-ladder. The behaviour this descends from marked the check spent on a refusal and never asked again for the rest of the session, so a revoked permission silently disabled the whole mechanism until the next check-in.
- **"Refused" means three things, and the permission is only one of them.** `NotificationDelivery.canDeliver` — pure, and separate from `AndroidNotifier` for the same reason `EngagementRouting` sits outside its receiver: the class is Android-only, so on a JVM-only suite the decision every caller trusts would be the one part of the path nothing exercises. It refuses when `POST_NOTIFICATIONS` is revoked, when notifications are switched off app-wide, **or when that one channel is blocked while the rest stay on**. The platform reports none of the three: `NotificationManager.notify` drops the post and returns normally. A missing channel counts as undeliverable too — from Android 8 a post to a channel that was never created is discarded, and `ensureAll` runs at startup, so a null means something is already wrong.
- **Attribution errs against the app, in both directions.** A nudge that was *swiped away* earns no conversion from a check-in that follows it: `AttributionRules.canCredit` takes a `latestDismissedAt` alongside `latestConvertedAt`, and `RoomEngagementLog` supplies it from the same `latestOfType` query. Without it a rejection reported as a success, which made the one signal `NotificationDismissReceiver` exists to capture invisible to the only metric that reads it. `latestOfType` is not scoped by key, so a dismissal of *any* nudge since the showing suppresses — accepted deliberately, because under-crediting is the safe direction. Note this **is** now reachable: at `maxPerDay = 2` across three checkpoints, swiping the morning nudge away costs the evening one its conversion credit. That is the intended reading — a user who dismissed today's reminder and checked in eight hours later was not converted by the second copy of it — but it means the reported rate is a floor, not an estimate. Conversely, an **`OPENED` is attributed to the notification actually tapped**: `EngagementTag` (source + key + variant) rides the tap intent as well as the delete intent, so `DefaultEngagementReporter` records against the tag rather than inferring from whatever the log holds as most recently shown — and needs no time window to do it, which also stops under-counting a tap that lands outside the 4h window. `recordOpenedForLastShown` stays as the fallback for a null or retired key: a notification posted by a *previous* release carries no tag and its `PendingIntent` outlives the update. The two intents use different extra keys on purpose — the receiver's are frozen for exactly that reason.
- **Nothing is `autoCancel`, and that is what makes a dismissal mean something.** The platform can deliver a delete intent when an auto-cancel *tap* removes a notification, which is indistinguishable from a swipe — so `NotificationFactory` always sets `setAutoCancel(false)` and whoever handles the tap cancels explicitly (`EngagementReporter.onNudgeOpened` for nudges). An app-initiated `cancel()` delivers no delete intent, so everything reaching `NotificationDismissReceiver` is a genuine dismissal, recorded as `DISMISSED` via the pure `EngagementRouting.resolve`. The session reminder is cancelled when the day boundary closes the session, and otherwise replaced in place by the next one under the same id.
- **The timer channel is `IMPORTANCE_DEFAULT`, and that buys placement rather than noise.** Below `DEFAULT` the shade files a notification into the collapsed *Silent notifications* group — and the timer carries a deliberately **stale** `when`, since the chronometer needs it pinned to `started_at`, so it sinks further the longer the session runs. The failure that closes: a user picking their phone up after a call and a dozen messages has no way to know a session is open, does not check out, and the day boundary then records hours nobody worked onto a row nothing can edit. It stays silent regardless — `setSound(null, null)` on the channel, `setSilent(true)` on the spec, and heads-up needs `IMPORTANCE_HIGH`. **Importance is frozen after creation just as the id is, and far more quietly**: it is applied only at creation, so a changed value is ignored on any install that already has the channel, and revising it for everyone means a new id, resetting every per-channel choice. It follows that **a device running an earlier build keeps the old importance until the app is uninstalled** — the first thing to check when this looks inert. The engagement channel is the worked example: it needed to become `IMPORTANCE_HIGH` so a once-or-twice-a-day message peeks instead of landing in a shade nobody reads for hours, and the only way to make that land on an existing install was a new id (`engagement_channel_v2`), with `deleteNotificationChannel` on the old one so it does not linger in the user's settings. That cost every per-channel choice made against the old channel, and was free only because it happened before an install base. A third id would not be.
- **The timer notification survives Clear all but not a deliberate swipe, and that is why nothing re-posts it.** From Android 14 the platform allows a foreground-service notification to be swiped away **even with `setOngoing(true)`**, which the app sets. Verified on device: **Clear all leaves it alone**, so the accidental path is closed and every dismissal is an individual swipe by someone who just read "session running" beside a Check Out action. Re-posting after that — on unlock, on a ticker, on any cadence — would override a decision made with full information, so the app does none of it. Coverage without it: dismissal inside the first ~2h still meets the session reminder's **first** fire, which is the audible one (`silent = count > 1`) and stays audible even if an earlier post was refused, since a refusal re-arms without advancing the count; dismissal after that meets only silent reminders on the shade; and the day boundary closes the session in every case. The lever if this ever proves too quiet is that one predicate in `SessionReminderRunner.onReminderFired`, **not** a shorter interval — more frequent silent reminders achieve nothing.
- **Notification icons are the brand mark, not platform stock.** `ic_stat_checkin` (a 24dp silhouette from the same geometry) is the small icon for the timer, the reminder and every nudge; `ic_stat_check_out` matches `Icons.AutoMirrored.Filled.Logout`, which the UI already uses for that action. Status-bar icons keep only their alpha channel, so they must stay white-on-transparent.

## Conventions

- Kotlin official code style; Composables PascalCase. `./gradlew ktlintFormat` is the arbiter — don't hand-format against it.
- **Time arithmetic goes through named unit constants, never inline `60 * 60 * 1000`.** `util/TimeFormat` declares the millis/seconds/minutes/hours ladder for formatting; `DefaultCsvExporter` and `TimerGauge` carry their own `MILLIS_PER_HOUR` because they convert rather than format. Detekt's `MagicNumber` enforces this outside Composables, where dp/sp/alpha literals are exempt.
- Each screen observes **one** `uiState: StateFlow<XUiState>` via `collectAsStateWithLifecycle`; VMs are constructor-injected from `AppContainer` through a `viewModelFactory`. Add a `LifecycleResumeEffect { onResumed() }` so prefs changes re-read on return to a screen; the day-rollover is handled reactively by `TimeSource.currentDay()`, not gated on the resume.
- All DAO/repository DB operations are `suspend` (or return `Flow`); Room via **KSP**.
- The day hue comes from `ui/theme/dayColor(...)` (light/dark tuned) — never hardcode it in screens, and never introduce a second colour to mean a worse day.
- **Dates the user reads are formatted in `util/TimeFormat` and nowhere else.** `dateWithYear` ("Jul 25, 2026") for a date read in isolation; `dateWithWeekday` ("Saturday, Jul 25") where the surroundings already supply the year and the weekday earns the space instead; `dateKeyWithWeekday` for the nullable ISO `date_key` the screens hold, returning null rather than throwing on a malformed one. Both patterns are the same abbreviated-month family, so a date is recognisably a date wherever it appears. Scattering them across call sites is the bug this replaced: Reports printed a raw `LocalDate.toString()` ("2026-07-25") and History printed a raw `date_key` under "Sessions on". **`date_key` itself stays ISO** — `CheckInSessionDao` range queries depend on its lexicographic ordering, and the CSV `Date` column is machine-read; only the display side goes through `TimeFormat`.
- Duration/clock formatting goes through `util/TimeFormat` — do not re-implement it. `durationLive` ("0m 0s" → "59m 59s" → "1h 0m") is for a *ticking* clock only — the Check-In gauge and the open interval; everything settled (totals, reports, CSV, past sessions) uses `durationShort`, where seconds would be noise.
- **Two bundled typefaces, split by reading size** (`ui/theme/Type.kt`): **Outfit** on display/headline/title, **Manrope** on body/label. The split follows from their x-heights (0.460 em vs 0.540) — Outfit reads as elegant on the 45sp gauge and thin in a 12sp row, Manrope the reverse; swapping them is the mistake the arrangement exists to prevent. Each weight is a **static instance cut from the upstream variable font**, four per family. The variable files would be 331 KB smaller, but selecting a weight out of one needs `FontVariation.Settings`, which is `@ExperimentalTextApi` — and without pinning the axis the file loads at its default instance and the platform fakes the heavier weights by smearing glyphs. Real cuts buy a stable API and genuine weights; **don't "optimise" this back to two variable files without reintroducing that opt-in.** Only `fontFamily` is overridden — every M3 size, line height and letter spacing is untouched. **`TextStyle.tabularFigures()` on the ticking clock is load-bearing, not polish:** Outfit's default `1` is 321 units against `0` at 659, a 2.05x spread that makes the gauge lurch sideways once a second without `tnum`. Both families resolve the feature to uniform widths (Outfit 590, Manrope 1240), and instancing preserves it along with the embedded copyright notice — check both if the cuts are ever regenerated. Bundling costs 608 KB of resources and means the app no longer honours a device font *choice* — font *scale* is still honoured, everything stays in `sp`.
- **String casing follows the header comment in `strings.xml`.** Section and card titles are Title Case ("Overall Stats", "All-Time Split"), and so are **notification channel names** — Android renders all three as the titles of one list, where a lone sentence-case entry reads as an oversight; everything read as a line rather than a heading — row labels, buttons, help text, empty states — is sentence case ("Open notification settings", "Showed up"). The only exceptions are the product name CheckIn and the "Check In"/"Check Out" actions it is named after. The Reports stat rows are the drift this rule was written from: they were Title Case with a sentence-case parenthetical bolted on ("Current Streak (target met)") while every Settings and About row beside them was sentence case.
- Material 3 with a **fixed brand color scheme** (indigo seed, `ui/theme/Theme.kt`) — dynamic color is intentionally not used — plus system dark mode and a branded splash. Large screens are width-capped (`ui/components/ConstrainedContent`) and History goes two-pane on expanded widths (`WindowSizeClass`).
- **The brand mark is generated, not drawn.** `play-store-assets/generate_icons.py` owns the geometry and emits the `pathData` for `drawable/ic_launcher_foreground.xml` and `ic_stat_checkin.xml`, plus the 512px Play icon — change it there and paste the printed paths back, never hand-edit a path. Its `verify()` asserts the adaptive-icon safe circle on every run.
